## The incoming object and static initialization

`0x00399D60` (192-byte ledger span) takes r0 and retains it in r4; 0x00399DC8 passes r4 to 0x0039AF30 and 0x00399E10 passes r4 to 0x0039B58C on different guarded paths. `0x0039AF30` in turn passes its saved r4 to 0x0039D758 at 0x0039B03C. An aligned text ARM B/BL scan found no direct branch to 0x00399D60. This is bounded scan evidence; callbacks, Thumb and dynamic calls remain open.

A function-pointer-like absolute word 0x00399D60 occurs at 0x00404A8C, adjacent to zero at 0x00404A90. The table base 0x00404A74 is a literal at 0x00399F24 used by 0x00399E20. At 0x00399E20..F20 that routine copies pairs from the table into its input object: specifically 0x00399EA4..B0 loads the pair at table+0x18 (0x00404A8C/90) and stores it at object+0xB24/+0xB28. Thus this is a statically initialized callback-like pair, not by itself proof that an indirect call actually dispatches it or which r0 it receives. Other neighboring pairs include 0x00399854 and 0x0039C564; their names/types are not assumed.

Direct chain 0x00291D2C→0x00399594→0x00399E20 is visible in the original. 0x00291CAC allocates 0x12344 bytes via 0x002C4B84 (0x00291CCC..DC), stores the resulting pointer at the global slot 0x0044CDF0 (0x00291CE0..F0), then passes allocation+0x40 to 0x00399594 at 0x00291D28..2C. 0x00399594 retains its input in r4 and calls 0x00399E20 with that same pointer at 0x003995AC..B0; it initializes object fields including byte +0xC=-1, word +0x10=0 and byte +0x55=0. Therefore the table pair containing 0x00399D60 is installed at allocation+0xB64/+0xB68 for this initialization route. `src/engine/map_runtime.cpp` labels this host Navi and documents "NAVI PROC" task registration; its readable body is disabled and the production body is an exact wrapper. The paired instructions establish a host allocation/embedded object association, not the runtime callback's argument or proof it runs during the H4 checkpoint.

## The two helper contracts correct the +0x162 inference

Callers such as 0x0039B6BC and 0x0039D83C compute r0=incoming object+0x162 before BL 0x00231F58; 0x0039B748 and 0x0039B840 similarly pass that value to 0x00231B38. However, original 0x00231F58 immediately overwrites r0 with literal slot 0x0044CDF0, dereferences it, and returns `*0x0044CDF0 + 0x38`. Original 0x00231B38 likewise overwrites r0 with that slot, loads two words from r1, dereferences the slot, writes those words at global-host +0x38/+0x3C, and returns. Neither helper dereferences the passed +0x162 address. Thus earlier descriptions of these calls as applying to the +0x162 subobject were only a register-level inference and should not be treated as its ownership or type contract. The output pair's interpretation remains unknown, as do null/fault and alias domains. Other functions that receive object+0x162, e.g. 0x002327EC, are outside this pair's established contract; no conclusion about their use is imported here.

The initialization route makes the host slot and callback-bearing embedded object parts of the same statically allocated Navi host for that route; the helpers always address the current global slot and do not verify it still equals the allocation that supplied the callback object. A dynamic dispatch may pass a different pointer, and no lookup of the actual 0x00399D60 entry argument was observed. This distinction matters for multiple allocations, stale pointers and failure paths.

## H4 comparison and next evidence

The H4 field report observes `*[0x00447E88]=0x004BCCD0`, camera helper 0x0027FBC8, and the 0x00208CE8 enemy-manager path via slot 0x00447600. It does not record 0x0044CDF0, allocation+0x40, callback +0xB24, or entry r0 at 0x00399D60. These are different global slots; address equality, host activity and object identity cannot be inferred without reading actual runtime pointers. The shared global gate 0x0049F91C +0x18 also does not establish player work or interaction. No field player, movement, input producer, physical event or H4 interaction is demonstrated by this static association.
