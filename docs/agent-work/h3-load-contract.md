# H3 title-to-load contract: static reconnaissance

Reference: extracted/exefs/code.bin SHA-256 `1f98884fe997af22e032a14c51a46c872b05b0e079a0f29e307b0e059cfaa558` (matches config/game_info.json). ARM instructions disassembled with Capstone 5.0.7, text VMA 0x00100000. These are static observations, not differential or runtime results. Symbols and UI field names are provisional.

## Title entry and return

At 0x001EA32C state 7 tests title work byte +0x7C; if nonzero it exits the callback. Otherwise 0x001EA33C calls 0x002A7604 with 0, 0x001EA348 calls 0x0030A9A4, then state 8 is set. At 0x001EA35C state 8 calls 0x00282DF8; nonzero waits. On zero 0x001EA36C reads signed manager byte via 0x00215918. Nonzero sets title work +0x62 to 1, calls 0x0029C650(15), and enters state 12; zero branches to title reset 0x001EA3D8. The signed byte is a result flag, but the precise semantic meaning and relation to successful load are not proven.

0x0030A9A4 calls 0x00202950 with r0=r1=0, then reads manager 0x0044DE28 +4 (work). It clears work +0x14, manager bytes +0/+1, work byte +0x49; sets work byte +0x379 to 1; calls 0x002BF6D0(0x36,3), sign-extends returned halfwords +8/+0xA to floats at work +0x38/+0x3C; clears +0x49 again, writes word 1 at +0x34 and word 9 at +0x50. No null checks. 0x00202950 itself allocates/initializes resources and registers callbacks; therefore do not replace it with the incorrect conditional-allocation sketch `saveLoadUI_Init_Decompiled`.

0x00282DF8 reads manager +4: null returns 0. Otherwise it calls 0x002B2530(work[0]); nonzero returns 1; zero with work byte +4 zero also returns 1. When both task query is zero and byte +4 is nonzero, it frees the current manager +4 via 0x002C4360 if non-null, stores null, returns 0. Caller inputs must account for callback side effects; this is not a mere flag check.

## UI state and load-related work

Callback 0x001C8D28 loads manager +4, calls 0x002C0B94, dispatches work word +8 if <22 via absolute ARM jump table 0x001C8D48. States 0..9 targets: 0x001C8DA0, 0x001C8DBC, 0x001C93EC, 0x001C997C, 0x001C9A64, 0x001C9B54, 0x001C9D28, 0x001C9D7C, 0x001C9EC4, 0x001CA350. 10..14 go to common exit 0x001CA4A8; 15..21 have distinct entries. The indexed PC load is an indirect dispatch; target bits and valid range are part of the future interworking audit. State 1 has another 8-entry indirect table at 0x001C8DCC. The callback's full UI input selection and cancel branches remain unmapped; do not claim selected slot validity or cancellation behavior.

At 0x001C9918..0x001C9964, after work +0x54 becomes nonzero, byte +0x49 selects state 8 versus state 5 and resets work +0x0C; both invoke 0x0026B7EC(1). In state 5, 0x001C9C14..0x001C9C24 sets work +0x73 and calls 0x0026B874(manager word +8 + 1) when +0x72, +0x73 and +0x355 permit. This is directly observed, but `0x0026B874`'s source label `SaveLoadProcess_Init` and its apparent slot argument are not a proven load operation. State 5 polls 0x0026B864 and has a >30 counter condition, then 0x0026B854; on its nonzero result, 0x001C9CA0..0x001C9CC4 copies 0x80 bytes from 0x002C0B94 result +0x2470C into work +0x24C + manager[+8]*0x80 and sets work byte +0x34C + manager[+8]. Bounds of manager[+8] are unproven. State 5 sets manager byte 0 when 0x0019DFBC(work +0x248) returns 2 (0x001C9B98..AC); when manager byte 0 is nonzero and work +0x355 is zero it enters state 6, then state 7 after two helper checks.

`SaveLoadProcess_Read` 0x00322D70 allocates a 0x18-byte object, invokes 0x0026B7EC/0x002594CC/0x002594AC with 1, and obtains byte +3 from 0x002C0B94 result, placing it at object +0x10 (substituting 1 if zero). It zeroes bytes +0..+4, halfword +6 and word +8 at global 0x0043E2F0; registers a task via 0x002C5978, calls 0x001EC8E4 with task and 0x80000, registers two resources, writes object +4=8, returns task pointer. Despite its name, its exact caller and relation to state 5 require further tracing. Existing `SaveLoadProcess` struct comments assigning operation/status/size/progress are not established contracts.

0x002EF9AC obtains object from 0x002C0AC8, dispatches object word +4. State 4 stores size 0x24DB0 at +0x0C, allocates a buffer at +8, calls 0x00247C64(3,0,object[+0x10],buffer,size), then enters 5. State 5 waits for 0x001A1BF8()==1; then 0x002CED0C()!=0 enters 7; otherwise copies buffer segments of lengths 0x80, 8, and 0x24D28 through helpers, stores byte object +0x10 into returned data +3, calls 0x0026B734, and enters 6. State 6 writes global 0x0043E2F0 bytes +3 and +0 to 1 and returns -1; state 7 writes +3=0, +0=1 and returns -1. Other paths return 0. This is a bounded state description, not proof of on-disk formats or success/error semantics; helper behavior and task registration linkage need verification.

## Recommended bounded implementation and tests

First reconstruct 0x0030A9A4 with original 0x00202950 and 0x002BF6D0 as explicit dependencies. Capture call arguments/order, all listed writes including signed halfword-to-float boundaries (-32768, -1, 0, 32767), initial nonzero memory, and null/fault behavior; test a caller composition for title states 7/8 separately. A second independent slice is 0x00282DF8, with null, task-busy, unfinished, finished, and helper-mutated manager pointer cases, asserting free call and returned value. Both require non-leaf/VFP support where relevant, pinned reference and negative controls; no claim of load equivalence follows from either.

Next map all state 1/3/8/9 and 15..21 branches and direct callers of 0x00322D70, resolve the registered task callback and task-user context, trace cancellation/empty/error paths and manager-byte writes, then obtain an isolated known save fixture and observable scene state. Only after differential and caller-composition coverage plus ARM/Thumb checks may the coordinator compare an autonomous original/patched runtime scenario. No emulator was launched.
