# H18 leaf_batch36_c boundary audit

## Result

The pinned original contains `mov r0, r0` (`00 00 a0 e1`) at each assigned address, followed immediately by a separate ledger entry whose first instruction starts an executable body. The four-byte rows do not return; execution falls through. None is supported as a standalone no-op function. This audit is read-only and does not reconstruct or validate replacement code.

## Reference scan and limitations

- Loaded the image and ledger through `load_pinned_reference`; image SHA-256 is `1f98884fe997af22e032a14c51a46c872b05b0e079a0f29e307b0e059cfaa558`. Each target row is a four-byte ARM `matching` ledger entry with the pinned bytes above.
- Scanned every four-byte-aligned word for ARM immediate BL and immediate BLX encodings targeting each target or adjacent body entry. No immediate BLX encodings matched. Counts are candidate encodings, not individually verified executable sites; data and literal pools can resemble instructions. The cited callsites were decoded as instructions and their containing ledger rows checked.
- Scanned four-byte-aligned words for each exact address and its low-bit-set variant. Only `0x00363a8c` at `0x00420d8c` and `0x0037f76c` at `0x00421abc` were found. These are pointer-like words only; the table boundaries, element type, and runtime use were not established.
- The scan does not resolve register BLX, computed targets, unaligned pointer tables, runtime dispatch, or arbitrary Thumb code. Static xrefs and source declarations do not prove runtime execution.
- No compilation, differential execution, caller-composition runner, or emulator session was used. Suggested C++ routes above are not validated candidates.
