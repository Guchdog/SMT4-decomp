# H2 runtime cave and loader audit

## Finding

The pinned Azahar source and audited title metadata support loading the H2 cave in an executable guest page. The nominal text bytes end at `0x003FE624`, but the loader uses the ExHeader text **page count**, not nominal byte size, for its segment: `[0x00100000, 0x003FF000)`. Thus the entire cave `[0x003FE624, 0x003FF000)` is within that segment, including Calc at `0x003FE624`, Draw helper at `0x003FEE54`, and secondary at `0x003FEED4`. The pool at `[0x0042AB78,0x0042ABBC)` is within the page-aligned read-only segment `[0x003FF000,0x0042B000)`. The H2 crash is not explained by an established execute-permission or page-boundary error. This conclusion assumes the staged binary corresponds to its embedded source commit and the selected NCCH ExHeader matches the independently audited title metadata; it is not a readback of this run's guest memory or PC.

## Loader and patch chain

- [Pinned NCCH loader](https://github.com/azahar-emu/azahar/blob/219d743a1e698101fe1ab8bef43e6563126c3c27/src/core/loader/ncch.cpp#L111-L156) reads the decompressed `.code`, uses `text.num_max_pages * CITRA_PAGE_SIZE`, places rodata immediately after that full allocation, appends rounded BSS, and applies the code patch before moving the vector into the codeset. [Process mapping](https://github.com/azahar-emu/azahar/blob/219d743a1e698101fe1ab8bef43e6563126c3c27/src/core/hle/kernel/process.cpp#L216-L226) copies each full segment and assigns code ReadExecute, rodata Read, and data ReadWrite. This supports the entire page tail, not just the nominal text byte count. [ExeFS load](https://github.com/azahar-emu/azahar/blob/219d743a1e698101fe1ab8bef43e6563126c3c27/src/core/file_sys/ncch_container.cpp#L435-L455) returns the decompressed or uncompressed buffer; the file offset mapping relies on the verified original image and ExHeader layout, not a claim about compressed-file offsets.
- [Patch selection](https://github.com/azahar-emu/azahar/blob/219d743a1e698101fe1ab8bef43e6563126c3c27/src/core/file_sys/ncch_container.cpp#L481-L503) selects the first existing path and logs before calling the patch parser. [IPS parser](https://github.com/azahar-emu/azahar/blob/219d743a1e698101fe1ab8bef43e6563126c3c27/src/core/file_sys/patch.cpp#L15-L52) applies big-endian-offset records to the code vector, checks output bounds and returns failure if a record exceeds it. The H2 log identifies the expected `exefs/code.ips`, but its logging occurs before parse and does not independently prove every guest byte. Subsequent gameplay is consistent with successful loading; no memory readback was captured.
- Run-013 manifest is the intermediate image `7b2bc298...eb2b291`, not the final manual image. Its cave record is file offset `0x2FE624`, length `0x9DC`, and initializer pool record is offset `0x32AB78`, length 68. The manual package also applies mapper and fill/pair patches; its separately reviewed standalone IPS `447074920cee05ab5d8a684b1a8e3142e7f097fa0c021eef1e0ba4b082533788` was independently decoded from the original to final SHA-256 `5e9aa08b449985f012e24400c45b4b037e4a0d5d069723b6cfa7ccf83300d8fa` (533 records), as documented in `h2-manual-comparison-package-review.md`. It is inappropriate to treat the intermediate manifest's single cave record as the standalone IPS record structure.
- Prior independently reviewed H1 report records a live breakpoint hit at `0x003FE720`, in this same page for the same game/title. That is direct prior evidence that one installed H1 payload executed there, but neither demonstrates execution of H2 Calc/secondary nor validates all bytes of this H2 run.

## Failure boundaries and next observations

Initializer is in-place at `0x002F4CA0` (572 bytes), calls original helpers and references the relocated string pool. Calc entry at `0x001EA928` branches to a 2,096-byte cave body with four in-body rebased absolute references. Draw is in place with calls to a cave helper; secondary entry branches to a cave body; the ready gate and mapper/fill/pair bodies are also changed. These are separate possible boundaries, not demonstrated crash causes. Offline comparisons use mocked helper boundaries and do not establish real asynchronous resource readiness, scheduler state, original helper side effects, or runtime register/stack behavior. The preserved log says the IPS was selected, while the user reports closure on opening Audio Settings. The application event identifies host `KERNELBASE.dll` exception `0x20474343`, not a guest fault address or the responsible replacement; its incomplete final log line is not proof of a specific error.

First examine the preserved crash dump for exception parameters, crashing thread stack and any guest CPU context/JIT diagnostics; do not assume the host exception address is guest PC. If absent, a separately authorized, controlled run should capture actual guest PC/registers and memory/permissions around initializer, Calc entry/cave, Draw helper, secondary, and strings before blaming any component. Use an original baseline at the same action and state, and verify loaded bytes by readback. If the cause remains unlocalized, construct independently validated selective patches against the same original: isolate initializer plus required strings, then Calc, Draw/helper, secondary, ready gate, and mapper/fill dependencies as coherent groups, keeping all unrelated entries original; preserve identical profile and inputs and retain negative controls. Change one group at a time and record first failing action/PC. A pass or failure still needs provenance and does not establish whole-game equivalence.

No emulator, socket, profile or firewall change, keyboard/mouse operation, or binary mutation occurred. Source inspection used the pinned public GitHub pages; this report does not claim current-run guest execution or runtime equivalence.
