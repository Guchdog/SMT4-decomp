# Independent review: H4 input-buffer producer trace

## Recommendation

Accept the producer report's static trace within its stated limits. The pinned listing supports the chain `0x001078D8 → 0x0011C5EC → 0x0012A758`, the 16-byte record-copy layout, and the separation between initialization, counter updates, and conditional sample-record refresh. It does **not** identify the source object's producer, physical device mapping, refresh cadence, or a player-work/control path. The report's title should be read as a bounded trace of writes toward the analog buffer, not proof of a complete live-input producer.

## Reference and ledger cross-check

- Pinned `extracted/exefs/code.bin` SHA-256 is `1f98884fe997af22e032a14c51a46c872b05b0e079a0f29e307b0e059cfaa558`, matching the task packet and `config/game_info.json`.
- `config/functions.csv` labels the inspected functions as `matching` wrappers with the reported extents: `0x001078D8` (164), `0x0010A1D4` (360), `0x0010B578` (604), `0x0011C5EC` (304), `0x0012A758` (424), `0x00128610` (148), `0x0013B8F8` (260), `0x0013B9FC` (228), `0x0013BAE0` (460), `0x0013BCAC` (212), `0x0027FBC8` (320), and `0x002C4B30` (84). These ledger labels establish code identity/classification only, not high-level input semantics.
- Direct ARM branch instructions in the pinned image confirm `0x001078E8→0x0011C5EC`, `0x0011C640→0x0012A758`, `0x0011C668→0x00128610`, calibration dispatch from `0x00128658/678/698` to `0x0013BAE0/0x0013B9FC/0x0013B8F8`, conditional `BLEQ` at `0x0011C6FC→0x0013BCAC`, initializer call `0x0010A24C→0x002C4B30`, and `0x0010B57C→0x001078D8` followed by `0x0010B580→0x00108B10`.
- The producer report's aligned literal scan records the relevant constants at their instruction/pool locations and explicitly limits coverage to aligned ARM literals in `.text`. That scan can include embedded data and does not enumerate Thumb spans, computed addresses, indirect calls/pointers, or writes formed without an in-image literal. Its caveat is material and correctly prevents treating the table as an exhaustive writer inventory.

## Verified dataflow and ABI

1. `func_001078D8` loads `*[0x004650A0]` into `r0`, `0x004E3C28` into `r1`, and calls `0x0011C5EC`. The return controls availability at `0x004650A4`: nonzero stores 1; zero stores 0. It then walks 31 mapping rows at `0x004099C0` (8-byte stride), testing each row mask against the same fixed state word at `0x004E3C28`; the state pointer is not advanced. Counter words begin at `0x004E3C58` and advance by four bytes. The loop leaves a counter unchanged when availability is zero for a zero-first-word row; a missing mask bit on the valid-input path resets it, a match increments it, and nonzero first-word rows reset it. This is not evidence of 31 fresh input states.
2. `0x0011C5EC` preserves the output pointer in `r4` from input `r1`. A failing `0x00128C2C` precheck returns 0 before the buffer-copy call. Otherwise it obtains an object through `*[r5]`, passes that object's `+4` pointer as `r0`, output `r4` as `r1`, count 1 as `r2`, and a local count pointer as `r3` to `0x0012A758`; two additional stack arguments are pointers to local cursor/index values. A nonpositive returned count exits with 0. A positive count invokes `0x00128610` using the output's signed halfwords at `+0xC/+0xE` as values and corresponding output-halfword addresses as destinations. Calibration selector byte `+0xC` dispatches to `0x0013B9FC` (selector 0), `0x0013B8F8` (1), or `0x0013BAE0` (2); other values skip these three cases. Exact transformation/clamping contracts remain outside this producer review.
3. `0x0012A758` uses destination `r1 + 16*i`; source is indexed by a ring value and advances in 16-byte units. The copy is three words from source `+0x28/+0x2C/+0x30` to destination `+0/+4/+8`, then two halfwords from source `+0x34/+0x36` to destination `+0xC/+0xE`. It compares snapshots of source fields and retries when they change. The `r2=1` request from `0x0011C5EC` caps this call to at most one output record, namely the first 16-byte record at `0x004E3C28` for the caller in `0x001078D8`. It does not establish a refresh of the second primary record at `+0x10` or the alternate record at `0x004E3C48`.
4. After a positive copy, `0x0011C5EC` transforms `+0xC/+0xE`; it conditionally copies/masks output words `+0/+4/+8` and can clear those words and the two halfwords following helper outcomes. A conditional `BLEQ` can also call `0x0013BCAC` with the output pointer. These are real conditional writers to the primary first record, but helper semantics and runtime ordering remain separate questions.
5. `engine_func_0010A1D4` is initialization/reset evidence: it points the global at the alternate record `0x004E3C48`, clears the byte at `0x004E3C60`, zeroes 0x7C bytes from `0x004E3C58` (the counter region), clears alternate words `+0/+4/+8` and halfwords `+0xC/+0xE`, and clears selection/state word `0x004650A8`. This does not demonstrate refresh cadence or source population. The 31 counters beginning at `0x004E3C58` are distinct from primary records `[0x004E3C28,0x004E3C48)` and alternate `[0x004E3C48,0x004E3C58)`.
6. `0x002C43D4` changes bit 0 of `0x004650A8` according to `r0`; it is source-selection control, not a sample-record writer. `0x0010B578` calls the refresh function and then `0x00108B10`, but static call order alone does not establish it as the scheduler or prove how often it runs.

## Unsupported claims and next observation

The code establishes an object-to-record copy and consumers of the resulting record. It does not resolve the source object/ring-buffer producer, OS or frontend input API, physical stick mapping, record freshness, event order, refresh cadence relative to consumers, safe input injection, or semantic names for each field. The separately reported H4 field observation changes adjacent camera-reader stack outputs while leaving raw buffers untouched; it supports a camera-axis response, not this buffer's real source. No player-work pointer/position/orientation fields, player movement, action/interact target, or map transition are established by this producer trace.

Next, at an authorized isolated checkpoint and without mutating guest memory, observe the actual scheduler entry and repeated timing first; record call entry/return at `0x001078E8/0x001078EC` and `0x0011C640/0x0011C644`, the root and ring-object pointer identities, `r2` request/count, the full primary/alternate 16-byte records and selection bit before/after each call, plus timestamped camera-reader use. Only then correlate a separately verified real frontend input event to the source object and copied halfwords. Do not infer a physical mapping or player movement from address names or camera output alone. Any runtime collection must be assigned, autonomous, read-only, and preceded by the offline-first gate where applicable.

## Evidence and limits

Read-only static review of the pinned image, function ledger, existing producer/caller/control reports, and matching source wrappers. No source/build/emulator/save edits, no compile or test runner, no GDB/RSP or input action, and no new runtime observation. Existing reports are evidence only within their own described domains; this review does not elevate them to a producer differential or H4 equivalence claim.
