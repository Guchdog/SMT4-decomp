# Caller audit: `UiConfig_FillPair` (`0x0027EDF8`)

## Recommendation

The current production implementation is supportable across the statically identified caller alignment patterns **for target-specific ordinary writable memory**, including `camp_func_001d14fc`'s `g_ConfigWork + 0x76`. It now takes `u8*` and emits the original ARM `str` operations directly, so it does not express a potentially misaligned destination as a C++ `u32*`. The coordinator reports separate differential coverage for destination offsets 0–3; this audit did not rerun that validation. Remaining caller-domain questions are allocator success, writable ordinary-memory addressability and object extent, especially for dynamic engine objects. The H2 call is within its declared workspace if allocation succeeds and the expected object is provided.

## Scope and method

Pinned US v0.1.0 `code.bin` SHA-256 is `1f98884fe997af22e032a14c51a46c872b05b0e079a0f29e307b0e059cfaa558`, matching `config/game_info.json`. I scanned every four-byte-aligned word in the 0x2FE624-byte ARM text segment for an ARM `BL` immediate resolving to `0x0027EDF8`, then confirmed each result in its ledger function using `split_asm.py`. The scan found seven sites. A separate Thumb scan of the configured Thumb interval `[0x00100048,0x00101300)` found no `BL`/`BLX` immediate to the helper. Source xrefs also show a generated wrapper call in `src/engine/leaf_batch33_c.cpp`; that is decompilation/build scaffolding, not an eighth original-image call site.

## Contract implications

The pinned helper masks `r1` to its low byte, replicates that byte through the 32-bit value, and executes word stores at `[r0]` and `[r0,#4]`; its footprint is eight consecutive addressed bytes. The isolated experiment candidate in `experiments/semantic_equivalence/h2_pair_fill_candidate.cpp` uses two `u32` indexed stores and remains restricted to suitably aligned `u32` storage. The current production body in `src/engine/leaf_matching.cpp` instead takes `u8*` and emits those two ARM `str` instructions directly. This matches the target-specific word-store operation without imposing C++ `u32` alignment on the pointer. The coordinator reports an independent differential of destination offsets 0, 1, 2, and 3 for this implementation; this caller audit did not rerun or independently inspect that report. Its evidence applies to the tested target ordinary-memory setup, not MMIO or arbitrary invalid addresses.

This current body removes the specific C++ alignment issue previously reported for `+0x76`. It does not prove every dynamic caller's reachable span: the object rooted at `0x00439C88+0x20` still lacks a verified allocation size and lifecycle here. All inspected callers use object-relative addresses and later access those objects, supporting ordinary writable-memory use, but that is not a substitute for an allocator/extent contract. The production helper's target-specific unaligned access behavior is also not portable C++ behavior outside the intended ARM target.

No caller reads the helper's return value or consumes its flags. All seven provide RAM/object-relative destinations rather than MMIO addresses in the inspected setup. For five dynamic/non-H2 sites, the pointer is derived from runtime globals or a function argument; static code demonstrates subsequent accesses to the same object but does not identify its allocator, full object extent, failure path, or alignment guarantee. Those remain explicit caller-contract assumptions.

For H2 specifically, both titleConfig callers use offset `+0x1C`, and the initializer requests a `0x158`-byte object. The span `+0x1C..+0x23` fits the declared object. The helper's inline stores do not themselves require four-byte pointer alignment, but typed `TitleConfigWork` use and the wider initializer still rely on a successful allocator returning the expected writable object with the alignment required by that C++ type. The allocator's success/alignment behavior was not proven here. This is a conditional caller-local finding, not proof of runtime invocation or user-visible semantics.

## Evidence, limits, and next step

- Pinned reference identity: image hash above; ledger identifies `0x0027EDF8` as a 24-byte ARM function.
- Direct-call sweep result: seven ARM `BL` sites listed above; no Thumb immediate `BL`/`BLX` in the repository's configured Thumb interval. The scan does not exclude computed indirect dispatch, function pointers, nonstandard entry modes, or references outside the scanned text segment.
- Disassembly command used: `python tools/split_asm.py --code extracted/exefs/code.bin --addr 0xADDRESS` for each containing function. Source/layout comparison used `rg -n "UiConfig_FillPair|camp_func_0027edf8" src include`, the H2 initializer/header, and the reviewed helper contract.
- No build, test, emulator, or UI action was performed.

Next, independently review the coordinator's offset-0..3 differential record and retain its target/ordinary-memory limits. Verify successful allocation and `TitleConfigWork` alignment/extent for `0x002C4B84`, and resolve reachable extent/lifecycle for the dynamic object rooted at `0x00439C88+0x20` before claiming unrestricted all-caller support. The alignment-specific reason to exclude the `+0x76` caller is addressed by the current target-specific inline-ARM body; allocator and object-domain assumptions remain open.
