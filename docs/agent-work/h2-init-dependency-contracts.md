# H2 initializer direct dependency contracts

Status: static contract research against the pinned US v0.1.0 ARM image and checked-in helper bodies/call sites. No candidate, build, emulator, or runtime test was performed. The initializer is `titleConfig_func_002f4ca0` at `0x002F4CA0`; its detailed instruction contract is in [h2-init-contract.md](h2-init-contract.md). The notes below focus on its eleven direct engine helpers that are the most important external calls.

## Evidence and ABI conventions

The pinned image SHA-256 is `1f98884fe997af22e032a14c51a46c872b05b0e079a0f29e307b0e059cfaa558` per `config/game_info.json`. The initializer's checked-in ARM listing is `src/camp/title_flow.cpp` near its `titleConfig.cpp` section. Function declarations and shared ABI comments are in `include/engine/asd_symbols.h`; implementation mirrors are listed below. Unless explicitly stated, the initializer ignores `r0` from these calls. “No return used” is therefore an initializer-level fact; it does not mean the callee has no incidental result.

The ARM call convention is AAPCS-style: integer/pointer arguments use `r0-r3`, later words use the caller stack; the original wrappers for task factories copy stack argument **bits** through VFP `s0-s3` to the downstream generic process factory. Those words include function/data pointers and should be treated as opaque 32-bit fields, not numeric floating-point values. The helpers' actual register-save masks are mentioned where directly visible. Caller-saved registers and condition flags are not initializer outputs. Do not infer scheduler dispatch order from task creation or callback registration.

## Grouped evidence and what can remain original

The strongest direct, self-contained contracts among the assigned calls are `UiSpriteGroup_Init` (`0x002C3344`), `UiSpriteGroup_BindTable` (`0x002C32F8`) for its descriptor writes, and `UiAnimSprite_SetAnim` (`0x002BDAC0`) for its mode-0 behavior under a valid table/index. Retaining these original calls is straightforward; their narrow effects are measurable. The existing checked-in helper code and declarations can serve as a baseline for a later differential helper test without implying the full initializer is validated.

For the remaining dependencies, the original call itself is the bounded compatibility boundary, but replacing it with a guessed C++ implementation is not supported yet:

- Allocation and failure/resource policy: `0x002C4B84`.
- Process/task creation, bucket registration and parent attachment vs. scheduler/lifecycle: `0x002C5978`, `0x002C4C00`.
- Sprite resource setup and cursor setup: `0x002BDB2C`, `0x0029FAE8`.
- Async asset request and completion: `0x00297704`.
- Sound engine effects and shared UI/global reset: `0x002B8B78`, `0x0029F10C`.

This split is about how much of each helper effect is evidenced; it is not a recommendation to remove effects from a candidate. A non-leaf candidate that calls original helpers still requires correct ARM ABI, relocation support, valid global/data fixtures, and observables for asynchronous/scheduler effects.

## Bounded initializer candidate and differential seam

A first candidate can be limited to reproducing the initializer's **orchestration** while invoking the original dependency functions. The candidate should not inline or reimplement the helpers listed above. Bind the pinned original entry points via an explicit engine-call interface with the observed ABI, including opaque callback words and VFP argument placement, and preserve the tail-call to `UiConfig_CopyPair` (`0x002ADB40`) separately documented in the initializer contract. Preserve the unchecked allocation result and all call order; do not add null recovery or assume task callbacks run during creation.

Use two validation layers:

1. **Helper-envelope/orchestration differential:** execute original initializer and compiled candidate from identical machine snapshots. Start with allocator success and a poisoned `0x158` work region, identical task-pool/global/resource state, config bytes, and table/request state. Compare the return/branch continuation, callee-saved ARM registers and SP, published global pointer, full work region, sprite/cursor subobjects, task handles, config bytes, and ordered helper call trace (target, GPR args, stack words, relevant VFP bit patterns). Record async request and process/task pool effects rather than asserting undocumented scheduler timing. Use original dependencies on both sides when possible; if a helper is stubbed, make its exact modeled contract explicit and compare separately against the original helper before relying on that stub.
2. **Failure and boundary controls:** test allocation success first. Exercise allocation failure only in a separate controlled case: the original initializer has no null check, so a resulting fault is an expected baseline result, not a missing fallback to invent. Vary incoming `r0` and caller-saved scratch because the initializer overwrites/doesn't depend on the argument; seed the work area with distinct nonzero poison to catch blanket-zero assumptions. Use valid pinned table/resource data for positive runs. For async loads, capture request creation and output slots at call/return and after an explicitly modeled completion; do not demand a synchronous loaded-handle value. For task factories, assert argument forwarding, returned tokens, and directly visible node/pool links, but do not assert callback order or task lifetime without scheduler evidence. Use a negative control changing one initializer call argument (e.g. count `0x18`, cursor parameter 3, resource group `0x2F`, or table pointer) and ensure its call trace or resulting descriptor/work snapshot changes.

The real caller layer remains separate: retain MainTitle state-9 transition preparation and call `titleConfig_func_002f4ca0(nullptr)`, then observe state 10 readiness and reset-to-title path. H1 reaches initializer/calc and cancels once, but it does not observe each helper effect, edit semantics, persistence, or task scheduling. A successful orchestration differential is not whole-screen/runtime equivalence.
