# H2 initialization contract: `titleConfig_func_002f4ca0`

Status: researched from the pinned original and checked-in caller/evidence; no candidate, differential run, or emulator run was performed.

## Identity and provenance

- Address/span: ARM-state function `0x002F4CA0..0x002F4EDC`, 572 bytes (`config/functions.csv` currently says `matching`). The listing and checked-in naked wrapper correspond to the pinned US v0.1.0 `code.bin`, SHA-256 `1f98884fe997af22e032a14c51a46c872b05b0e079a0f29e307b0e059cfaa558` (matches `config/game_info.json`). The function ends in a tail branch at `0x002F4E3C`; literals/strings occupy the rest of its ledger span.
- Original listing reproduced by `python tools/split_asm.py --addr 0x002f4ca0`; source mirror is `src/camp/title_flow.cpp:201` onward. Existing `TitleConfigWork` layout and static asserts are in `include/camp/title_flow.h:61-94`.
- The argument in `r0` is overwritten before any read. After restoring the frame, it tail-branches to `UiConfig_CopyPair` (`0x002ADB40`), so the machine-level return is whatever that helper returns; the checked-in title caller ignores it.

## Contract supported directly by ARM instructions

1. **Allocation/global publication.** Prologue preserves `r4-r6,lr` and reserves `0x20` stack bytes. At `0x002F4CB4..0x002F4CCC`, the allocator arguments are prepared as `r0=0x100`, `r1=0x100`, `r2=0`, `r3=0x158`, stack `[sp]=1`; it calls `0x002C4B84`. The returned pointer becomes `r4` and is stored to global pointer `0x0044E2D0` at `0x002F4CE0`. There is no null check, existing-global check, clear/free call, or reuse branch in this function. Thus each invocation calls the allocator and publishes its result; allocator pooling/reuse semantics and the fate of a previous object are unresolved outside this body.
2. **Calculation task.** A 12-byte parameter tuple is formed on the stack with `calc=0x001EA928`, secondary callback `0x002CAEF0`, and workspace pointer `r4`; `AsdTask_CreateCalc` (`0x002C5978`) receives title key `"TITLE_CONFIG_MAIN"`, priority/argument `2`, and two zero parameters. Its returned task pointer is stored at workspace `+0x00` (`0x002F4D10`). This establishes registered entry addresses, not what the task framework invokes first or its lifetime guarantees.
3. **Draw task.** `AsdTask_CreateDraw` (`0x002C4C00`) is called with entry `0x002CAFD0`, key `"TITLE_CONFIG D"`, priority `0xE6`, zeroed optional parameters, and the calc task pointer in the stack tuple. The helper's interpretation of each tuple slot is not independently verified here.
4. **Workspace/object setup.** Calls initialize sprite group at `work+0x3C` (`0x002C3344`), bind it to table `0x00407EC6` with `0x18` entries and zero arguments (`0x002C32F8`), setup sprite at `work+0x5C` with resource group `0x2F`, index `0`, scale `1.0f`, panel `0xC9` (`0x002BDB2C`), then set animation `0` (`0x002BDAC0`). Cursor setup at `work+0xE8` passes args `r1=3`, `r2=3`, `r3=1`, stack `{0,1}` to `0x0029FAE8`.
5. **Explicit field initialization.** It stores zero to `work+8` (`0x002F4DB4`); calls `UiConfig_FillPair(work+0x1C, -1)` (`0x0027EDF8`); writes halfword zero to `+0x1A` and `+0x24`. It loads `"camp/config.bf"` into `+0x14C` and `"camp/config.mbm"` into `+0x150` via `ScriptVm_LoadTable` (`0x00297704`) with third arg zero. Other bytes are initialized only if those called helpers do so; this body is not a blanket zero of all `0x158` bytes. `UiConfig_FillPair` (`0x0027EDF8`, `src/engine/leaf_matching.cpp:2570`) replicates the low input byte across a word and stores two words, so the `-1` argument sets `+0x1C` and `+0x20` to `0xFFFFFFFF` each.
6. **Global/resource side effects.** Calls `Sound_PlaySE(0x99)` (`0x002B8B78`) and `Camp_SetFadeColor(nullptr, 0x323232FF)` (`0x0029F10C`; `r0=0`, color in `r1`). The H1 title-message contract identifies this as the shared `0x0029F10C` null/reset mode (legacy `Camp_SetFadeColor` alias), not a text string. Its documented null-path effects include storing the color and clearing message state; these are callee effects, not direct initializer stores.
7. **Config reads/mapping/copy.** Literal `0x0044E0F8` is loaded into `r5`; bytes `[0]`, `[1]`, `[2]` are read unsigned at `0x002F4E04`, `0x002F4E10`, `0x002F4E1C`. Each passes through a distinct helper (`0x002CAB70`, `0x0021F39C`, `0x002E0AF4`) and stores the result to workspace `+0x28`, `+0x2C`, `+0x30`. Then the function tail-calls `UiConfig_CopyPair(dst=work+0x34, src=0x0044E0F8)` (`0x002ADB40`). `UiConfig_CopyPair` (`0x002ADB40`, `src/engine/leaf_matching.cpp:2452`) performs two word loads from `src+0/+4` and stores them at `dst+0/+4`; this tailcall copies exactly eight bytes from `0x0044E0F8` to `work+0x34/+0x38`. The global’s total storage extent still depends on its producer/layout. The mapper table domains/results and any additional hidden effects need separate evidence.

## Layout facts vs meanings inferred

The offsets/sizes and accesses above are facts. `TitleConfigWork` is `0x158` bytes; checked-in types divide it into task pointer `+0`, opaque fields through `+0x38`, sprite group `+0x3C..+0x5B`, sprite `+0x5C..+0xE7`, cursor `+0xE8..+0x14B`, and the two table outputs at `+0x14C/+0x150`. Static asserts confirm the declared offsets and size.

Only the task pointer, subobject spans, table output slots, and stores/call destinations are grounded by the initializer. The semantic meanings of fields `+0x04`, `+0x0C..+0x18`, `+0x28..+0x30` (mapped selection values), `+0x34/+0x38` (copied config pair), and `+0x1A/+0x1C/+0x20/+0x24` are not all established just by their names/comments. The signed `-1` fill at `+0x1C` is directly passed to `FillPair`; the checked-in helper proves it fills both words at `+0x1C/+0x20` with all ones. Likewise `+0x34/+0x38` are known eight-byte copy destinations, while the pair’s logical interpretation is inferred from H2’s audio-options scope.

`include/camp/title_flow.h:229` declares the eight-byte global, and says the config/save loader initializes it. In this function only first three bytes are mapped and bytes `[0..7]` are copied to the work pair by the helper; no write to `g_ConfigBytes` is visible in this body. The header documents an eight-byte persisted option block; any larger global storage extent is not established here.

## Caller and prior runtime evidence

- Checked-in caller (`src/ui/ui_runtime2.cpp` around the State 9 case; original main-menu callback block `0x001EA398..`) waits for `work->flag_7c == 0`, calls `Script_PrepareTransition(0)`, invokes `titleConfig_func_002f4ca0(nullptr)`, then sets title state to 10. State 10 polls `TitleConfig_IsReady` (`0x002FC0EC`) and calls `Title_ResetForBoot` when ready. State 9 is selected when main menu option 2 is confirmed; selection is four-way and option 2 is Audio Settings.
- H0 (`docs/milestones/H0-reproducible-test-base.md`) recorded a live title → Audio Settings → title/cancel pass on US v0.1.0, using A and B, plus screenshots; it saw patch hits only at `0x0037C46C` and `0x002ADB40`, not this initializer. No settings were changed and no save files were present at end. This is traversal/safety evidence, not initializer equivalence or confirmation semantics.
- H1 integration evidence (`docs/agent-work/h1-menu-slice-integration.md` and its review) reports a 11-step original-vs-patched menu scenario reaching `0x002F4CA0`, then callback `0x001EA928` with allocated pointer `0x086E4700`, and returning via cancel to title state 5. `g_ConfigBytes` stayed `3250503000000000` and save files remained absent. It corroborates the caller path and one observed allocation/config baseline only; it does not observe each initializer store/call, task/draw setup internals, changed settings, or confirmation persistence.

## Registered secondary callback and lifecycle boundary

The initializer registers `0x002CAEF0` as the secondary calculation callback. Its checked-in ARM body in `src/engine/leaf_batch32_c.cpp:3578` resolves `g_TitleConfigWork`, sets `work+4`, drains the signed counters at `+0x1A` and `+0x24` through `0x002B9008`, releases/clears handles at `+0x154`, `+0x14C`, and `+0x150`, then proceeds into task/global cleanup. This establishes a cleanup role for the callback; it does not establish scheduler ordering, the exact lifecycle trigger, task framework ownership, reentry safety, or all indirect cleanup effects. Those remain open and must be treated as callback/lifecycle dependencies.
