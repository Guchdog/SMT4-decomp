# H4 field-control contract — static reconnaissance

Reference `extracted/exefs/code.bin` SHA-256 `1f98884fe997af22e032a14c51a46c872b05b0e079a0f29e307b0e059cfaa558`; ARM disassembly with Capstone 5.0.7, VMA 0x00100000. This report is static analysis cross-checked against the existing H3 capture, not an H4 runtime test or functional equivalence claim.

## Starting point and identity

H3 paired runtime captured a known private save, slot 0, at the Shinjuku Station — Underground screen after 250 matched callbacks at 0x00208CE8, entry registers r0=0x3B, r1=r2=0x4096CBE4, r3=3. Reading that latter address returned E0E; neither position nor a player object was established. Screenshots support scene identity, not player/camera work identity. See `h3-runtime-comparison.md` for fixture/profile hashes, replay and bounded negative controls. No new emulator session was run.

The name `Map_Field3DManager` and `MapFieldWork` layout in map_field.h are unsupported as a player/camera contract. At 0x00208CEC the function immediately overwrites incoming r0 with a literal, loads `*[0x00447600]` at 0x00208CF8, and at 0x00208D6C..80 indexes records `base+0x34+index*0x180`, reads entry byte +0 and word +0x84, dispatching 26 states using `ldrlo pc` at 0x00208D88. This corresponds to the static `MapEnemyWork` pointer slot and records documented in map_runtime.h; it does not demonstrate that r1/r2 were valid work pointers or that this routine controls the player. 0x001D30CC directly calls 0x00208CE8 inside 0x001D2F1C; at 0x001D3038..58 flags can bypass this call, and at 0x001D2F20..34 it loads the same manager through 0x00447600. The caller's scheduler registration and precise H3 path to it remain unproven.

A view-object pointer slot is 0x00447E88. At 0x001D3060..88 caller 0x001D2F1C loads `*[0x00447E88]`, copies +0x28..+0x30 to manager +0x14..+0x1C, copies +0x7C to manager +0x20 and float +0x50 to +0x24, then derives further values with 0x0028277C and 0x00282600. The H4 follow-up observes the slot value `0x004BCCd0` in both paired runs. 0x001FA8B4 loads this slot and 0x001FA930..48 reads view +0x28..+0x30 before calling 0x0027FBC8. The helper call and opposite-sign state response are dynamically observed below. This establishes an active camera-state update path, but `camera_pos`, player anchor, individual coordinate meanings, and rendered-camera effect remain unverified.

## Input helper and candidate calls

0x0027FBC8 loads literal global 0x004650A0, dereferences its word +0, selects signed-halfword range endpoints using byte +0x18 (0: +0x0C/+0x12; 1: +0x0E/+0x14; otherwise +0x10/+0x16), and computes float denominator `(end-start)`. Mode r2 >=2 unsigned, or global word +4 < mode, returns 0 without output writes. With global word +8 bit 0 clear, source is 0x004E3C28 + mode*16; when set it is 0x004E3C48 (independent of mode). A null source returns 0. Source signed halfwords +0x0C/+0x0E are converted and divided by the denominator; if global float +0x14 is nonzero each value goes through 0x0019FE4C; if both results compare equal to zero then return 0. Otherwise each nonnull output pointer is written and return 1. With zero threshold the function writes zero results and returns 1; zero denominator/NaN, FPSCR behavior, dynamic validity and helper semantics require actual tests. This is an axis-like reader, not proven to be the field control input used by the saved scene.

Direct BL sites in the original include 0x001FA948 within 0x001FA840, 0x002C9748 within 0x002C8C90 (the source describes a world-map route camera), plus 0x001FE650, 0x00254E10, 0x00272564, 0x00272888, 0x002D508C, 0x002E982C, 0x002FBA20 and 0x0031E5B4. At 0x001FA948 mode is 0 and output pointers are stack addresses; the caller's flags at 0x001FA8C8..E8 can take a different early path. Direct-call enumeration is not exhaustive for indirect calls. Trace those outputs to actual motion before selecting an H4 reconstruction.

## Transition boundary

0x0027EE6C allocates 0x80 bytes and stores it to pointer slot 0x004475B8 (0x0027EE9C..A8). Non-null request +0 chooses cases 0,1,2; mode 0 copies request +4 to work +0x10 and a helper-returned object +0x24; mode 1 or 2 copies request +8 to work +0x14 and writes 1 or 2 to work +0x0C. With runtime state word >=100, it copies request +0x10..+0x1C to work +0x48..+0x54. Null and other mode paths differ. 0x001BBF78 in FlowScript_DispatchNativeCommands and 0x001D73AC in FlowScript_ExecuteOpcode call it with stack request first word 0 and next word loaded from a script/runtime field. This is a plausible script departure boundary, not evidence of any particular door, destination, interaction, or action in Shinjuku. 0x00270BD4 is another direct BL site. Confirm callback pointer, request provenance, destination and timing before attributing a zone transition.

## Required capture and comparisons

A reproducible movement/camera/interaction/zone script cannot yet be stated honestly: missing are the real controller sampling source/cadence and its physical/frontend mapping, a readable player-work pointer and position/orientation offsets, a rendered-camera screenshot tied to the observed view-state changes, an identified interactable and its range/event ID, and a reachable doorway plus source/destination map IDs. H3's trigger hooks 0/1 were demonstrated only for the save UI and cannot be assumed to drive field input. The passive and controlled camera evidence now lives in `h4-live-input-observation.md`. Use known mapped memory only, follow dereferenced pointers with read-back, log exact frame counts and initial profile hashes, and verify candidate fields by controlled input and visual/coordinate correlation before naming them.

Once observed, freeze the exact action sequence: initial settled frame; neutral frames; bounded movement input and release; distinct camera input and release; approach a uniquely identified target, one interaction edge; approach a uniquely identified exit, cross it, wait for destination readiness. At each stage compare original vs patched input samples, task/branch sequence, work pointer identities where stable, position/orientation and camera values only after validated offsets, event/interaction state, map identifier and screenshots. Pair no-input stationary and invalid/out-of-range interaction controls; explicitly define tolerance and asynchronous wait bounds from original baseline. Compare profile/save hashes and stop on any mismatch or timeout. Do not equate image similarity alone with coordinate or event equivalence.

For the 0x0027FBC8 candidate, isolate original dependencies, test mode 0/1/2 and unsigned boundaries, both source modes, all calibration selectors, signed extreme halfwords, threshold zero/nonzero, null outputs, both output zeros, negative values, denominator zero, NaN/Inf and exact FPSCR assumptions; compare return, memory, helper calls and fault behavior, plus composition with observed field caller. Use mutation/negative controls. Preserve VFP ABI and ARM/Thumb bits. The 0x00208CE8 callback is a large multi-state enemy-manager path, not a sensible player-movement first slice. 0x0027EE6C is a bounded future transition construction slice only after actual H4 caller/request is observed. Offline differential and caller-composition with interworking checks precede the coordinator's autonomous original/patched runtime comparison. No evidence here fulfills H4.

## Runtime follow-up (2026-10-28)

The new passive paired capture confirms the H3 checkpoint reaches the camera path. At the 250-field-callback stop, `*[0x00447E88] == 0x004BCCd0` and the view prefix is readable in both original and H3-patched runs. The task at `0x001FA840` is reached with entry registers `(r0,r1,r2,r3) = (1,0x801,0xC19FFFF6,250.0f)` and returns to `0x002767D4`. Inside it, the BL at `0x001FA948` reaches `0x0027FBC8` with `mode r2=0`, output pointers `r0=0x0FFFFCB4`, `r1=0x0FFFFCB0`, and `r3=250.0f`; these are adjacent caller-stack slots. The original helper returns `r0=1` and writes `+0.0f,+0.0f`. Both source buffers sampled at `0x004E3C28` and `0x004E3C48` are zero in the neutral checkpoint. See [the paired observation report](h4-live-input-observation.md) and raw JSON in the ignored H4 build evidence directory.

A controlled GDB intervention at the helper's observed return boundary changed only those two validated stack output slots, leaving the raw input buffers untouched. With `(0.5,0.0)`, the view's anonymous floats at +0x24,+0x30,+0x4C,+0x50 changed from `(250,250,270,270)` to `(261.666656,285,300,-0)`. With `(-0.5,0.0)`, they changed to `(238.333328,215,240,180)`. In the neutral `(0,0)` run, the full 0x170-byte view prefix was identical across the same camera call. Original and patched outputs were byte-identical for each scenario. This supports a causal axis-to-camera-state path and opposite X responses, but no screen was captured during the intervention, so no rendered movement or camera appearance is claimed.

The keyboard automation attempt could not focus Azahar in this unattended desktop session (`foreground: Idle`), so it is not evidence of a real frontend key mapping. H4 still lacks a confirmed player-work pointer/position, movement input path, identified interaction, and destination transition. The camera probe narrows the next reconstruction target to the 320-byte axis reader on a real field caller; it does not close H4.
