# H4 source cursor and producer reconnaissance

Reference `extracted/exefs/code.bin` SHA-256 `1f98884fe997af22e032a14c51a46c872b05b0e079a0f29e307b0e059cfaa558`. Read-only ARM disassembly and aligned ARM BL scan of text 0x00100000..0x003FE624. This does not cover all Thumb, indirect/computed branches, data mistaken for instructions, runtime-created pointers or external code. The earlier independently reviewed paired trace observed `r0=0x10000000`, `r1=0x004E3C28`, `r2=1` at 0x0011C640; its reread is after several probes, not immediately after this call. The object changed in both processes; those changes cannot be attributed to a particular writer from those snapshots.

## Source-object access and copy

`0x0011C5EC` (ledger 304 bytes) receives a root in r0 and output pointer in r1. At 0x0011C620..640 it loads r0=`*(*(root)+4)`, sets r1=output, r2=1, r3=pointer to a local count and passes two local cursor/index pointers on the stack, then BL 0x0012A758. In the captured instance that source pointer was 0x10000000. The root's indirection identifies the particular dynamic base **at that call**, not all objects with similar offsets.

`0x0012A758` (ledger 424 bytes, ARM entry) initializes the output-count word through r3 to zero, returns early if signed requested count <=0, and caps positive count at 7. At 0x0012A780..790 it reads source word +0x10 into r4 and `ldrd` pairs at +0 and +8 into r8/r9 and r2/r3 respectively. It examines the signed count and cursor pair equality, compares caller cursor values and computes an available item count; comparisons involving upper words use signed ARM conditions. These fields have a cursor/snapshot role in this helper, but not a proven event count, timestamp type or device identity.

For each selected item at 0x0012A83C..98, the source index is the ARM signed remainder-by-8 computation of `(r4 - i + 8)`; destination is `output + i*16`, source base `r0 + index*16`. It loads source words +0x28/+0x2C/+0x30 and halfwords +0x34/+0x36, and stores them respectively to destination +0/+4/+8/+0xC/+0xE. For the observed r2=1 at most one record is copied. A hypothetical first iteration with effective r4=3 uses source offsets +0x58/+0x5C/+0x60/+0x64/+0x66; with effective r4=6 it uses +0x88/+0x8C/+0x90/+0x94/+0x96. These examples are conditional; r4 may be adjusted by earlier branch logic, and 0x0011C640 pre-call count and later reread cannot prove which record was actually selected. Noncanonical negative/overflow r4 values need independent domain and fault analysis.

At 0x0012A89C..D8 the helper rereads object +0x10 and both 64-bit fields; if any differ from the snapshot it retries from 0x0012A780. On equality, 0x0012A8DC..F4 writes the selected count and updates the caller-provided cursor/index storage; these final stores target pointers supplied on the stack, **not** demonstrably source-object +0/+8/+0x10. The copy helper is a consumer of those source header fields; its consistency reread does not identify the producer or guarantee an atomic whole-record capture if the source writer does not follow an established protocol.

After the BL, 0x0011C644 reads the local result count; nonpositive returns failure. A positive count passes output halfwords +0xC/+0xE by pointer and value to 0x00128610, and modifies or conditionally clears output words and halfwords as detailed in the frozen producer review. Thus the observed buffer may differ from the raw copied record; do not equate post-transform output with an untouched source slot.

## Callsite and producer boundary

An aligned ARM direct-BL scan of the pinned executable yields 0x001078E8→0x0011C5EC and 0x0011C640→0x0012A758. The neighboring 0x0011C3C0→0x0012A900 uses a different helper and 8-byte record layout; equal offset names do not establish it has the captured object as base. A scan finds a 0x10000000 word at 0x002A4638, but a raw constant alone does not link that location to the captured object or prove a producer. No source-object header or indexed-payload writer, initializer, device API, or thread has been established through these paths. This is a bounded negative result, not proof none exists.

The source reread reported dword +0x10 and +0xB8 moving together, and bytes +0xA8/+0xB0 matching +0/+8 at both sampled times. The helper reads +0/+8/+0x10 and indexed +0x28..+0x36 only; it has no fixed +0xA8/+0xB0/+0xB8 access in its copy. Those later bytes fall within the broader 0x100-byte observed span, but the copied payload for normal indices 0..7 ends at +0xA7; numerical proximity or coincident values is not proof of a second header, structure boundary, ownership, relation, or writer. No dynamic source-index or per-write trace establishes which byte changes were read by this call.

## Safe next observation

The evidence supports a **read-only**, separately assigned trace at entry and immediately after 0x0012A758, recording r0/r1/r2/r3, the two stack cursor pointers and contents, source +0/+8/+0x10, selected source-index calculation or executed copy-instruction registers r3/r7 at 0x0012A858..94, the raw 16 destination bytes before 0x00128610 and at post-transform return, and a second contemporaneous snapshot of +0xA8/+0xB0/+0xB8. Log each event and process separately with neutral control, actual pointer read-back and bounded retries. Only this can establish an observed read/order for that execution; it still cannot identify the external producer or physical input by itself. Runtime requires exclusive assignment and applicable offline-first checks; no guest writes, source-save access or emulator run occurred in this task.
