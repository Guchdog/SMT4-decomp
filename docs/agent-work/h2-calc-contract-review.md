# Independent review: `TitleConfig_Calc` contract (`0x001EA928`)

Review scope: compare `docs/agent-work/h2-calc-contract.md` with the pinned original, titleConfig registration, readiness predicate, and title caller. Reference image SHA-256: `1f98884fe997af22e032a14c51a46c872b05b0e079a0f29e307b0e059cfaa558`. This is a research review, not candidate or milestone approval.

## Review result

Most of the contract's branch and memory observations are supported by the instructions. Two concrete address-arithmetic descriptions need correction before they are used as an implementation contract:

1. **TBB row stride is `0x96`, not `0x56`.** In the display paths at `0x001EAA24..0x001EAA34`, `0x001EADE8..0x001EADF8`, and `0x001EAEDC..0x001EAEEC`, the instruction sequence is `rsb r1,r4,r4,lsl #4`; `add r1,r1,r1,lsl #2`; `add r0,r0,r1,lsl #1`. For non-wrapping mathematical index `r4`, that is `(16−1)*5*2 = 150 = 0x96` bytes per selected payload row, followed by `+0x16`. The report's `0x56` claim and its proposed `0x56` negative control are unsupported. Keep the exact ARM arithmetic in the report/tests and use a deliberately wrong nearby stride (for example `0x56`) as a negative control against proven `0x96`.
2. **The `sl` comparison is an entry snapshot of the selected work value, not a TBB row payload.** At `0x001EAA90`, `r6 = work + (selection<<2)` and `ldr sl,[r6,#0x28]` captures `work[0x28 + 4*selection]`. After the input handling and possible mutation, `0x001EACE8` reloads `[r6,#0x28]` and compares it with `sl`. The later “equal/changed” paths therefore test whether this work option value changed during the callback. They do not compare it with the display TBB payload. The report's references to “row payload value” in this comparison and its equal/unequal branch explanation should be corrected.

The arithmetic review can be checked directly: `(16 - 1) * (1 + 4) * 2 = 150 (0x96)`. Since selection is held in a register sourced from list-cursor helper calls, behavior for a malformed or large selection remains unsafe/unbounded unless those helper/caller contracts establish its range; do not generalize the multiplication to arbitrary C++ signed inputs without defining overflow/range behavior.

## Independently supported claims

- The original is a 1796-byte ARM callback at `0x001EA928`; the state dispatch reads `[work,#8]`, uses an unsigned `<5` dispatch, and jumps to `0x001EA964`, `0x001EAA60`, `0x001EAF98`, `0x001EAFEC`, or `0x001EB004`. States `>=5` reach the common `r0=0` return. State 4 returns `-1` at `0x001EB004`. The prologue/epilogue save and restore `r4-r12` and `lr` and restore SP.
- State 0 has resource/script readiness gates before it writes state 1. State 1 contains explicit selected work-value decrement/increment clamps at `0` and `10` (`0x001EABEC..0x001EAC54`). These facts prove local clamp behavior, not the full user-visible range or event meaning.
- State 1 writes config bytes `+0..+3` from work/map-encoder values (`0x001EACB4..0x001EACE4`); its row-specific branches also write defaults to bytes `+0`, `+1`, `+2`, and `+3`. State 2 only writes byte `+4` on the branch where `0x00297674()` returned zero (`0x001EAF C8..0x001EAF E0`; addresses without spaces: `0x001EAFC8..0x001EAFE0`). No save-file/flash write is visible in this callback. The report is right to leave commit, rollback, and cross-session durability unresolved.
- `titleConfig_func_002f4ca0` stores the allocated work at `0x0044E2D0` and registers `0x001EA928` and `0x002CAEF0` in the `AsdTask_CreateCalc` argument block (`0x002F4CD4..0x002F4D00`). The callback ignores `r0` and loads its work through the global.
- `TitleConfig_IsReady` (`0x002FC0EC`) returns true if the work global is null or if `battle_func_002BF41C(work->calc_task)` says the task is no longer alive. The title state-10 caller waits on this result, then calls the reset path at `0x001EA3D8`; state 9 invokes the initializer. These are consistent with `src/ui/ui_runtime2.cpp` and original caller boundaries recorded in H1.
- The secondary callback at `0x002CAEF0` sets `work+4`, drains counters, releases script/resource handles, destroys its task if present, and frees/nulls the global. Names such as “confirm,” “cancel,” “sound,” and “animation” still require behavioral evidence; the original branch targets alone do not assign those meanings.

## Remaining limitations / recommendation

The report appropriately marks input decoding, state-2 decision semantics, re-encoding helpers, audio/script side effects, and persistence semantics as unresolved. Keep them as original dependencies or resolve them with separate evidence. Do not infer that the `0` and `1` returns from `0x00297674` mean cancel/confirm solely from structure; the milestone's changed-option cancel and confirmation scenarios remain untested. Existing H1 evidence only covers entry/no-edit cancellation and unchanged bytes.

Before implementation, correct the two arithmetic statements above in the source contract and packet copy, then add a focused address-arithmetic check: exercise selections `0,1,2` against original-calculated offsets `0x16`, `0xAC`, `0x142` respectively (`0x16 + n*0x96`) and a negative control using `0x56`. Do not claim those three selections are the full valid domain without cursor setup evidence. Keep the requested caller scenarios for no-change exit, changed-option cancellation, edited boundaries, both state-2 result paths, state-5 return, re-entry, save/config data, and clean restart. Compiled, ARM differential, caller-after-edit, and runtime evidence remain unrun in this review.
