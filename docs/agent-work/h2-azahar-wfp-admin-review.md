## Conclusion

The capture does not prove either the localhost connection decision or the non-loopback boundary. These are distinct questions. If an independently established, current non-loopback boundary holds throughout the wildcard listener lifetime, an attempt to 127.0.0.1 can be safe with respect to that boundary even when localhost availability is unknown; a denial merely prevents the probe. Connecting to loopback does not itself constrain the wildcard listener against other clients. This review did not launch or connect to anything.

The saved rule is enabled, inbound block on all profiles and all protocols, with non-loopback remote ranges; its configuration supports the intended boundary. It is a local rule snapshot, not a demonstrated effective classification. The elevated WFP inventory does not identify the global rule or a non-loopback classification result. Its query arguments and capture time are not embedded; the adjacent failed non-elevated command specifies loopback remote address, so, if the elevated command used the same scope, absence of a non-loopback filter is expected and is not evidence that the rule was inactive. The current ActiveStore and third-party filter arbitration remain unproven for non-loopback flows, including the Radmin interface. Saved profiles all have firewall enabled with default BlockInbound, but do not settle local rule merge or the final WFP decision. The IPv4-only capture does not establish an IPv6 boundary.
