# Independent review: H2 APT Utility-4 paired runtime entry

## Scope and result

Reviewed the assigned run-001 packet, the run-003 runtime report and offline attestation, the probe source/tests, relevant staged runtime logs, and the documented prior failures. This was a read-only review: no emulator, debugger, build, or test was run, and no save was opened or hashed by the reviewer. All 23 non-save files listed in the review packet's `input_sha256` map still match their pins. The selected base/candidate images and IPS files also match all four hashes in the runtime attestation.

Recommendation: retain this as **bounded runtime evidence for the entry-to-wrapper path only**. Do not promote the candidate or close H2. Correct the report's breakpoint-cleanup field and preserve the actual bytes read before relying on the report as independently replayable evidence.

## Captures verified from run-003

Both sides report a stop at `0x002C0EFC` with `LR=0x00103E84`; both then stop at the original wrapper `0x002B5A1C`, `LR=0x002C0F20`, `SP=0x0FFFFEF0` (`SP & 7 == 0`), and arguments `(4, 0, 0, 0, 0, 0)`. The report includes `r0=0x0044E3B0` and `r5=0x00465198` at entry. It marks the wrapper body as not entered, which matches the breakpoint address. The candidate image differs from the reviewed base at 29 bytes, all in the 40-byte candidate body. Both runtime-entry byte checks are reported true.

I independently re-hashed the selected base and candidate images and IPS files: all four match the attested values. The expected 44-byte image spans at file offset `0x1C0EFC` hash to `b9a39d87d00611a2803ab486d556fca74afbae3c52a3294e98569550151f9a55` (base) and `24df48386fd274d2f96593370f951f634f412028fa517e0017db3860760daa1c` (candidate). The runner reads 44 runtime bytes and compares them to the selected image, but the runtime report stores only a boolean, not those bytes or their hash. Thus the source code supports the reported comparison, but the saved report does not let a reviewer independently recompute it.

The two listener records are exact loopback rows: `127.0.0.1:62180` owned by host PID `24792`, and `127.0.0.1:62181` owned by PID `20820`. The runner checks both address and PID, then connects to `127.0.0.1`. Run-002 Azahar logs independently show the title ID and `patching code.bin` for both sides. Their SHA-256 values are `11a0ebcaadce87a855391a2548019930e1dd8b619f35ba53a27f96c74def80ea` (base) and `17362b1f02aea320a2cc0256bb1c0ca645971afedc1d5db3015959aaa75f8933` (candidate). Each process was terminated after capture, exited with code `1` from bounded termination, and has `listener_after_cleanup: null`; this is not evidence of a clean emulator shutdown.

## RSP and save-isolation limits

The reviewed runner's RSP path uses `Z0`/`z0`, continue, register reads, memory reads, and detach. It does not call its memory-write helpers or send explicit `M`, `P`, or `X` packets; it injects no logical input. The report's empty `explicit_rsp_memory_write_packets` field is generated by the runner rather than a persisted packet transcript. Software breakpoints can temporarily alter target code internally, so the defensible wording is “no explicit RSP memory-write packets,” not “guest memory was never changed.”

There is a concrete serialization bug: the report object sets the wrapper breakpoint's `cleared` field to `false` before the subsequent `rsp_clear_bp(rsp, WRAPPER)` call. The helper raises unless `z0` returns `OK`, and a captured result proceeds past that call, so the code path indicates successful removal while the JSON says it was not cleared. The actual RSP transcript is not saved, so this is an inconsistent report field rather than an independently retained acknowledgement. Record/serialize the field only after the successful `z0` response.

The probe hashes the protected source save before and after, but does not pass its path to Azahar. It copies the pinned disposable fixture to a fresh staged profile and checks the staged copy; the report says source and fixture hashes were unchanged. The reviewer did not independently hash either file, as required by the no-save-access scope. `profile_seed_contains_save` is a literal `false` in the runner's stage record, not a recorded recursive inventory. The staging code uses the approved seed/profile path and then adds the disposable fixture at the isolated save path; the process command contains only the staged Azahar executable, GDB port, and CCI.

The run-003 packet pins `tools/h2_autonomous_gdb_verify.py`, and its current hash matches that pin. It does not pin the directly imported RSP/listener helpers `tools/h2_azahar_rsp_probe.py` or `tools/h2_apt_utility4_caller_probe.py`, nor `tools/h2_calc_code_patch.py`. Their current hashes were recorded during review, but without run-time pins their exact versions at capture time are not established.

## Prior failures and provenance

The first narrow attempt (run-001) stopped before guest capture. Its Azahar log records failure creating/opening the staged `nand/.../config` path followed by an assertion; that logged path is exactly 260 characters. The report has `partial_or_failed`, no breakpoint capture, and early process exit. The later run uses verified 8.3 aliases and a projected save path of 254 characters, and run-003 contains both successful bounded captures. The first attempt therefore contributes no runtime contract evidence and does not negate the later capture.

The broader TitleConfig runner's WM_CLOSE failure is recorded in the implementation note and bounded summary as occurring after the original side, before its patched side. The only assigned broad-runner stderr file is empty, and the packet contains no primary WM_CLOSE failure report, so this review cannot independently validate its exact timeout event. If accurate, that failure leaves full paired TitleConfig behavior, clean shutdown, and restart persistence untested; it does not invalidate the separate run-003 entry-to-wrapper capture, which deliberately terminates its isolated processes.

The offline attestation retains four inherited `source_identity_mismatches` (three mapper entries and FillPair). They limit source-level provenance of the composed base, but the selected image/IPS hashes and the candidate's 29-byte delta are pinned. Focused tests are recorded as 4 passed in the upstream handoff; they are shallow helper/contract tests and were not rerun in this review. No whole-game, service-effect, wrapper-return, caller-continuation, clean-shutdown, or H2-completion claim follows from this capture.

## Bounded next action

Keep the candidate experimental. Before using the result to support promotion, have the integrator correct the breakpoint-clear serialization and emit the captured 44 runtime bytes (or their hash plus a retained byte artifact) in a fresh task output with every imported helper pinned. If that evidence is not required for the current bounded decision, preserve this report as partial runtime support and leave H2 open.
