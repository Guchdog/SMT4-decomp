# H2 pinned Azahar diagnostic feasibility

## Recommendation

**GO, with a larger bounded scope, for a separate private implementation worker, subject to review before runtime use.** A network listener is unnecessary. The pinned Qt frontend already provides CLI movie record/play. The in-process observation point is viable, but the CLI does not expose single-step mode: the private Qt emulation thread needs an opt-in stepping path to reach the hook at each guest instruction. This changes the earlier route audit's statement that no movie path had been found; that statement described repository tooling and missed Azahar's built-in feature.

The movie path substantially reduces input work, but it proves only repeatable HID state delivery. It does not establish how SMT4 turns those states into the logical queries or touch-manager results used by H2. H2 remains open until a matched original/patched capture and caller-specific evidence are reviewed.

## Pinned source findings

All source references below are pinned to Azahar commit [`219d743a1e698101fe1ab8bef43e6563126c3c27`](https://github.com/azahar-emu/azahar/tree/219d743a1e698101fe1ab8bef43e6563126c3c27), identified in local launch records as Azahar 2126.2 / `HEAD-219d743`.

### Movie replay covers pad and touch at the HID producer

The Qt argument parser accepts `--movie-record <path>` (`-r`) and `--movie-play <path>` (`-p`), setting the corresponding start-on-load flags at the verified source lines 2768–2795 in [`src/citra_qt/citra_qt.cpp`](https://github.com/azahar-emu/azahar/blob/219d743a1e698101fe1ab8bef43e6563126c3c27/src/citra_qt/citra_qt.cpp#L2768-L2795). The same executable and existing staged `azahar.exe` CLI workflow can therefore record a human-operated input trace once and replay the same trace for the staged original and patched images. No added UI or host keyboard/mouse automation is needed for replay.

[`src/core/movie.cpp`](https://github.com/azahar-emu/azahar/blob/219d743a1e698101fe1ab8bef43e6563126c3c27/src/core/movie.cpp#L27-L117) defines the CTM records: `PadAndCircle` includes digital button bits and circle-pad X/Y; `Touch` includes X/Y and valid. Its playback handlers restore those values, and `HandlePadAndCircleStatus` / `HandleTouchStatus` route the records through the same wrappers used by HID ([play handlers and wrappers](https://github.com/azahar-emu/azahar/blob/219d743a1e698101fe1ab8bef43e6563126c3c27/src/core/movie.cpp#L218-L260), [wrappers](https://github.com/azahar-emu/azahar/blob/219d743a1e698101fe1ab8bef43e6563126c3c27/src/core/movie.cpp#L625-L642)). [`src/core/hle/service/hid/hid.cpp`](https://github.com/azahar-emu/azahar/blob/219d743a1e698101fe1ab8bef43e6563126c3c27/src/core/hle/service/hid/hid.cpp#L187-L221) invokes pad playback as part of `UpdatePadCallback`; the touch handler is called at [the touch shared-memory publication site](https://github.com/azahar-emu/azahar/blob/219d743a1e698101fe1ab8bef43e6563126c3c27/src/core/hle/service/hid/hid.cpp#L253-L269). Thus movie playback restores both controller button/circle-pad state and touch coordinates/validity at the emulator's HID producer boundary.

**Scope caveat:** this is not proof that touch is equivalent to the title's logical control queries, nor that a particular physical button maps to an H2 query ID. The local [H2 input seam contract](h2-input-seam-contract.md) leaves those producers and mappings partly unresolved. Movie playback makes the input *trace* reproducible; the runtime capture must still show how the title consumes it. Playback records a stream of HID update records, so the same pinned build, title, initial profile state, and movie start point are required for comparable sequencing.

**Title/revision gate caveat:** CTM stores `program_id` and source revision in its header ([header](https://github.com/azahar-emu/azahar/blob/219d743a1e698101fe1ab8bef43e6563126c3c27/src/core/movie.cpp#L103-L117)). `ValidateHeader` warns on source revision mismatch but does not reject it; `StartPlayback` accepts every non-invalid header and copies its program ID into movie state, without comparing it with the loaded application's ID ([validation and playback](https://github.com/azahar-emu/azahar/blob/219d743a1e698101fe1ab8bef43e6563126c3c27/src/core/movie.cpp#L425-L438), [start playback](https://github.com/azahar-emu/azahar/blob/219d743a1e698101fe1ab8bef43e6563126c3c27/src/core/movie.cpp#L481-L505)). A driver must check the CTM title ID and revision against the run manifest before both launches, and reject a mismatch itself. The original and patched staged images should be verified as the same title/build context. Do not rely on Azahar to enforce this gate.

### Exact in-process observation boundary

The source-level observation hook can sit in [`Core::System::RunLoop`](https://github.com/azahar-emu/azahar/blob/219d743a1e698101fe1ab8bef43e6563126c3c27/src/core/core.cpp#L284-L295), immediately before `ExecuteCore(*cpu_core, thread, tight_loop)`. That code runs on the emulation thread. `RunLoop(false)` dispatches one CPU instruction and `ARM_Interface` exposes `GetPC()` ([RunLoop contract and public `SingleStep`](https://github.com/azahar-emu/azahar/blob/219d743a1e698101fe1ab8bef43e6563126c3c27/src/core/core.h#L110-L143), [`SingleStep` implementation](https://github.com/azahar-emu/azahar/blob/219d743a1e698101fe1ab8bef43e6563126c3c27/src/core/core.cpp#L338-L340), [CPU dispatch](https://github.com/azahar-emu/azahar/blob/219d743a1e698101fe1ab8bef43e6563126c3c27/src/core/core.cpp#L88-L104), [CPU PC API](https://github.com/azahar-emu/azahar/blob/219d743a1e698101fe1ab8bef43e6563126c3c27/src/core/arm/arm_interface.h#L86-L102)). At a matching H2 guest PC, copy guest state before executing that instruction.

**There is no CLI route to that mode in the pinned frontend.** `EmuThread::run` normally calls `system.RunLoop()` with its default `tight_loop=true`; its existing `exec_step` debugger branch calls `system.SingleStep()` only while paused ([`src/citra_qt/bootmanager.cpp`](https://github.com/azahar-emu/azahar/blob/219d743a1e698101fe1ab8bef43e6563126c3c27/src/citra_qt/bootmanager.cpp#L94-L129)). `System::SingleStep()` is a public core API that calls `RunLoop(false)`, but no supported movie or CLI option selects it. Therefore an observer CLI flag must be passed through the Qt frontend into the `EmuThread` execution policy, making the normal loop call `SingleStep()` repeatedly while capture is enabled; the per-instruction hook then checks PC and snapshots on the same thread. This does not require a network interface or a second scheduler, but it is a source change in both frontend option plumbing and the emulation-thread loop, not just a `RunLoop` hook.

At that boundary, use `Core::System::Memory()` with `MemorySystem::ReadBlock(const Kernel::Process&, VAddr, ...)` to copy the desired guest bytes. The API explicitly reads from the supplied process's **guest virtual address space**; this is a `VAddr` interpreted using that process's mapping, not a host pointer ([`src/core/memory.h`](https://github.com/azahar-emu/azahar/blob/219d743a1e698101fe1ab8bef43e6563126c3c27/src/core/memory.h#L494-L528); `System::Memory()` accessor: [`src/core/core.h`](https://github.com/azahar-emu/azahar/blob/219d743a1e698101fe1ab8bef43e6563126c3c27/src/core/core.h#L268-L276)). Capture the current guest thread's owning process explicitly and pass that process to `ReadBlock`; do not use the convenience overload whose target depends on whichever process is current. Tag each record with process/title identity, guest PC, tick/frame counter if available, event index, and snapshot address/length. Keep reads small and bounded to the documented config/work/input fields.

**Thread-safety and accuracy limits:** do not read CPU registers, guest pointers, or memory from a GUI/CLI/worker thread while the core is running. `RunLoop` single-step plus `GetPC` and `ReadBlock` in the same emulation-thread turn gives a coherent CPU-before-instruction observation point and prevents concurrent guest CPU execution during the copy. The API docs do not promise a global lock against every non-CPU subsystem; keep this to small ordinary guest-RAM ranges, not mapped device registers or rasterizer-owned buffers. Dynarmic advertises `HasSingleInstructionBreakAccuracy() == false` for watchpoints ([`arm_dynarmic.h`](https://github.com/azahar-emu/azahar/blob/219d743a1e698101fe1ab8bef43e6563126c3c27/src/core/arm/dynarmic/arm_dynarmic.h#L47-L56)); do not build the observer around memory watchpoints. Its GDB software-breakpoint path patches guest instruction bytes and clears instruction caches ([`gdbstub.cpp`](https://github.com/azahar-emu/azahar/blob/219d743a1e698101fe1ab8bef43e6563126c3c27/src/core/gdbstub/gdbstub.cpp#L1573-L1604)), so it is not the desired read-only, no-listener path.

## Minimal no-network design

1. Leave Azahar's GDB and RPC servers disabled. Add a private, opt-in CLI flag such as `--h2-snapshot <jsonl>` to the pinned Qt frontend. Pass a bounded observer configuration into `Core::System` and the Qt `EmuThread`; only enable it for the expected title ID and an explicit output path inside the diagnostic run directory.
2. While capture is enabled, have the Qt emulation thread repeatedly use the existing `System::SingleStep()` API instead of its normal batched `RunLoop()` call. At the `RunLoop` dispatch point, check a fixed allowlist of H2 callback PCs before each instruction. At a hit, use `ARM_Interface::GetPC()` and process-scoped `MemorySystem::ReadBlock` to emit a JSONL record containing PC, run/title/movie identity, sequence number, and approved guest snapshots. Keep the observer read-only; do not expose guest writes, sockets, RPC, arbitrary memory ranges, or user-selectable breakpoints.
3. Use built-in `--movie-record` once for a controlled, user-operated H2 trace, then use `--movie-play <same CTM>` on both staged runs. Verify the CTM program ID, source revision, title/image hash and patched/original image identity in a driver manifest before either playback. Use separate existing isolated profile trees and pristine matching seeds; do not point these launches at the installed profile.
4. Verify the movie produces the expected H2 event sequence and callback hits in both runs; include no-op, cancel, confirm, re-entry and restart cases as appropriate. Compare recorded config/work/cursor snapshots and the existing visible runtime observations. Include negative control (wrong title/movie rejected before launch), output-path containment, no-network/disabled-server log checks, observer-disabled behavior, and exact original-versus-patched image hashes. Then request independent review before using the diagnostic build for H2 evidence.

This design needs no listener, firewall exception, RSP connection, RPC server, or remote reader. It does require a private Azahar source build and the normal user-authorized runtime comparison; this audit did not make either.

## Effort and handoff decision

| Work | Estimate | Notes |
| --- | ---: | --- |
| Input trace recording/replay | 0.25–0.5 day | No new emulator code. Record a representative H2 trace using existing `--movie-record`; validate the movie's title/revision and use existing `--movie-play` for original/patched launches. Includes initial manual trace capture and repeatability checks. Logical-input/touch interpretation remains an H2 evidence task. |
| Read-only observer implementation | 2–4 engineering days | Add bounded CLI plumbing, `EmuThread` stepping policy, title/path gating, per-instruction PC allowlist, scoped process `ReadBlock` snapshots, and JSONL output. The existing normal run loop batches instructions; capture mode has to pay the full single-step dispatch overhead. Keep no-network and read-only invariants explicit. |
| Build, focused validation and independent review | 1–2 days | Compile the private pinned source; verify no observer writes/network, title mismatch rejection, loop responsiveness/performance, deterministic movie replay and matched captures, then review source diff and evidence. This audit ran none of these checks. |

**Separate worker scope:** implement the private observer only, reuse built-in movie CLI behavior, and return source diff plus a structured report. No game-code edits, canonical game build, network listener, firewall/profile changes, or H2 acceptance claim. This remains a bounded and feasible task; estimated total is 3.25–6.5 engineering days including validation/review, with movie replay likely the small part. The worker should stop if the exact staged Azahar revision differs, if the observer would require GDB/RPC, or if a safe process/PC boundary cannot be preserved. No pinned Azahar source checkout was available. A read-only host check found Git but no `cmake`, `ninja`, Qt/qmake or vcpkg commands, and no `C:\Qt`, `C:\Program Files\CMake` or `C:\vcpkg` directories. The estimate assumes a worker gets the pinned source and build prerequisites provisioned; none were installed or built during this audit.

## Evidence and limitations

This report is read-only source/docs research against pinned primary source and saved local H2 reports. No Azahar source was checked out or changed; no build, emulator launch, listener connection, firewall action or profile access occurred. No movie was recorded or replayed. No guest state was captured. Existing user-reported manual H2 behavior remains partial evidence only, as recorded in [the final image runtime report](h2-manual-final-image-runtime.md). H2 remains open.

Prior local reports [H2 route audit](h2-safe-guest-state-capture-route.md) and [runtime CLI contract](h2-runtime-cli-contract.md) should be updated in later integration work to reflect the newly found native movie path and the source-level observer design above.
