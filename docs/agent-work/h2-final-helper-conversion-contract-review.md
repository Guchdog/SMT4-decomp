**Callee inventory correction:** contract's table correctly identifies 0x28DF54 on state 5, but its later consolidated callee list omits it. Do not treat that list as complete. Its description of prior runtime callback observation cannot be independently corroborated from the packet's older callback audit, which explicitly says run-017 did not resolve the indirect target; the current contract may refer to a later trace not pinned here. Therefore retain the static caller fact and do not elevate any particular runtime branch or binding without separately pinned evidence.

**Candidate counterexample requiring tests:** in source after the 0x28DF98 branch, candidate loads P+4 unconditionally, even for arg5=0. Original executes its first P+4 read only when arg5 is nonzero (0x286AF0–0x286AFC). More consequentially, original reloads P+4 at 0x286B04 *after* 0x2C4BF0, while candidate caches one volatile load and passes it to both 0x2C4BF0 and 0x2B90F0. If a valid 0x2C4BF0 implementation or controlled stub changes P+4, the latter receives different arguments; whether that behavior is reachable in a real lifecycle is unresolved. Read traces also distinguish arg5=0 even if final normal-RAM behavior does not. This is a pending source-level counterexample, not a compiled differential result; it blocks accepting equivalence for the q=0 route until the behavior is resolved. Do not silently assume callee immutability. Correct the candidate with conditional P+4 load and reload after 0x2C4BF0, then test a fixture that mutates P+4 in that callee and records the second call argument.
