# Independent review: H2 initializer contract

Outcome: **ready for review as bounded instruction-level research**. The address, immediate call sequence, field destinations and State 9/10 caller are materially sound against the pinned US v0.1.0 image (`code.bin` SHA-256 `1f98884fe997af22e032a14c51a46c872b05b0e079a0f29e307b0e059cfaa558`). This review does not approve an editable reconstruction, differential result, full caller equivalence, or runtime behavior.

## Checks against original and checked-in source

`python tools/split_asm.py --addr 0x002f4ca0` reproduces `[0x002F4CA0,0x002F4EDC)`. The initializer notes correctly read the allocator setup (`r0/r1=0x100, r2=0, r3=0x158, [sp]=1`, BL `0x002C4B84` at `0x002F4CCC`), global publication at `0x002F4CE0`, calc and draw callback literals/stack tuples (`0x002F4CD4..0x002F4D30`), object offsets and setup arguments, config reads at `0x002F4E04/10/1C`, and tail branch to `0x002ADB40` at `0x002F4E3C`. The State 9 call then State 10 readiness/reset sequence in `src/ui/ui_runtime2.cpp` matches the caller description. The declared `TitleConfigWork` size/offset asserts match the observed allocations/accesses.

The report appropriately limits itself: no null-check or global reuse branch is present in the initializer; the result of its tail-call is inherited from the helper while the title caller ignores it; H0/H1 traversal is not per-initializer differential evidence; and no settings-edit or persistence claim follows from the no-edit cancel run.

## Corrections and refinements before using this as an implementation brief

1. **Pair widths are already settled by the checked-in callees.** `UiConfig_CopyPair` (`0x002ADB40`, `src/engine/leaf_matching.cpp` near its `DECOMP_FUNC`) performs exactly two word loads at `src+0/+4` and stores them at `dst+0/+4`, then returns. Thus the initializer copies exactly eight bytes to `work+0x34/+0x38`; no helper speculation is needed for the width. `UiConfig_FillPair` (`0x0027EDF8`, same file) replicates the low input byte across one word and writes two words. For the initializer’s `-1` argument, `work+0x1C` and `+0x20` become `0xFFFFFFFF`. Update the report’s “exact width needs own evidence” and “don't assume its full width/effect” caveats accordingly. The `g_ConfigBytes` object’s total storage extent still depends on its producer/global layout, but this use reads bytes 0..2 and copies bytes 0..7.
2. **Name the `0x0029F10C` call by behavior/address.** `src/camp/title_flow.cpp` declares the legacy alias `Camp_SetFadeColor`, but the H1 contract at `docs/agent-work/h1-title-message-contract.md` directly inspects this target and proves null `r0` selects a color/reset path that writes color and clears message state. It is not merely a color setter. Use e.g. “shared `0x0029F10C` null/reset mode (legacy `Camp_SetFadeColor` alias)” and list its helper effects as dependency behavior; this avoids importing the misleading source alias into the contract.
3. **Record the known secondary callback cleanup path.** `0x002CAEF0` is not wholly unknown in the declared read inputs: the checked-in original in `src/engine/leaf_batch32_c.cpp` begins by resolving `g_TitleConfigWork`, sets `work+4`, drains counters at `+0x1A/+0x24`, releases handles at `+0x154/+0x14C/+0x150`, and continues task/global cleanup. The initializer correctly records that this callback is registered, but the contract should mention this known cleanup role while leaving scheduler timing and full lifecycle/reentry behavior open. In the helper list, treat `0x002CAEF0` as a callback/lifecycle dependency to analyze, not an uninspected address.
4. **Separate initializer orchestration coverage from mapper coverage.** The proposed all-256 byte matrix is good for each mapper candidate, but an initializer candidate which continues to call the original three helpers does not thereby validate candidate mapper semantics. Define the test boundary: either keep mapping helpers as original dependencies and compare the three resulting workspace words as part of initializer orchestration, or run each compiled mapper separately against original ARM over 0..255 with its own table inputs. The literals are distinct (A `0x004077EB`, B `0x004077F6`, C `0x00407801`), so don't conflate their domains.
5. **Include edit-then-cancel in the safe profile cases.** The separate `docs/agent-work/h2-calc-contract.md` reports direct writes from the Calc state-1 path to `g_ConfigBytes+0..+3` before exit and a state-2 write to `+4`. Existing H1 proves only cancel without editing. In an isolated profile, test cancel-with-no-edit, edit-then-cancel, and edit-then-confirm separately; capture live config bytes before exit and after returning to title, then compare profile files/re-entry independently. Don't assume cancellation rolls back in-memory changes or that in-memory changes are durable. The pristine cloned profile/snapshot requirement remains sound.

## Recommendation / limits

Accept the initializer note as a useful research handoff after the width/name/callback refinements. The next implementer still needs an explicit non-leaf differential harness or bounded composition harness that can represent globals, external calls and callback registration; the leaf-only helper runner is outside scope. The current report does not establish allocation failure behavior, task scheduler ABI/lifetime, resource helper effects as a whole, map-table domains/outputs, file persistence, or safe profile availability. Keep `compiled`, ARM differential, caller-candidate, and runtime semantic evidence open until independently produced.

No emulator, build, or test was run for this review.
