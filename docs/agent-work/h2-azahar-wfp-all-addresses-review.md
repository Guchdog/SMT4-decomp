# H2 all-address WFP capture review

## Finding

The capture does not establish confinement of a wildcard Azahar listener on all non-loopback interfaces. The sandbox block's effective filters have a local-user security condition naming a different SID from the current shell user. The staged application's private-profile TCP permit and a custom Radmin permit provide additional reasons not to infer an effective block from the rule's name and address ranges. This corrects the earlier review's unqualified characterization of the saved rule as proving the non-loopback block.

`whoami /user` returned `desktop-rdffji8\altair`, SID `S-1-5-21-1924653288-2963105298-1535699604-1001`. Every one of the 11 sandbox filters in the capture has `ALE_USER_ID` equal to security descriptor `O:LSD:(A;;CC;;;S-1-5-21-1924653288-2963105298-1535699604-1004)`. Its only DACL ACE grants the match access to -1004, not the shell's -1001 user SID. WFP evaluates this descriptor by an access check; a grant means the condition matches, not that traffic is permitted ([Microsoft's WFP user-filter example](https://learn.microsoft.com/en-us/windows/win32/fwp/permitting-and-blocking-applications-and-users)). The SID discrepancy is strong evidence against assuming applicability to a listener launched under this shell. `whoami /user` alone is not a full token access check, and the actual future listener token is not captured; token groups, impersonation or a different launch identity cannot be ruled out solely from this comparison.

## Capture and filters

`wfp-all-addresses-admin.xml` is 708,527 bytes, SHA-256 `8d752b426b38afa810270aa191671e22515aa06790a13a017b015e4485ba20d2`. It begins with a UTF-8 BOM consistent with the XML declaration and parses as XML: 349 filter entries and 16 providers. It has no embedded command, capture time, sublayer definitions/weights, or classification verdict. Its source is the supplied administrator capture; the bytes alone do not establish the precise query arguments or current policy at a later launch.

All 11 named sandbox filters are `FWP_ACTION_BLOCK` in `FWPM_SUBLAYER_MPSSVC_WF` at ALE receive/accept, with the user descriptor above and no app or TCP-port condition. IPv4 profile-ID 1 filters 146391/146392 and profile-ID 2 filters 146387/146388 cover respectively `0.0.0.0–126.255.255.255` and `128.0.0.0–255.255.255.255`, effective weight 11538222520201125376; 146395/146396 have those ranges without profile condition, weight 5773614997166882816. Thus their address conditions exclude 127/8, but all still require the user match. IPv6 profile-ID 1/2 filters 146393/146389 match `::` at weight 11817445559659138560, and 146394/146390 match `::2–ffff:ffff:ffff:ffff:ffff:ffff:ffff:ffff` at 11529215183507426816; 146397 matches `::` without profile condition at 6052838036624900096. The capture contains no profile-unrestricted `::2–ffff:...` sandbox filter; do not infer one from the saved configuration or prove coverage for an unobserved profile. The pinned Azahar implementation was observed using an IPv4 wildcard listener, but no current runtime socket was inspected here.

For the staged app device path ending `run-007-59931\app\azahar.exe`, IPv4 listen filter 146703 permits the app at weight 11529215046068469888. At receive/accept, IPv4 TCP app filter 146704 blocks original profile 1 at 11530060020754423296, 146688 permits original and current profile 2 at 10377138516147576768, and 146708 blocks without profile at 5765452497720180736. The profile-specific sandbox IPv4 blocks have higher weights within that same sublayer than these app filters, but only when every condition, including the user check, matches. Otherwise the private-profile app permit can precede the generic app block. Specific flow profile values are not established here. IPv6 counterparts are 146706, 146690, and 146710.

Radmin custom sublayer `{1b96d0be-ff7e-4dfa-a7ba-3cf6e9e796d1}` includes receive/accept permits 102826 (IPv4) and 102827 (IPv6), conditioned on local-interface LUID 1689399750295552 and carrying `FWPM_FILTER_FLAG_CLEAR_ACTION_RIGHT`. Similar permits exist at packet, transport and listen layers. These are potentially hard permits on that interface, not automatically proof that a particular Azahar flow is permitted. Filter weights compare within a sublayer; sublayer order, action rights, callouts and matching determine the cross-sublayer outcome. The capture lacks sublayer weights and final classification. Microsoft describes hard/soft decisions and callout vetoes in its [arbitration documentation](https://learn.microsoft.com/en-us/windows/win32/fwp/filter-arbitration). No blanket conclusion about Radmin overriding or being overridden is supported.

## Next action

Keep the wildcard-listener runtime gate closed until an independently verified, current boundary applies to the actual launch token and all relevant non-loopback interfaces throughout the listener lifetime, accounting for Radmin arbitration; alternatively use a verified loopback-bound build. A separately authorized local connection can test availability once that safety boundary is established; its success would not prove non-loopback isolation. This review performed no emulator launch, socket probe, firewall modification or keyboard/mouse action.
