# H2 manual comparison package independent review

## Finding

The staged standalone IPS independently replays from the pinned original to the reviewed final image; the two staged application packages and pristine user profiles match apart from the intended patch. The package is suitable for a user-controlled manual comparison subject to verifying the selected portable profile and patch load in the emulator. No emulator was launched and no runtime equivalence is established.

A separately written in-memory IPS reader checked the header, record bounds, EOF and full output, rather than calling the package's `apply_ips`. The pinned 3,633,152-byte original has SHA-256 `1f98884fe997af22e032a14c51a46c872b05b0e079a0f29e307b0e059cfaa558`. The three chain patch hashes and successive output hashes match the manifest; final output `5e9aa08b449985f012e24400c45b4b037e4a0d5d069723b6cfa7ccf83300d8fa` is byte-identical to the reviewed final file. The staged standalone IPS SHA-256 `447074920cee05ab5d8a684b1a8e3142e7f097fa0c021eef1e0ba4b082533788` contains 533 records and independently produces the same final bytes, with 4,218 original-to-final changed bytes. I inspected the composer and existing tests; its equal-length, bounded record generation, EOF-offset workaround, and roundtrip are appropriate for this actual image. This does not establish correctness of the reconstructed behavior itself.

Both staged applications have 60 identical non-user files by relative path and hash; both executables have SHA-256 `c248414eb5328cb8bb720775ace6959898e2f50a0a10221c3a1e7a14190183eb`. The only CCI in the stage hashes to `9cc760c2f37da9a4a3657e918e0eaebb3e8e80a91047e5c18f95aedf0242b4c2`, matching the pinned input identity. Each initial user has identical config, NAND config and MAC files, with no save; only the patched user has the single `load/mods/00040000000E5C00/exefs/code.ips`. The title ID agrees with `config/game_info.json`. Pinned Azahar [loader source](https://github.com/azahar-emu/azahar/blob/219d743a1e698101fe1ab8bef43e6563126c3c27/src/core/file_sys/ncch_container.cpp#L465) checks that ExeFS IPS path first under the selected user load directory. Pinned [Windows user-directory code](https://github.com/azahar-emu/azahar/blob/219d743a1e698101fe1ab8bef43e6563126c3c27/src/common/file_util.cpp#L863) selects an existing executable-local `user` directory absent an explicit path override. This is source-level evidence, not a runtime observation.

Both config files explicitly contain `[Debugging]` values `use_gdbstub=false` and `enable_rpc_server=false` with corresponding default flags false; the pinned [configuration reader](https://github.com/azahar-emu/azahar/blob/219d743a1e698101fe1ab8bef43e6563126c3c27/src/citra_qt/configuration/config.cpp#L480) reads both settings. Both documented PowerShell commands name the correct stage executable and shared CCI and contain no GDB option. Actual settings and profile selection have not been observed in a running process. The commands should be run separately; confirm UI/log profile and IPS application, use equivalent game state and actions, and record results. Neither a staged patch nor an initial file match proves the intended scenario, and profiles change once used. Recheck files if the stage changes before use.
