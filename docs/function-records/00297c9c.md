# Function Record: script_vm_func_00297c9c (0x00297C9C)

## Summary

- **Address:** `0x00297C9C`
- **Size:** 404 bytes (92 ARM instructions plus a 36-byte constant pool)
- **Source:** `src/engine/leaf_batch41_c.cpp`
- **Role:** Presets the map-interface record block owned by the object published
  through `0x00447A78` (`g_MapIfWork`, `include/engine/map_runtime.h`).
- **Status:** Typed C++ (`non_matching`, 400/404 bytes, no relocations). Verified
  by a Unicorn ARM differential test with 17 fixtures, a null-global boundary
  case and six negative controls.

## Contract

- **Signature:** `extern "C" u32 script_vm_func_00297c9c()`
- **Arguments:** none are read. The routine never touches the incoming `r0`;
  the mapIf tail call at `0x0018ADD4` passes `tables + 0xC80` and that value is
  dead. `r1`/`r2`/`r3` are unused as well.
- **Global:** `0x00447A78` holds a pointer to the host object. The single
  `ldr r2, [r0]` at `0x00297CAC` dereferences it once; the address stays in
  `r2` for the whole routine.
- **Record layout:** each record is `0x194` (404) bytes, proven by
  `mov r4, #0x65` / `mul r0, r0, r4` / `add r0, r2, r0, lsl #2`.
  - The sweep stores at `base + i*0x194 + 0x1D0` (`strb r1, [r0, #0x1d0]!`) for
    `i = 0..0x7F` (128 records, `+0x1D0..+0xCBD0`).
  - The element at `+0x03C` is a single record of the same size
    (`0x03C + 0x194 = 0x1D0`); the region is therefore 129 contiguous records
    whose first element receives a different, partial preset. `+0xCBD0` is the
    `field_cbd0` marker in `include/engine/map_runtime.h`.

### Control flow and ABI

- No calls, no indirect branches, no loop other than the 128-record sweep
  (`cmp r3, #0x80` / `blt`, signed but the counter is `0..128`).
- Only `r4` is callee-saved (`str r4, [sp, #-4]!` / `pop {r4}`); the C++
  candidate additionally uses the caller-saved `ip`/`lr`-class registers and
  restores all of `r4-r11`, which the differential test confirms.
- No read of pre-existing record state: every value written is a literal or a
  field the routine itself just wrote. The `stm r2, {r0, r3, r4}` at
  `0x00297E00` copies the zero bits of `+0x05C`/`+0x060` (loaded back after the
  stores) plus a VFP zero into `+0x068/+0x06C/+0x070`; they are all zero.
- Return: the last `ldm r0, {r0, r3}` reloads the zeroed `+0x05C` word, so the
  register image returns `r0 = 0`. No reconstructed caller consumes it, so the
  C++ returns `0` to keep the register image.

## Verification

- `python tools/test_leaf_00297c9c.py`
- Compiles `src/engine/leaf_batch41_c.cpp` with the pinned ARMv6K pipeline and
  runs the original image (`extracted/exefs/code.bin`) against the candidate in
  separate Unicorn ARM machines.
- **17/17 differential fixtures passed.** Each compares return `r0`,
  continuation PC, final SP, callee-saved `r4-r11`, the whole 128 KiB fixture
  page, a second 128 KiB argument page (must stay untouched) and the whole data
  page holding the `0x00447A78` pointer word, plus any write outside those
  regions.
- Fixture fills: zero, `0xFF`, `0x55`, `0xAA`, `0x7F`, `0x80`, `0xF0`, a
  deterministic xorshift byte stream and a distinct word pattern, so both
  written and preserved bytes are exercised and store widths are checked.
  Bases at page offsets 0, 4, 0x100, 0x1000, 0x8000 and 0x10000 cover the
  128-record bound and the `+0xCBD0` end of the block.
- A junk `r0`/`r1`/`r2`/`r3` case proves the incoming argument is ignored.
- Null-global boundary: with `0x00447A78 = 0` both bodies fault with
  `UC_ERR_WRITE_UNMAPPED`. The faulting PC differs (original `0x00297CE8` =
  `strb [r0,#0x1d0]!`, candidate `0x00297CF4` = `strh [ip,#0x1f8]`) because the
  two bodies order their first stores differently, so only the fault outcome is
  compared; a valid non-null pointer is required.
- Negative controls (each mutant is detected): changed sweep constant
  (1150 → 1152), shortened sweep (last record unwritten), over-long sweep
  (129th record at `+0xCBD0`), changed single-preset value (50 → 25), changed
  sweep word (`+0x190`), and a widened byte store (`+0x04C` u8 → u32, which
  clobbers the preserved `+0x04D..+0x04F` padding).

## Unresolved / limits

- No semantic names for the record fields: the ARM evidence only proves offsets
  and widths, so they stay `field_XXX`.
- The producer of the `0x00447A78` pointer (the `MapIfWork` allocation in
  `mapIf_func_0018aba8`) and the consumers of the preset values are outside
  this function; the block is exercised on synthetic RAM only.
- The `+0x03C` element is modelled as a separate `preset` member followed by
  `records[0x80]`; it is observationally identical to a 129-element array whose
  element 0 gets the partial preset, but no listing proves which spelling the
  original source used.
- Runtime/integration and whole-game equivalence were not tested here; no
  emulator run was performed.
