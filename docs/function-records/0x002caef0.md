## Evidence

The run-001 harness compiled the candidate for ARMv6K with no unresolved relocations and compared it against pinned US v0.1.0 code image SHA-256 `1f98884fe997af22e032a14c51a46c872b05b0e079a0f29e307b0e059cfaa558` under identical helper-entry models. Seed `20261025` covered 17 directed cases: positive/negative/zero counter values for each loop independently, independent distinct loop counts, nullable each cleanup slot, active-task false/true, and manager halfword values 9/10/11/12. All cases returned to the sentinel and agreed on full 0x158-byte work memory, global pointer, manager field, normalized helper sequence/arguments, writes, stack at/above entry SP, and preserved `r4-r11`, SP, and `d8-d15`.

Two controls were detected: omitting the last first-loop call and reversing the `+0x14C/+0x150` release order. The callback is `void`; final `r0` is incidental and recorded but not compared. Initial harness iteration caught an overly broad comparator that treated callee-owned stack below entry SP and caller-saved helper scratch as observable; comparator was narrowed to AAPCS caller-owned stack and declared helper arguments, then the same matrix passed.
