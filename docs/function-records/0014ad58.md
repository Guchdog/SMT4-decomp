# Function Record: func_0014ad58 (0x0014AD58)

## Summary
- **Address:** `0x0014AD58`
- **Size:** 624 bytes (original span `[0x0014AD58, 0x0014AFC8)`; 155 ARM
  instructions through `bx lr` at `0x0014AFC0`, followed by the literal word
  `0x004221F8` at `0x0014AFC4`)
- **File:** `src/engine/leaf_batch34_c.cpp`
- **Role:** Consistency pass over a node's optional child-object graph. The node
  at `r0` points (through its first word) at an object that carries a
  request/state word, a byte kind, a presence word and a self-relative offset to
  a six-slot container. The routine verifies that every requested child resolves
  through two self-relative hops, clears the request that failed, and reports
  `1` (all requested children present) or `0` (at least one failed). When the
  request word changed it is written back and the caller's `+0x2BC` word is
  zeroed.
- **Status:** Semantically equivalent C++ (`non_matching`). The compiled body is
  592 bytes versus the 624-byte original: the candidate keeps the six slot
  offsets as a struct, folds the duplicated offset reloads into one expression
  per hop, and emits `ldrb` for the `+0x18` low-byte test where the original
  loads a word. The table literal is still a plain `0x004221F8` word and the
  object produces no relocations. The ledger row is classified `non_matching`
  with this semantic record.

## Contract and Behavior

### Signature and ABI
```c
extern "C" int func_0014ad58(u32 node,   // r0: node whose [0] is the base object
                             u32 context); // r1: caller context, only +0x2BC used
```
- Leaf body: no `bl`/`blx`, no indirect branches, no stack arguments, no `LR`
  save (the original only pushes `{r4-r8, sb, sl}` = 28 bytes and returns with
  `bx lr`). The candidate's prologue also pushes `fp`/`lr` and restores them, so
  `sp` and `r4-r11` are identical after return.
- `r0` is the sole result register: `1` when every requested child is present,
  `0` when any request failed. No other register is a documented result.
- `r2`, `r3`, `ip`, `lr` are scratch and not preserved.

Each slot word is a **self-relative** offset added to its own address
(`container + slot_offset + value`, all 32-bit wrapping). The container itself
is resolved with `base + 0x28 + container_28`; the original has no separate
wrapped-zero test after that addition (`0x0014AD78..0x0014AD88`), unlike the
slot resolver.

### Child presence test
For a slot at `offset`, the original requires all of:
```text
rel   = *(u32*)(container + offset)
child = rel != 0 ? container + offset + rel : 0
child != 0                                     // tested before the next load
next  = *(u32*)(child + 0x08)                  // only loaded when child != 0
next != 0
child + 0x08 + next != 0                       // 32-bit wrapping arithmetic
```
`0x0014AD94..0x0014ADD4`, `0x0014ADEC..0x0014AE2C` and
`0x0014AE44..0x0014AE84` are three copies of this pattern; the first-hop
wrapped-zero case is exactly `0x0014ADAC` / `0x0014AE04` / `0x0014AE5C`, and the
second-hop wrapped-zero case is folded into the final `cmp r4,#0`.

### Request bits and outcomes
| Gate | Requested slot | Failure effect |
|---|---|---|
| `flags_10 & 0x02` | `container + 0x0C` | `flags_10 &= ~0x02`; result 0 |
| `flags_10 & 0x04` | `container + 0x10` | `flags_10 &= ~0x04`; result 0 |
| `present_18 & 0xFF != 0` | `container + 0x14` | `present_18 = 0` (whole word); result 0; **flags untouched** |
| `flags_10 & 0x20` | `container + 0x00/0x04/0x08` | `flags_10 &= ~0x20`; result 0 |

The kind mask is the byte at `0x004221F8 + (kind_14 & 0xFF)`; only bits 0, 1
and 2 are consumed and each selects the matching container slot. All three
selected checks are evaluated (the original keeps a sticky failure in `r8`);
any failure clears bit `0x20`. The first twelve bytes of the addressed table
region are `c9 e1 99 d8 df ef f9 ff d1 d8 87 ff`, but the index is masked to
8 bits and the surrounding bytes at `0x00422200` onward are other `.rodata`, so
only the low three bits of the addressed byte are modelled.

Bits `0x02`, `0x04` and `0x20` are tested in that order with the original's
`bics` form, so each block runs only while its bit is still set. A failure in
`0x02` or `0x04` cannot affect the `0x20` gate (different bits).

### Write-back
`0x0014AFAC..0x0014AFB8` reloads `flags_10` and compares it with the surviving
value. Only when they differ:
```text
flags_10            = surviving value
*(u32*)(context+0x2BC) = 0
```
The `+0x2BC` store therefore happens exactly when a flag bit was cleared, not
when only `present_18` failed. High flag bits are preserved verbatim.

## Limits
- Fixtures are synthetic: the node, object, container, children and caller
  context are pattern-filled pages, not captured game memory.
- A request bit that needs the container while `container_28` is zero, or a
  child address that is unmapped, faults in the original; the harness excludes
  those faulting configurations. This is a precondition (set request bits imply
  a valid container), not modelled recovery behavior.
- The candidate emits `ldrb` for the `+0x18` low-byte test; the original loads
  the whole word first. This differs only when the byte sits at the very end of
  a mapped page, which the fixtures do not exercise.
- The kind table's meaning beyond bits 0..2 is not recovered, nor are the
  higher-level names of the object/container fields or the consumer of
  `context+0x2BC`. Names in the candidate are descriptive.
- The original's exact instruction stream is not reproduced (592 B candidate
  vs 624 B original); the ledger row is truthfully `non_matching` with this
  semantic record.
