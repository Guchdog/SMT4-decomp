# Function Record: engine_func_0038f950 (0x0038f950)

## Summary
- **Address:** `0x0038f950`
- **Size:** 408 bytes (original span `[0x0038f950, 0x0038fae8)`): 94 ARM
  instructions through the unconditional `pop` at `0x0038fac4`, plus the
  eight-word literal pool at `0x0038fac8`.
- **File:** `src/engine/leaf_batch36_b.cpp`
- **Classification:** `non_matching` with semantic evidence. The compiled body
  is 420 bytes versus the 408-byte original: it saves three extra callee-saved
  registers (`r9-r11`), uses a 0x68-byte frame instead of 0x60, folds the shared
  constant pointer into `0x003FF12C + 0x30`, shrinks the literal pool from eight
  words to six, and converts the final `bl 0x00233600` plus epilogue into a
  sibling tail call. Return register, continuation PC, SP, callee-saved
  registers, ordered call arguments and full observable memory are identical in
  the differential suite.
- **Role:** Builds one UI work block. It initialises a 0x20-byte shared sprite
  descriptor at `ctx + 0x35C`, creates one leading animated sprite, 24 more
  sprites in a `0x8C`-stride array at `ctx + 0x37C` whose labels come from a
  24-byte constant table, resets two trailing sub-objects, clears two state
  bytes, allocates a text object and stores it at `ctx + 0x1C30`, then resets
  the object at `ctx + 0x17B0`.

## Contract and Behavior

### Signature and ABI
```c
void engine_func_0038f950(u8* ctx);
```

- `r0 = ctx`, the caller-owned work block. There are no stack arguments and no
  VFP arguments. `d8` is saved only because `s16` holds the `1.0f` constant

- **Returns:** nothing is computed explicitly. The epilogue is
  `pop {r4,r5,r6,r7,r8,sb,pc}`, so the observable `r0` is whatever the final
  `unite_func_00233600` call left there. The only static caller ignores it.

  is the same helper return; only the incoming `lr` of that helper differs

### Sprite descriptor and array
`camp_func_002c3344` zeroes 0x20 bytes and `camp_func_002c32f8` fills the same
0x20 bytes, so `ctx + 0x35C` is a 0x20-byte descriptor. With the arguments
above the descriptor receives visibly:
- `u16` fields at `+0x00, +0x02, +0x04, +0x06, +0x08` =
  `0, 0x0C, 0, 0, 0` (`count`, then stack words 0, 2, 4, 6);
- `u32` fields at `+0x0C, +0x10, +0x14, +0x18, +0x1C` =
  `0, 0x003FF12C, 0, 0, 0` (`table`, `reg_word`, then stack words 1, 3, 5).

`0x003FF12C` is a pointer to a shared constants block (first words:
`1.0f, 1.0f, 1, 0x6E`). The descriptor is passed straight to every
`camp_func_002bdb2c` call, whose real body copies descriptor words 3..7 into
the sprite at offsets `+0x4C, +0x58, +0x64, +0x70, +0x78`.

The sprite array starts at `ctx + 0x37C` with stride `0x8C`:
`ctx + 0x37C + i * 0x8C`, `i = 0..23`. The leading sprite is at
`ctx + 0x109C`, which is exactly one stride after the array end
(`0x37C + 24 * 0x8C = 0x109C`). This function never touches the leading
sprite's `+0x18/+0x1A` position fields, whereas every loop sprite gets them
from `script_vm_func_00296154`.

`ctx + 0x15C5` is `ctx + 0x11B0 + 0x415`, the byte that
`engine_func_002baacc` sets to 1 together with `+0x414`; this function clears
`+0x415` immediately afterwards.

### Label table and loop
The 24 bytes at `0x003FF15C` in the pinned image are
`00 01 01 00 00 00 01 01 01 01 00 00 00 00 01 01 01 01 00 00 00 01 01 00`,
i.e. only 0 and 1. The original copies them to its stack before the loop
(`ldm` of five words plus one `ldr`/`str`) and then loads each entry with
`ldrsb`; a mid-loop change of the source table therefore does not reach the
labels. The copy is preserved in the reconstruction and covered by a
dedicated case and negative control.

irrelevant because `i` is non-negative and the bound is 24):

### Code-generation note
- The candidate's final `unite_func_00233600` call is compiled as a sibling
  call: it restores the full frame (`add sp; vpop {d8}; add sp; pop
  {r4-r8,sb,sl,fp,lr}`) and then branches to the helper, whose `bx lr` returns
  straight to the original caller. `r0`, `pc`, `sp` and all callee-saved
  registers match; only the helper's incoming `lr` differs, which is not part
  of the calling convention.
- Clang uses `r9-r11` (`sb/sl/fp`) and therefore saves three registers the
  original did not, growing the frame from 0x60 to 0x68 bytes.
- The candidate folds `0x003FF15C` as `0x003FF12C + 0x30` and the
  `ctx + 0x15C5` address as `ctx + 0xC5 + 0x1500`, and spills the latter to the
  stack before the loop. These are same-value address computations with no
  observable difference.
- The candidate's literal pool holds six words (shared table pointer, `1.0f`,
  global slot, text flags, text colour, `0.0f`); the original also stores
  `0x003FF15C`, `0x15C5` and the original word order.
