# Function Record: engine_func_0015e600 (0x0015E600)

## Summary
- **Address:** `0x0015E600`
- **Size:** 448 bytes (span `[0x0015E600, 0x0015E7C0)`). The last two words
  (`0x0015E7B8 = 0x00000E5C`, `0x0015E7BC = 0x00432FC8`) are the literal pool;
  the last instruction is the `pop` at `0x0015E7B0`.
- **File:** `src/engine/leaf_batch34_c.cpp`
- **Role:** Mounts one add-on-content entry: compares the requested mount name
  with the one remembered in the path-root object, releases the previous mount
  when it changes, records the new name, issues the content-size request through
  `0x0015E7D0`, and fills the caller's 20-byte status/result object (the same
  object shape as `AocFileContentState` in `include/engine/aoc.h`).
- **Status:** Reconstructed as readable C++ and **differentially verified**
  against the pinned original. The candidate body is 548 bytes and is not
  byte-identical, so the ledger row is `non_matching` and this record carries
  the semantic evidence.

- `r0 = out`: 20-byte status/result object. It is an **explicit first
  parameter**, not an AAPCS structure-return pointer: the only caller

  from that buffer (`ldm r5,{r0,r1,r2,r3,ip}` at `0x0015C840`), never from `r0`.

  byte flag) and `+0x331..+0x340` (the 16-byte mount name). The caller
  additionally reads `+0x310` (entry count) and `+0x318` (entry table) before
  the call, but this body does not.
- `r2 = mount_name`: pointer to the record's 16-byte `mount` field. The caller
  passes `record + 0x24`; the string is also the second argument of the name
  comparison and the source of the 16-byte copy.
- `r3 = word20`: opaque word, caller's `record + 0x20` (documented as `buffer`
  in `AocFileContent`). Forwarded unchanged as the 6th argument of `0x0015E7D0`.
- `[sp+0] = value34`: 32-bit word, caller's `record + 0x34` (documented as
  `size`). The original loads it with `vldr s16,[sp,#0x80]` and stores it with
  `vstr s16,[sp,#8]` without any arithmetic; the reconstruction carries it as a
  `u32` because this translation unit is compiled hard-float and a `float`
  parameter would be placed in `s0` instead of the architected stack slot.
- `[sp+4] = index`: caller's `record + 0x08` (loaded with `ldrh`, so
  zero-extended). Forwarded as the 3rd argument of `0x0015E7D0`.
- **Return value:** none. `r0` at return is leftover register state: `out` on
  the string-equal (`0x0015E6A8`) and request-success (`0x0015E72C`) paths, `0`
  on the release-failure path (`0x0015E698`), and the status word (`0x64` or
  `0xC8`) on the failure path (`0x0015E7A0`). The caller ignores it.
- Callee-saved `r4-r11` are preserved and the final SP equals the entry SP. The
  original builds a `0x54`-byte frame after the nine-register push plus the

Details pinned by the ARM encoding:
- The name comparison is `strcmp` (`0x002AA7F4` is the newlib word-at-a-time
  implementation with the `0x01010101` zero-byte test), and the branch is taken
  when it returns exactly 0.
- The 16-byte copy is four unaligned word loads/stores in ascending order; the
  byte-wise copy emitted for the reconstruction preserves the same forward
  overlap behaviour (the test includes a `mount_name = context+0x335` case).
- The release result is tested with `ands r0,r0,#0x80000000` + `bpl`, i.e.
  signed `code >= 0` continues; the raw `u32` is then passed to `0x002BAD80`.
- Both result tests use `lsrs r0,r0,#0x1f` + `beq`, i.e. the sign bit of the
  value returned by `0x002A1578`. The second test is emitted after the state
  initialiser even though a pure result helper can never make it differ from the
  first; both calls and both tests are kept. The differential test exercises the
  second test with a stub-only `[negative, non-negative]` sequence.
- The applet global pointer at `0x00432FC8` is loaded twice: once to form the
  `+0x98` argument and once for the `+0x754` flag update. The test rewrites the
  global from the lock stub to prove the second load.
- The `0x002BB09C` call targets a stack slot that the compiler reuses for the

- `0x002C583C(0)` indexes the global table at `0x00446DA0` and its value is

## Domain Limits
- All nine direct-call targets are stubbed by address, so their internals (the
  `strcmp` word loop, the release table walk and its vtable dispatch, the
  `nn::Result` module-descriptor lookup, the `0x0015EF34` request pipeline and
  the atomic lock) are not exercised. The stubs are deterministic models of the
  documented contracts above.
- `0x0015E7D0` is a two-level forwarder whose final callee `0x0015EF34` performs
  the actual content query. Only the argument tuple is verified here; whether
  the request succeeds or fails is supplied by the stub.
- `[out+0x01..0x03]` are never written by `0x002A13D0`. On the ready paths they
  keep whatever the caller's buffer held; on the failure paths they are copied
  from this function's stack local. The test runs with a zeroed stack, so both
  sides see zeros there. This is unobservable in the original C++ object model
  and is not a meaningful difference.
- `r0` at return is path-dependent leftover state in the original and is not
  reproduced as a value; the sole caller ignores it.
- The second `Result_Value` test cannot be taken with a pure result helper; the
  test forces it through a stub-only sequence to validate the emitted structure,
  and that sequence is not claimed to occur in the real SDK helper.
- `0x002AD46C` is a recursive-style try-lock that this function never releases;
  the release is the caller's responsibility and is outside this span.
- No runtime, staging or production promotion is claimed.
