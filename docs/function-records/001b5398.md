# Function Record: script_vm_func_001b5398 (0x001b5398)

## Summary
- **Address:** `0x001b5398`
- **Size:** 600 bytes (original span `[0x001b5398, 0x001b55f0)`). The body ends
  with the `pop {r4, r5, r6, r7, pc}` at `0x001b55e4`; the two words
  `0x001b55e8` (`0x00435D78`) and `0x001b55ec` (`0x000002A2`) are the literal
  pool. `0x001b55f0` starts the next function (`btlMain_Calc`).
- **File:** `src/engine/leaf_batch34_c.cpp`
- **Role:** Per-frame update of the `"btlHelp Calc"` task. It walks the global
  help-entry list, discards leading entries marked with a negative status,
  performs the per-entry text/audio/id update for the first live entry, advances
  the entry's status/counter pair and returns 0.
- **Status:** Reconstructed as readable C++ and **differentially verified**
  against the pinned original (37 cases + 4 negative controls). The candidate
  body is 520 bytes and is not byte-identical (register allocation and block
  layout differ), so the ledger row is `non_matching` and this record carries
  the semantic evidence.

## Contract and Behavior

### Signature and ABI
```c
extern "C" u32 script_vm_func_001b5398(u32 handle);
```
- `handle = r0`; `r1..r3` are never read by this body.
- The handle is forwarded to `0x002C0AC8` on entry (`0x001b53a0`) and that
  result is discarded.
- **Return value:** always `0`. `r6` is cleared before the scan and never
  written; the null-manager path returns the zero it has just loaded. Both
  `0x001b55dc` and `0x001b5588` return `r0 = 0`.
- The prologue pushes `{r4, r5, r6, r7, lr}`; `r4-r7` are restored and `r8-r11`
  are never touched. `r12` is not preserved (caller-saved).
- No stack arguments, no floating point, no indirect call of its own.

### Caller and task context
- The only reference to this address is the static task descriptor at
  `0x001d25c0`: `{ 0x0020EE34, 0x001B5398, "btlHelp Calc" }` (words at
  `0x001d25c0`/`0x001d25c4`, name at `0x001d25c8`).
- `0x0020EE34` is the task trampoline. It also calls `0x002C0AC8(r0)`, keeps the
  result in `r5`, then walks the same list and removes **every** node through

- `0x001d2580..0x001d25bc` allocates the manager and stores it in `0x00435d78`
  with `head = tail = count = 0`.

### Control flow
1. `0x002C0AC8(r0)`; result discarded.
2. `manager = [0x00435D78]`. Null returns 0. `node = manager->head`; null
   returns 0.
3. Loop head (`0x001b53c4`): save `next = node->next` **before** the status
   test, then read `status = (s16)node->+0x2A2`.
4. `status < 0`: unlink and release the node:
   - read `previous = node->previous`, then **reload the manager pointer**;
   - `previous == 0 ? manager->head = next : previous->next = next`;
   - re-read `node->next`; if null store `node->previous` into `manager->tail`,
     otherwise store it into `re-read next->previous`;
   - `manager->count -= 1`;
   - `0x002C4360(node)`; continue with the saved `next`, or return 0 at the end.
5. `status >= 0`: process this single node, then return 0.
   - **state 0:** if `0x002B6E44() != 0` or (`0x002B6E44() == 0` and
     `0x00295E74() != 0`), preload status 1 and skip the body. Otherwise:
     - zero a 0x60-byte stack frame with `0x002C4B30(frame, 0x60)`;
     - `kind == 0`: `0x0027EA24(+0x0C, low16(+0x08))`, then
       `0x0027E9E4((s32)(s8)+0x298, 1)`;
     - `kind == 1`: when `(+0x10 | +0x14) != 0` and signed `+0x29C >= 0`, copy
       the text chosen by bit 1 of `+0x10` (`0x002BD3EC` when set,
       `0x002BD25C((u16)+0xDE)` when clear) into the frame with
       `0x002BF86C(frame, source)` and call
       `0x00295904(+0x29C, frame)`; then the kind-0 tail;
     - `kind == 2`: the same text condition and calls, then
       `0x00212024((u16)+0x04)`; no script tail;
     - any other kind: no tail call (the frame is still zeroed);
     - finally write `status = 1` and `state = 1`.
   - **state 1:** only `0x002B6E44()`; a non-zero result preloads status 1.
   - **any other signed state:** no work.
6. Common tail (`0x001b5568`): read `u16 status`, read `u16 counter`, store
   `status - 1` and `counter + 1` (both modulo 2^16), then return 0. The
   status preload plus this decrement leaves status 0 on every processed path.

## Contract corrections found during implementation
- **`+0x08` is a 32-bit load, not a halfword load.** `0x001b54a4` does
  `ldr r1,[r4,#8]` followed by `uxth r1,r1`; a `u16` field would have emitted
  `ldrh` and read a different access width. The struct uses `u32 low_08` and
  forwards `static_cast<u16>(...)`.
- **The status preload is immediately decremented.** Both `0x001b553c` and
  `0x001b5560` write 1, then the common block at `0x001b5568` subtracts one.
  The net observable status of a processed node is 0; the intermediate write is
  still reproduced in source order.
- **The manager pointer is reloaded in the removal path** (`0x001b5594`) after
  the previous-pointer load; the C++ reloads it there rather than reusing the
  entry-time value.
- **`kind` 1 and `kind` 2 share the text test but not the tail.** Kind 1 ends
  at `0x001b54a4` (`0x0027EA24`/`0x0027E9E4`); kind 2 ends at `0x001b5534`
  (`0x00212024`). Other kinds jump straight to `0x001b553c`.
- **The return value is constant 0**, not the last helper result. `r6` is set
  to 0 at `0x001b53b8` and never written, including the removal path.

## Limits
- Helper bodies were not reconstructed here. Calls are stubbed from their
  observed register contracts; in particular `0x002BF86C` is modelled as a
  NUL-terminated string copy and `0x002C4B30` as a zero fill. Their internal
  scene side effects are outside this routine.
- `0x002C0AC8`, `0x002BD3EC` and `0x002BD25C` contain their own indirect
  dispatch/table lookups; only their arguments and returned pointers matter to
  this caller and were stubbed deterministically.
- No emulator/runtime scenario was run: the differential evidence is offline
  Unicorn ARM execution of the pinned bytes versus the compiled candidate with
  the same fixtures. Node ownership and manager lifetime beyond this routine are
  inferred from the `0x0020EE34` trampoline and the `0x00435D78` allocator.
- The candidate does not reproduce the original's `r12` value or its exact stack
  frame layout; neither is part of the AAPCS contract and neither is compared.
