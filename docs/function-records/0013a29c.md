# Function Record: engine_func_0013a29c (0x0013A29C)

## Summary
- **Address:** `0x0013A29C`
- **Size:** 484 bytes (span `[0x0013A29C, 0x0013A480)`)
- **File:** `src/engine/leaf_batch41_c.cpp`
- **Role:** Resets one audio-channel state record to its initial values and
  publishes the reset through the shared audio-channel helpers. The 484-byte
  ledger span contains **two entry points** plus their literal words:
  - `0x0013A29C engine_func_0013a29c(void* state)` — 109 instructions
    (`0x0013A29C..0x0013A450`), followed by the literals `0x3F800000` (1.0f at
    `0x0013A450`) and `0x004E6F64` (at `0x0013A454`).
  - `0x0013A458 engine_func_0013a458(void* state, f32 value)` — 9 instructions
    (`0x0013A458..0x0013A47C`), followed by the literal `0x004E6F64` at
    `0x0013A47C`. This entry is not a separate ledger row.
- **Status:** Reconstructed as readable C++ and **differentially verified**
  against the pinned original. The candidate is not byte-identical (388 B main
  body and 44 B second entry vs. 436 B / 40 B), so the ledger row is
  `non_matching` and this record carries the semantic evidence.

## Contract and Behavior

### Signature and ABI
```c
extern "C" u32 engine_func_0013a29c(void* state);            // 0x0013A29C
extern "C" u32 engine_func_0013a458(void* state, f32 value); // 0x0013A458
```
- `r0 = state`: pointer to the channel state record. Both entries use it. In
  production the only caller passes `0x004EAD10` (see *Caller evidence*); the
  differential treats it as an arbitrary pointer.
- `r1..r3` are ignored by both entries (only `r0` is read before the first
  helper call).
- `s0 = value` for the second entry only; it is a VFP single-precision value.
- **Return values:** the initializer tail-branches to `0x00146F44(base, 0)`, so
  its visible `r0` is that helper's result. The setter tail-branches to
  `0x002A86E4` on the update path (helper result) and returns with `r0` still
  holding the incoming `state` pointer on the skip path. The candidate models
  both explicitly.
- Callee-saved registers are preserved. The original pushes
  `{r4,r5,r6,r7,r8,lr}` plus `d8` (for the 1.0f constant) and restores them, so
  the final `SP` equals the entry value. The second entry uses no stack.

### Caller evidence
A raw scan of the pinned `.text` for ARM `b`/`bl` immediates found exactly two
references:
- `0x00128DA8 bl 0x0013A29C` inside the initializer beginning at
  `0x00128D44`. Immediately before the call (`0x00128DA0`) the caller loads
  `r0 = 0x004EAD10` (literal at `0x00128E1C`); it does not pass its own
  `r4` object.
- `0x00128E38 b 0x0013A458` inside the wrapper entry at `0x00128E20`. That
  wrapper tests its own `r0->+00`, stores `s0` at its own `r0->+04`, then loads
  `r0 = 0x004EAD10` (literal at `0x00128E40`) and tail-branches to the setter.

No literal word in `.text` contains either entry address, so there is no
in-image function-pointer reference to these entries.

## Domain Limits
- `0x002A86E4`, `0x002A8674`, `0x002A8608`, `0x00147074`, `0x00146F88`,
  `0x00147020`, `0x00146FD8`, `0x00147128` and `0x00146F44` are stubbed by
  address. Their own `0x002BB5B4` readiness checks are therefore bypassed; the
  gate is exercised only through the one direct call at `0x0013A3FC`. The real
  helpers' internal table reads are modelled from their disassembly, not
  executed.
- `0x00146F44`'s `slot+0xC0` read-modify-write and the descriptor flag words
  are modelled per the observed ARM instructions; no other fields of the
  descriptor are validated.
- The candidate folds `1.0f * x` and `x * 1.0f` into `x`. The only behavioural
  difference from the original's `vmul.f32` is signalling-NaN quieting, which
  the fixtures do not exercise (finite and quiet-NaN cases do pass).
- The compiled second entry is 44 B versus the original's 40 B (the literal
  moves from `0x0013A47C` to `0x0013A480`), so a production placement of that
  entry needs a relocation/space decision. The candidate main body is 388 B
  and fits inside the original 436 B instruction region.
- In production `state` is `0x004EAD10`, which shares a 64 KiB page with the
  helper base `0x004E6F64`; the differential keeps the state in a separate
  page. For the record offsets `+0x00..+0x34` the two objects do not overlap
  (`0x004EAD10..0x004EAD44` vs. the selector/pointer cells at
  `0x004E8282`/`0x004E8004`), so this does not hide an observed alias.
- `0x002C3AA8` / `0x002C3A24` are stubbed without their thread-id
  read (`mrc p15`) and reference-count updates, so lock-block memory is not
  compared beyond its untouched fixture bytes.
- No runtime, staging or production promotion is claimed.
