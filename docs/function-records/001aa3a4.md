- **Role:** "EffectDrawUp3D" draw task.  Pushes one command word onto each of

### Push and pop sequences
Push (identical for the three nodes):
1. `previous = slots[depth]`
2. `depth = depth + 1`
3. `slots[depth] = value`
4. re-read `dirty`; if `dirty != 0 || previous != value`, call
   `flush_cb(value)` and store 0 to `dirty`.

Pop (identical for the three nodes):
1. `previous = slots[depth]`
2. `depth = depth - 1`
3. `new_top = slots[depth]`
4. re-read `dirty`; if `dirty != 0 || previous != new_top`, call
   `flush_cb(new_top)` and store 0 to `dirty`.

A pop always runs after its push, so a node's depth is at least 1 when the pop
executes; the `depth == 0` pop index is unreachable in this routine.

## Domain Limits
- All seven direct calls are stubbed deterministically because their real
  behaviour depends on live engine/render state.  `0x00286834`, `0x002c5f7c`
  and `0x002c5fa4` are reproduced faithfully from their ARM bodies (pure bit
  building); `0x002c0ac8`, `0x0028674c`, `0x002c1b64` and `0x002c1abc` are
  replaced by fixture-controlled stubs, so the object-table traversal, the
  callback-list walk and the two render flushes are not exercised here.
- The lookup result is not used by this routine, so its found/not-found
  behaviour cannot change the observable path; that is asserted rather than
  assumed (both variants are covered).
- The flush callback is fixture-controlled (three targets, one of which switches
  the render base).  Its real identity, arity and return use are not recovered
  beyond "called with the new value in `r0`, result unused".
- Neither `0x0044ea00` nor the flush callback is null-checked by the original;
  the reconstruction keeps that, and the render base is required to be a valid
  mapped pointer.
- The stack node layout is only backed by the observed byte offsets; ownership,
  capacity, the meaning of the pushed command words and the true slot count are
  not recovered.  Depth 3 is covered; a depth that pushes the slot store onto
  the callback pointer (`depth == 4`) was not exercised because both bodies would
  then `blx` a clobbered pointer.
- The reconstruction reuses the shared `func_002247c8` push/pop helpers, whose
  empty `asm volatile("" ::: "memory")` barrier keeps the ARM's `count == 3`
  dirty-byte observation; it emits no instruction.
- The compiled candidate loads `0x0044ea00` once before the three pops and
  reuses it while no flush callback runs (the original re-reads it before each
  pop).  The narrowing is unobservable unless a render node's `count` store
  aliases the global itself, which requires a base pointer overlapping
  `0x0044ea00` and no realistic render base does; after every flush callback
  the candidate re-reads the global, so callback-driven base switches are
  preserved (covered by the differential cases).
- Runtime integration (a live render base, the real object-table producer, the
  `0x0028674c` callback walk and the consumers of the queued command words) was
  not exercised; this record covers offline differential equivalence only.
