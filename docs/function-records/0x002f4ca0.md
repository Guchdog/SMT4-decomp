## Limits and next step

This supports only the readable orchestration under the explicit HLE boundaries. It does not establish equivalence for the allocator's real zero-fill/pool policy, task-pool mutation/scheduling/lifetime/parent linkage, sprite resource setup, cursor state, asynchronous asset completion, sound service, shared UI reset effects, or subsystem fault behavior. Helper call trace matching is not evidence that these stubs behave like the game engine. Mappers are executed as original functions; this test says nothing about separate mapper candidates. Valid pinned code/data is mapped, but no runtime caller composition was exercised.

Not tested: actual allocator failure/null behavior, callback invocation or ordering, draw task lifecycle, async load completion, visible UI, input/edit flow, cancel/confirm, persistence, profile isolation, integrated patch behavior, emulator runtime, or whole-game equivalence.

Next: resume the CLI-only Azahar scenario after the offline H2 batch is independently reviewed. Validate actual task scheduling, visible settings, input/edit/cancel/confirm, and persistence before advancing those claims.
