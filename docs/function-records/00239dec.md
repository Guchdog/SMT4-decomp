# Function Record: func_00239dec (0x00239dec)

## Summary
- **Address:** `0x00239dec`
- **Size:** 408 bytes (original span `[0x00239dec, 0x00239f84)`; 99 ARM
  instructions plus the 12-byte literal pool `0x075bcd15`, `0xe0c04702`,
  `0xc8804471`)
- **File:** `src/engine/leaf_batch41_c.cpp`
- **Role:** Hash-and-submit wrapper. It hashes a 12-byte halfword-keyed record
  (seed XOR `0x075BCD15`, then `value ^ ror(hash, 5)` per element), forwards the
  record and hash to `0x003fc300`, and on one distinguished failure status
  hashes the record again and calls `0x003fc46c`, returning one of two
  function-specific status literals.
- **Status:** Semantically equivalent C++ (`non_matching`). The compiled body
  is 244 bytes versus 408 original bytes (the unrolled two-at-a-time hash loop
  becomes a simple loop and the status test is folded into one mask compare);
  the ledger row is classified `non_matching` and this record carries the
  semantic evidence.

## Contract and Behavior

### Signature and ABI
```c
u32 func_00239dec(u32 context, u32 arg1, u32 arg2, Record* record);
// r0 = context, r1 = arg1, r2 = arg2, r3 = record
```
- `context`, `arg1` and `arg2` are forwarded unchanged as the first three
  arguments of `0x003fc300` (the test logs them independently).
- `record` points at three words read by `ldm r3, {r3, lr}` and
  `ldr r6, [r3, #8]` / `ldm r7, {r0, r5}` and `ldr r3, [r7, #8]`.
- Return: `r0` carries either the first helper result unchanged, the second
  helper result/literal, or one of the two literal statuses below. The original
  saves `r4-r11` + `lr` (36 bytes) and reserves 0x24 bytes of stack, so the two
  calls place their three stack arguments at `sp+0`, `sp+4`, `sp+8`.

### Record layout (r3/`record`)

| `+0x00` | `u32` | hash seed, XORed with `0x075BCD15` (literal at `0x00239f78`) |

### Hash
`hash = seed ^ 0x075BCD15`, then for ascending element indices
`hash = value ^ ror(hash, 5)`, where `value` is the zero-extended `ldrh` at
`values[i]`.
- The loop bound is **not** `count` directly. `0x00239e0c..0x00239e18`
  computes `values + count*2 - values` (the doubled count, modulo 2^32) and
  keeps it in `fp`; `fp, asr #1` then sign-extends and halves it. The resulting
  signed value `c` is the number of mixed elements:
  `c = (s32)(count << 1) >> 1`.
- A non-positive `c` mixes nothing (the original skips both the unrolled loop
  and the trailing element load, `0x00239e1c`/`0x00239e5c`). For `c > 0` the
  original mixes exactly `values[0..c-1]` once each, in ascending order; the
  two-at-a-time unroll at `0x00239e24..0x00239e58` together with the trailing
  mix at `0x00239e64..0x00239e6c` covers that range for both parities.
- Because of the doubled-count arithmetic the high bit of `count` is not a
  simple count: `0x80000000` and `0x80000001` derive `0` and `1`,
  `0x40000001`/`0xC0000001` derive negative counts, and `0xFFFFFFFF` derives
  `-1`. The test uses unmapped element buffers for the no-read derivations.
- The byte length passed to the helpers is `count << 1` (32-bit wrap)
  (`0x00239e70`, `0x00239f20`).

### Status handling
The original tests only bit 31 for success/failure and then a two-part status
pattern:
- **First call** (`0x00239e8c..0x00239eb0`):
  - bit 31 clear => return the helper result unchanged;
  - bit 31 set but module/description mismatch => return the result unchanged;
  - bits 10..17 equal `0x11` **and** bits 0..9 equal `0x6F` (i.e. the
    `0xC880446F` family: level bit 31, module `0x11`, description `0x6F`) =>
    run the second hash/call.
- **Second call** (`0x00239f40..0x00239f6c`):
  - bit 31 clear => return `0xE0C04702` (literal at `0x00239f7c`);
  - distinguished status => return `0xC8804471` (literal at `0x00239f80`);
  - any other negative result => return that result unchanged.

### Second pass
The record is **re-read** after the first call (`ldm r7, {r0, r5}`,
`ldr r3, [r7, #8]`), so a helper that updates the seed, count or buffer pointer
changes the second hash and its arguments. The first pass also submits the
record pointer itself, so the helper can mutate it.

### Caller evidence
Static ARM `bl` sites to `0x00239dec`: `0x002256ec`, `0x00355628`,
`0x003fc65c`, `0x003fc774`, `0x003fc828`. Each sets `r0-r3` immediately before
the call and several normalize the result with `(result & 0x80000000) == 0`
(`movge r0, #0`), confirming that bit 31 is the success/failure level and that
the two 12-byte records at `sp+8`/`sp+0x18` in the `0x003fc…` callers supply
the seed/count/pointer words. At `0x002256c8` the caller stores a word at
`record+0`, and passes `record+4` elsewhere before submitting `record`.

## Domain Limits
- Both helpers are stubbed. Their real bodies (`0x003fc300` and `0x003fc46c`,
  raw-ARM leaf bodies in `src/engine/leaf_batch38_b.cpp`) are not executed;
  the status values, record mutations and scratch writes are synthetic test
  inputs. The downstream requests performed by those helpers, their return
  conventions beyond the observed bit-31/status tests, and the module-`0x11`
  status meaning are not established.
- Field meanings beyond the observed offsets are **not** established; the
  names `seed`, `count` and `values` are inferred from use, and no external
  type is claimed. Caller argument provenance is documented from disassembly
  only.
- No range checks exist: `count` can derive a huge positive element count and
  the loop will walk until an unmapped page faults. The test only exercises
  mapped fixtures for positive counts up to 32 and uses unmapped buffers for
  the no-read derivations.
- The original's unrolled loop reads the trailing halfword in a different
  order than a simple loop; both access the same `values[0..c-1]` range and the
  function reads no volatile/device memory, so the scheduled load order is not
  observable in this contract.
- No integrated runtime, caller-composition or whole-game equivalence is
  claimed; the node is a synthetic-data differential test against the pinned
  original.
