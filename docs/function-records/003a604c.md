## Contract and Behavior

### Signature and ABI
```c

```
- `object = r0` is the pre-allocated shop object; `type = r1`, `flag = r2`,
  `mode = r3`.
- Return value: the same `object` pointer in `r0` (`mov r0,r7` before the
  epilogue). The verified caller `shop.cpp` stores that pointer as
  `work->shop_data`.
- Prologue `push {r4,r5,r6,r7,r8,r9,r10,lr}`; the final `pop` restores the

  the mode-specific setter/command branch, while its low byte is stored at

## Contract corrections found during implementation
- **The second `*(u32*)object = 0` is not redundant** in the sense that it
  happens after the header/array constructors, so a helper that touched
  `object[0]` is overwritten.
- **`0x003A4734` runs before the field stores**, not after; the table copy
  therefore cannot overwrite `+0x10`/`+0x18`.
- **`type` and `mode` are re-read from memory** (`+0x10`, `+0x18`) after the
  early helper calls; `flag` branch selection uses the original 32-bit
  argument, while `0x002C0C04` receives the stored byte.
- **The type-1 branch never scans the rows** and never calls
  `camp_func_0029c0fc(0x1C, 1)`.
- **The row count is re-loaded after each element**, so a helper that changes
  the count would change the termination; the candidate preserves this.
- **The incoming `r8` is a dead argument to `AsdMemory_func_002c23f8`.** The
  allocator overwrites `r1` before reading it, so the source form passes only
  the size. This is documented rather than reproduced with a register asm.
- **`0x003A0320` is an out-of-ledger constructor address**, passed only as the
  second array constructor argument. `0x004221D8` and `0x00421FF8` are vtable
  addresses, and `0x0100005B`/`0x0100005C`/`0x01000060` are opaque UI command
  ids.

## Limits
- All 24 distinct callees are deterministic stubs in the harness. The record
  validates the caller-side contract (argument values, order, return-flow,
  memory effects and row bounds), not the callees' own behavior.
- `0x003A0320` is not in the reconstruction ledger; it is used only as an
  element-constructor address passed to `0x002C5F58`.
- The two vtable addresses `0x004221D8`/`0x00421FF8` and the UI command ids are
  opaque values recovered from the literal pool; their object layouts are not
  reconstructed here.
- Row counts above `0x400` would read beyond a row's element array in the
  original; that out-of-bounds domain is not exercised.
- The incoming `r8` forwarded as a dead second allocator argument is not
  reproduced in C++; the callee ignores it.
- No emulator run was performed for this span; verification is the static
  original-vs-candidate differential above.
