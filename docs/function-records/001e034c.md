# Function Record: camp_func_001e034c (0x001e034c)

## Summary
- **Address:** `0x001e034c`
- **Size:** 516 bytes (original span `[0x001e034c, 0x001e0550)`; 127 ARM
  instructions through `0x001e0544` plus the two-word literal pool at
  `0x001e0548` (`0x0043dd68`) and `0x001e054c` (`0x3fff8000`))
- **File:** `src/engine/leaf_batch34_c.cpp`
- **Role:** Builds a "unite" definition for a camp unit slot. It merges the
  unit-id lists of two source records into a 24-entry work list, sizes a list
  cursor from the merged count and hands the list plus an eight-byte descriptor
  to `Unite_Init`.
- **Status:** Semantically equivalent C++ (`non_matching`). The compiled body is
  572 bytes (568 bytes of code plus one literal word) versus the 516-byte
  original. A differential Unicorn harness runs the pinned original against the
  compiled candidate; the ledger row is classified `non_matching` and carries
  this record.

## Contract and Behavior

### Signature and ABI
```c
extern "C" void camp_func_001e034c(u32 slot_id, const u8* primary,
                                   const u8* secondary);   // r0, r1, r2
```
- `r0` is a 32-bit slot identifier. Both callers derive it as `slot_word >> 34`
  from a 64-bit camp slot word (`((hi << 15) | (lo >> 17)) >> 17`).
- `r1`/`r2` are pointers to the two source records whose `u16[8]` unit-id list at
  `+0x34` and `u16` field at `+0x46` are read. `r3` is never read; there are no
  stack arguments and the frame is 20 bytes of locals (`sub sp,sp,#0x14`) after
  the nine-register push.
- Preserves `r4-r8`, `sb`, `sl`, `fp` (r4-r11) and `lr`. Both bodies restore the
  entry `sp`.
- Returns whatever `r0` the tail `Unite_Init` call leaves behind; `Unite_Init`
  is declared `void` both here and in `src/camp/unite.cpp`, so the function has
  no defined return value. The differential harness stubs `Unite_Init` without
  touching `r0` and both bodies then return the units-list pointer.

### Callers
Two direct `bl` sites exist in the pinned image:
- `0x0018307c` inside `Camp_MainProc` (`0x0017fe9c`, 27,308 B,
  `src/camp/camp_main.cpp`). Argument 0 is loaded from the slot word at
  `r5+0x390`, argument 1 is `sl`, argument 2 is `r7`.
- `0x00257d68` inside `camp_func_00257c84` (`0x00257c84`, 476 B,
  `src/engine/leaf_batch33_c.cpp`). Argument 0 comes from the 64-bit slot word
  at `[r7]`, argument 1 is `sb`, argument 2 is `r8`.

Both callers immediately walk `[*(0x0043DD68)+0x9020]` with the same 8-entry
halfword scan pattern, which confirms the work list is the shared output.

### Control flow
1. `work = *(u32*)0x0043DD68`.
2. `record = camp_func_002b9364(slot_id)`. This lookup happens **before** the
   work list is cleared; the harness logs the pre-clear list word at the lookup
   to pin that order.
3. Clear `work+0x9020 .. work+0x904c` with twelve 32-bit zero stores.
4. For `i = 0..7` over the primary list (`signed blt` bound, `r4 = 0,1,...,7`):
   `id = primary[0x34+2i]`; skip when `id == 0`; skip when
   `(camp_func_0029ec14(id)[3] & 0x20) == 0`; skip when
   `camp_func_0029d080(work+0x9020, 0x18, id) != 0`; skip when
   `camp_func_0029d080(record+0x3C, 8, id) != 0`; otherwise append `id` and
   increment the count.
5. Repeat step 4 for the secondary list.
6. `camp_func_0029fae8(work+0x9204, count, 8, 1, 1, 1)` — cursor, total,
   visible rows, columns, wrap row and repeat flag (the last two on the stack).
7. Build the eight-byte descriptor:
   - word 0 = `(primary[0x46] & 0x7FFF) | ((secondary[0x46] & 0x7FFF) << 15) |
     0x40000000`. The original also masks the shifted value with `0x3FFF8000`
     and clears bits 30..31 before setting bit 30, which has the same result for
     every `u16`.
   - word 1 = `0x1 | ((slot_id << 2) & 0xFFFDFFFF)`; bit 17 of word 1 (bit 15 of
     `slot_id << 2`) is cleared.
8. `Unite_Init(work+0x9020, count, &descriptor, NULL)`.

The original re-loads the source halfword before each helper call and before the
append store. The reconstruction captures it once per iteration; that is
observable only if a helper writes the caller's source record, which none of
them does (the differential harness keeps both source pages read-only and
compares them after every case).

### Relationship to the slot-word format
The descriptor word 1 is `0x1 | (slot_id << 2)` with bit 17 cleared, and
`Unite_Init` recovers `slot_id` as `word1 >> 2`. The two callers already compute
`slot_id` as `slot_word >> 34`, so the two 16-bit ids at bits 0..14 and 15..29 of
descriptor word 0 are the same pair the camp slot words store: `0x00257c84`
extracts them with `& 0x7FFF` and `(word >> 15) & 0x7FFF` in the code that runs
immediately before the call. The constant `0x40000000` sits in the unused
bits 30..31 of that layout.

### Original read-modify-write of the descriptor high word
`0x1e04d8` loads the not-yet-initialised stack slot at `[sp+8]` and
`0x1e0514`/`0x1e0520` OR bits 17..31 of the old high word back into the new one.
Every other bit of both descriptor words is overwritten, so the only effect is
that bits 17..31 of descriptor word 1 can carry stale stack values in the
reference build. No caller can depend on stack garbage. The reconstruction
starts those bits at zero; the differential harness zero-fills the stack, so the
original also observes zeros and the descriptor matches bit-for-bit.

## Limits and Unresolved Items
- All five callees are stubbed deterministically. The harness verifies the
  arguments, call order and caller-side use of the results, not the real
  callees' internal effects; the callees remain byte-preserved elsewhere and are
  not re-implemented here.
- `camp_func_002b9364` can return 0 for an unknown slot id. The original then
  passes `0x3c` to the 24-entry scan and faults on unmapped low memory; that
  domain is outside the verified range because both bodies would fault.
- `camp_func_0029ec14` may in principle return 0, which the original would
  dereference at `+3`; only non-null entries are in the verified domain.
- The 24-entry scan bound (`0x18`) is not behaviourally observable: the list is
  cleared first and at most 16 ids are appended, so the extra entries are always
  zero and can never match a non-zero id. It is preserved as written, but no
  mutant of that constant can be detected.
- Aliasing between the work list and the caller's source records is not
  supported; the original would observe the in-loop writes through the reloaded
  halfword, the reconstruction would not.
- Field names and the meaning of the flag byte, of `0x40000000` in the
  descriptor and of the two `+0x46` ids are not established by the ARM evidence.
- No emulator or whole-game runtime test was performed; this record covers the
  offline differential harness only.
