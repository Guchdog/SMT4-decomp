# Function Record: shop_func_0022f9c8 (0x0022f9c8)

## Summary
- **Address:** `0x0022f9c8`
- **Size:** 504 bytes (original span `[0x0022f9c8, 0x0022fbc0)`): 125 ARM
  instructions `0x0022f9c8..0x0022fbb8` (500 bytes) plus the literal word
  `0x00015d24` at `0x0022fbbc`.  The body ends with `pop {r4, r5, r6, pc}` at
  `0x0022fbb8`.
- **File:** `src/engine/leaf_batch42_b.cpp`
- **Role:** Shop/UI selection-change handler.  Reads the selection index from the
  shop object, resolves an item id through a per-selection entry count and a
  halfword table, drives three UI transition helpers according to a visibility
  predicate / already-applied id / per-object state bytes, and finally, when a
  further per-object gate is non-zero and the id changed, fills a 0x8C-byte
  scratch record and hands it to two engine consumers.
- **Classification:** `non_matching` with semantic evidence.  The compiled body
  is 472 bytes versus the 500 instruction bytes + 4 literal bytes of the
  original: the compiler folds the two adjacent byte flag stores into one
  halfword store, folds the switch table differently, and performs the same
  calls, the same object traffic and the same return values (76/76 differential
  cases, 16/16 negative controls).

## Contract and Behavior

### Signature and ABI
```c
u32 shop_func_0022f9c8(ShopObject* object);   // extern "C"
```
- `r0` is the only live incoming core register; `r1-r3` are dead and the
  reconstruction ignores them (the differential test feeds them junk).
- Prologue `push {r4, r5, r6, lr}`, `sub sp, sp, #0x90`; epilogue
  `add sp, sp, #0x90`, `pop {r4, r5, r6, pc}`.  The final SP equals the entry SP.
- Frame: `r5 = object`, `r6` is reused (initially `object + 0x860`, later
  `object + 0x15D54`, then the constant 1, then `object + 0x15D28`), `r4` holds
  the resolved halfword id.

  bytes.  There are no stack arguments.

### Return values (r0 is not forced to zero)
The epilogue does not set `r0`, so the caller observes whichever value the last
executed path produced:
1. `object + 0x15D24 == 0`: returns the loaded gate, i.e. `0`.
2. `object + 0x15D28 == id`: returns the stored word, i.e. `id`.
3. copy/consume path: returns `0x0029A368(buffer)`.
Every other path ends in (1) or (2) after the earlier helpers, whose results are
overwritten.  This was a deliberate check: the reconstruction returns exactly
those values and the differential test compares them.

### Call order
1. `shop_func_002337a0(object + 0x880 + index*0x74)` → element count.
2. `shop_func_003c2f7c(object + 0x880 + second_index*0x74)` → visibility.
3. `ui_func_00299974(0)` (reset path) or, on the visible path,
   `ui_func_0029a25c(active_1e)` and then maybe `ui_func_00299974(1)`.
4. On first activation with `id != 0`: `shop_func_002ae64c(id)` three times with
   an `ui_func_002998d8(slot, id)` between matches.
5. `script_vm_func_002b66ec()` → source pointer (no arguments).
6. `ui_func_002bcf58(buffer, source, 0x8C)` → record copy.
7. `shop_func_002ae64c(id)` → item type (only when `id != 0`).
8. `engine_func_0029960c(buffer)`.
9. `engine_func_0029a368(buffer)` → return value.

The two index reads are kept separate in the reconstruction: the second entry
pointer (used by `0x003C2F7C`) may differ from the first when `0x002337A0`
rewrites `object + 0x860`.  Note also that the u16 id load happens **before**
the `0x003C2F7C` call in the ARM code.

## Domain Limits
- All nine helpers are stubbed deterministically; their real behaviour depends
  on live shop/UI/engine state.  The stubs reproduce the recovered contracts
  (zero/non-zero predicates, the item-type dispatch, the record copy) but not
  the underlying data.
- The object page is a fixture.  `object + 0x860` is used as a flat index with
  no bounds check, exactly like the ARM; the test only exercises indices that
  keep the entry/page addresses inside the mapped 128 KiB object page.  An
  out-of-range index faults in both bodies.
- The u16 id load assumes 2-byte alignment (guaranteed by `0xC94` + even stride
  + `count*4`); the u32 field loads assume the object is 4-byte aligned.
- `0x0029960C` is a naked body in the same translation unit; the reconstruction
  reaches it through a typed function pointer because its declared parameter
  list is empty.  Clang folds that to a direct `bl` today; a future compiler
  that emits an indirect call would still behave identically, but the runner
  would then need an `R_ARM_ABS32` case for that symbol.
- The meaning of the item types, the UI slots, the visibility predicate and the
  scratch-record contents is inferred from their use; the record's real field
  names beyond the seven patched halfword offsets were not recovered.
- Runtime integration (live shop state, the real record producer and the two
  consumers) was not exercised; this record covers offline differential
  equivalence only.
