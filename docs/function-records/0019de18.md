### Control flow and calls
1. **Loop gate.** Load `source->count_28` and compare it signed with zero
   (`ble 0x19DFB4`). A count of `0`, `-1` or `0x80000000` skips the loop
   entirely, without dereferencing `source->+0x24`.
2. **Per item** (`index` is a signed `s32`, incremented and re-compared with the
   reloaded count):
   a. `element = source->items[index]`.
   b. If `list->+0x0C` is non-null and equals `element`, skip the item.
   c. Otherwise call `engine_func_002af604(list->+0x0C, element)` (0x002AF604,
      reconstructed in `src/engine/leaf_batch34_b.cpp`). That helper walks
      `node->+0x0C` and returns 1 when it reaches `element`, 0 at a null link.
      A non-zero result skips the item.
   d. If `element->+0x0C` is non-zero, skip the item.
   e. Otherwise append (below).
3. **Append with room.** `capacity = list->+0x20 & 0x3FFFFFFF` and
   `used = (s32)(end_byte_diff) >> 2`. The comparison is the original's signed
   `bgt`; a negative `used` (begin > end) therefore counts as "room".
   With room, `if (end != 0) *end = element; end += 4;` and the element's
   `+0x0C` link is set to `list->+0x10`.
4. **Append on a full vector.** `grown = capacity ? capacity * 2 : 1`
   (`lsl #1` / `moveq #1`). The original then has a signed
   `capacity >= grown` guard; it is unreachable because `capacity` is a 30-bit
   value, so the grow is always attempted. Growth requires a non-null
   `list->+0x14` **and** `(capacity_word & 0xC0000000) == 0x40000000`; if either
   fails the append is silently dropped (no end advance, no link write).
5. **Grow.** `ctx = list->+0x14`; `vtable = *(void***)ctx`;
   `new_begin = vtable[2](ctx, grown * 4, 0x20)`.
   Begin/end are re-read after the call (the original does a second `ldm`),
   then the existing words are copied forward:
   `for (src = begin; src != end; ++src, ++dst) if (dst != 0) *dst = *src;`.
   The destination null test is per iteration, so a null allocation skips only
   the first word and then writes low addresses — reproduced exactly. The copied
   count is recomputed from memory after the loop
   (`(s32)(end - begin) >> 2`). If the reloaded begin is non-null it is released
   through `vtable[3](ctx, begin)`. Finally `begin = new_begin`,
   `end = new_begin + copied * 4`, and the capacity word becomes
   `(capacity_word & 0xC0000000) | grown` (the capacity word is re-read from
   memory at this point, as in the original).
6. **After a successful append** the element's `+0x0C` is set to
   `list->+0x10`, after the end word has been advanced.

## Limits
- 0x002AF604 and both allocator vtable slots were stubbed rather than executed
  from the pinned image; the chain walk is reproduced in the hook, the allocator
  targets are runtime objects and have no static address.
- The higher-level meaning of the two head words (`+0x0C`, `+0x10`) and of the
  capacity tag `0x40000000` is not claimed beyond the observed operations.
- One microscopic ordering difference remains and is not observable through the
  tested contract: the original stores the new `end` before appending an element
  in the grow path, while the compiled candidate can sink that store past the
  element store. It only matters when the element store itself faults, or if
  `*end` aliases `list->+0x1C`; faulting runs are compared on call log and
  memory up to the fault, and the faulting case used here faults inside the copy
  loop before any container write.
- No emulator run and no canonical full-game build were performed for this task;
  the only pinned caller (`0x001DB890`) was inspected for argument/return usage
  but not executed as part of a caller-composition runner.
