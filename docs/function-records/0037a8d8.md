# Function Record: engine_func_0037a8d8 (0x0037a8d8)

## Summary
- **Address:** `0x0037a8d8`
- **Size:** 400 bytes (original span `[0x0037a8d8, 0x0037aa68)`)
- **File:** `src/engine/leaf_batch44_b.cpp`
- **Role:** Initializer for one engine object of the vftable-`0x00421774` family.
  It writes the header fields, copies the `0x00420870` vtable-table entry into
  the embedded AsdFileObject-style base subobject at `+0x14` (including the MSVC
  virtual-base fixup), stores the resource block, the two caller words and the
  error callback pair, then queries the resource through `0x002bb88c`.  A
  negative status either returns through the stored error callback or is
  reported through `0x002bbd10` and the routine continues; the success path
  publishes the low result word into the range view and sets the `+0x50`
  success flag.
- **Status:** Semantically equivalent C++ (`non_matching`). The compiled body
  is 320 bytes versus 400 original bytes (register allocation, literal-pool
  placement, independent-store scheduling and the two stack words being copied
  with integer loads instead of `vldmia`/`vstmia` differ); the ledger row is
  classified `non_matching` and this record carries the semantic evidence.

### Embedded base subobject (+0x14)
The write sequence is the same MSVC virtual-base idiom documented for
`AsdFileObject` in `src/engine/asd_file.cpp`:
1. `vftable = *(void**)0x00420870` (pinned value `0x004208B0`).
2. `self+0x14 = vftable`.
3. `offset = *(u32*)(vftable - 0x30)` (pinned value `0` at `0x00420880`).
4. `*(void**)(self + 0x14 + offset) = *(void**)0x0042087C` (pinned value
   `0x004208B0`).

Because the offset is read from the table, the second store can target any
object word.  The original performs it before the `+0x2C` sentinel store and
before `+0x34..+0x4C`; the C++ preserves that order.  The independent header
stores are reordered by the compiler (see Domain Limits).

### Unreachable cleanup
Before the resource query the original reads `[self+0x52]` and emits:
```
cmp  r0, #0            ; [self+0x52]
cmpne r8, #0           ; r8 is the hard-wired zero register
ldrbne r0, [self+0x50]
cmpne r0, #0
beq  continue
```
The middle operand is a compile-time zero, so the guarded release
(`0x002b93f0` on `resource->handle_04 & ~1`, then `handle_04 = 0` and
`+0x50 = 0`) can never run; `+0x50` has also just been cleared.  The C++ keeps
the byte read in source and documents the block with an explicit `false`
operand; the compiler removes both the read and the release from the compiled
body because the branch is statically dead (a normal-RAM read is not part of
the observable contract).

### Resource query (0x002bb88c)
`0x002bb88c(handle_block = &resource->handle_04, out_pair)`:
- reads the handle word at `handle_block+0x00`, masks bit 0 and queries it,
- returns a signed status,
- on `status >= 0` copies the 8-byte result to `handle_block+0x0C/+0x10`
  (`resource+0x10/+0x14`) and to `*out_pair`,
- on `status < 0` zeroes `handle_block+0x0C/+0x10` and leaves `*out_pair`
  untouched.

Two branches follow `resource->quiet_1c`:

1. `quiet_1c != 0` (quiet path):
   - The output pair is pre-cleared with a `strd` of zero.
   - `status` is stored to `resource->status_18`.
   - `status < 0`: reload `self->callback_48`; load `code = self->resource_34->status_18`
     (the re-read is unconditional in the original) and `self->callback_arg_4c`;
     call `callback(code, arg)` when the callback is non-null; return `self`
     without touching `+0x38`, `+0x44`, `+0x50` or `+0x52`.
   - `status >= 0`: continue to the success path with `out_pair[0]`.
2. `quiet_1c == 0` (reporting path):
   - The output pair is **not** pre-cleared.
   - `status < 0`: call `nn_sdk_func_002bbd10(status, site, 1)` where `site` is
     the address of the failing call in the original (`mov r1, pc`; the C++
     passes a label address inside its own body).  The routine then continues
     to the success path, so a negative status is swallowed after reporting and
     the low output word is whatever the untouched stack slot contained.
   - `status >= 0`: continue with `out_pair[0]`.

### Success path
1. `if (field_44 == 0) self->field_44 = value;`
2. `self->range_38 = value;`
3. `func_00235eec(&self->range_38, 0, 0)` (sets `self->range_3c = 0` because
   mode `0`; the field is already zero).
4. `self->initialized_52 = 0;`
5. `self->active_50 = 1;`
6. return `self`.

## Domain Limits
- Every direct callee is stubbed.  The real bodies of `0x002bb88c`,
  `0x002bbd10`, `0x00235eec` and `0x002b93f0` are not executed; the record
  covers the arguments, return values and memory effects this function observes.
- The stack output pair of `0x002bb88c` is a local whose address differs between
  the two bodies; the call log records it as a class rather than a value.  The
  stale word forwarded by the reporting negative-status path is an
  uninitialized stack read in the original; the test pins it with a stack
  sentinel.
- The report site passed to `0x002bbd10` is the address of the failing call in
  the original and a label address inside the candidate in the C++ body, so the
  numeric value is layout-dependent; the test only requires a code address
  inside the routine.
- The object and resource blocks are synthetic RAM.  Field meanings beyond the
  ARM offsets are not established; `+0x04..+0x0B`, `+0x30..+0x33`, `+0x51` and
  the words after `+0x52` are only known to be untouched.
- The C++ assumes `self` and `resource` are distinct typed objects, as the only
  known caller provides, and that the object does not overlap the static
  vftable tables; under a wrapped negative virtual-base offset or such an
  overlap the compiler's reordering of independent header stores and loads
  would differ from the original order.  Real offsets are small and
  non-negative.
- No runtime, caller-composition or whole-game equivalence is claimed.  The
  caller at `0x0037b628` is documented from disassembly but not executed against
  a patched image.
