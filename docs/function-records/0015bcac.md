### Cursor advance
The owning cursor is re-read after the packet stores:
- arena cursor non-zero: advance to `cursor + 0x70` when
  `(u32)(cursor + 0x70) <= [arena+0x04]`; otherwise leave it unchanged. The
  packet is written even when it does not fit.
- arena cursor zero: read `g_GpuCommandCursor` / `g_GpuCommandEnd`; advance the
  global cursor when `(u32)(global_cursor + 0x70) <= g_GpuCommandEnd`.
Both bounds tests are unsigned (`bhi`/`bls`), so a limit at or above the
cursor can still fail when the addition wraps.

## Unresolved / Domain Limits
- `0x002C39A4` and `0x002BC300` are stubbed deterministically (the former logs
  its screen selector and returns a fixture address, the latter adds a
  configurable bias or returns explicit per-call results). Their real
  framebuffer/address-translation behavior is not reconstructed here; the
  candidate passes exactly the arguments the original passes.
- The exact type and ownership of the arena, draw entry and the two shared
  cursor globals beyond the observed offsets are not recovered. Field names are
  descriptive, not original identifiers.
- A null destination (arena cursor null and `g_GpuCommandCursor` null) is a
  latent write to address 0 in both the original and the reconstruction; the
  differential fixtures never take that path.
- Aliasing between the packet destination and the arena or draw entry is not
  exercised; the only caller keeps the arena on its stack and the destination
  in a separately pointed buffer (`[entry+0x18]`).
- The candidate's register allocation differs (it uses `fp`/`r11`, merges
  stores into `stm`, and computes the halving shift with `clz`), and it loads
  the kind table before the helper calls exactly like the original. Final
  registers, call order and memory match in all differential cases.
- Runtime command-stream consumption, GPU state and in-game rendering were not
  exercised; this record covers offline differential equivalence only.
