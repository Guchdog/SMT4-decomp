## Payload size and buffer
`size = (u32)(4.0f * (f32)desc+0x00 * (f32)desc+0x04)` computed exactly as the
original's VFP sequence at `0x0012058C..0x001205B8`: `vcvt.f32.s32` for both
factors, `vmul.f32` by `4.0f` (literal `0x40800000`), a second `vmul.f32`, then
`vcvt.u32.f32` (unsigned, saturating: negative inputs give 0, values at or above
2^32 give `0xFFFFFFFF`).

- `desc+0x18 == 0`: `sub+0x08 = 0`, `sub+0x0C = 0`, no third allocation.
- Otherwise: `allocate(allocator, size, 0x80)`; when `desc+0x10 != 0` and
  `size != 0`, exactly `size` zero bytes are written with a byte post-increment
  loop; then `sub+0x08 = size` unconditionally and `sub+0x0C` is the
  self-relative link or 0 for a null buffer.

## Differential evidence
`tools/test_leaf_001204a4.py` compiles `src/engine/leaf_batch41_c.cpp`,
extracts this body, resolves its single `R_ARM_CALL` to a deterministic
`AsdMem_Zero` stub at `0x002C4B30`, installs two allocator slot targets
(`0x002E0000`, `0x002E0020`) in the fixture vtable, and runs the original bytes
and the candidate in separate Unicorn ARM machines with identical fixtures. The
machine is set to `UC_CPU_ARM_11MPCORE` with `CPACR = 0x00F00000` and
`FPEXC = 0x40000000`, which the VFP conversion requires.

Compared: return `r0`, continuation PC, final SP, callee-saved `r4-r11`, the
ordered event log (each allocation's call index, context, requested size and
flags; `AsdMem_Zero` pointer/size; the primary vs secondary slot target), and
the complete descriptor, both context pages, primary/secondary vtable, record,
alternate record, sub-record, alternate sub-record, payload and alternate
payload pages. Every write must stay inside a fixture page or the private
stack. The helpers take no stack arguments.

Coverage (41 cases):
- payload flag 0, 1, 0x80, 0xFF; fill flag 0, 1, 0x80, 0xFF; sizes
  0/4/8/24/80 bytes;
- signed factors `-1`, `0x80000000`, `0`, `1`, `0x7FFFFFFF`, `0x20000000`,
  `0x1FFFFFFF`, `0x0FFFFFFF`, `0x40000000`, `0x10000000`; the request sizes

## Unresolved / limits
- The allocator vtable slot `+0x08` target is dynamic and not resolved. The
  test installs deterministic stubs that log `(call_index, context, size,
  flags)` and return fixture pointers; real heap placement, alignment and the
  meaning of the second word (`4` / `0x80`) were not verified. The slot is
  called with the same `r0 = allocator` for all three requests.
- `0x002C4B30` is modeled as a literal zero fill of `size` bytes, matching its
  decoded body; its exact `AsdMem` bookkeeping was not reconstructed here.
- Null allocation results make the original store through address 0. On real
  hardware that faults; the candidate reproduces the first null access, but the
  compiler may reorder independent stores, so the faulting instruction/offset
  can differ (observed: the null-record case faults at offset `0x08` instead of
  `0x00`). The differential test therefore compares fault occurrence and the
  pre-fault call log/fixture state for those cases, not the fault address.
  Behaviour after a null write is undefined in both bodies.
- When `desc+0x18 == 0` the original still executes the two `vcvt.f32.s32`, two
  `vmul.f32` and `vcvt.u32.f32` operations; clang sinks that dead computation
  into the taken branch. The only difference is the cumulative exception flags
  in FPSCR for out-of-range factors; there is no memory, register or call-log
  difference.
- The descriptor's meaning is inferred from the single caller
  (`engine_func_0010bb08`) and from the arithmetic (four bytes per unit of
  `size_x * size_y`). The record is returned and published as
  `[0x00464AF0 + 0x80]`; its later consumers were not traced, and the three
  magic words are recorded as data, not identified formats.
- No emulator run, real allocation-failure injection or whole-game integration
  was performed.
