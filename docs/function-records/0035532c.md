# Function Record: camp_func_0035532c (0x0035532C)

## Summary
- **Address:** `0x0035532C`
- **Size:** 640 bytes (original span `[0x0035532C, 0x003555AC)`; instructions end
  at `0x0035559C`, followed by the 12-byte literal pool `0x004209F8`,
  `0x0044E650`, `0x6E6F6369` ("icon")).
- **File:** `src/engine/leaf_batch45_a.cpp`
- **Role:** Submits command 3 to the service session at `0x0044E650+0x10`,
  stores the session handle and the two response words in the 16-byte request
  slot (vtable `0x004209F8`), asks that slot's virtual method `0x0035654C` to
  build an operation object (vtable `0x00420998`) from the descriptor
  `{2, &{2, "icon", 0}, 0x0C}`, starts the operation with its vtable slot 0,
  releases it with slot `0x2C`, then releases the request slot and returns
  either the first negative status or zero.
- **Status:** Semantically equivalent C++ (`non_matching`). The compiled body is
  444 bytes versus the 640-byte original. The original emits four separate
  inlined copies of the request-slot destructor and a dead second copy in each
  tail; the reconstruction emits two destructor forms (reload after the getter
  on failure tails, reused pair on the start-success tail) with one copy each.
  The observed ABI, call order, argument values, branches, signed tests and
  return values are identical. The ledger row is classified `non_matching` with
  this record.

## Contract and Behavior

### Signature and ABI
```c
extern "C" s32 camp_func_0035532c(u32 argument); // r0
```
- Only `r0` is read (`mov r5,r0` at `0x355334`); `r1-r3` are ignored.
- The original saves `r4-r7` plus `lr` and allocates a 0x5C-byte stack frame.
  The compiled C++ keeps the same callee-saved contract and restores `sp` on
  every return.
- The return value is `0` on full success, otherwise the first negative status
  seen from `0x002ADB84`, `0x0035654C` or the operation's vtable slot 0.
- The routine is synchronous and has no loops; all four control-flow joins are
  the error/return paths described below.

### Request slot layout (`sp+0x08` in the original)
The 16-byte slot placed at `sp+0x08` is the object whose vtable is
`0x004209F8`; `0x003566F8` is its destructor (also inlined here).

| Offset | Width | Meaning (from ARM evidence) |
|---|---|---|
| `+0x00` | `u32` | vtable pointer `0x004209F8` (stored, never dereferenced here) |
| `+0x04` | `u32` | session handle; cleared at entry and on destruction |
| `+0x08` | `u32` | first `0x002ADB84` response word |
| `+0x0C` | `u32` | second `0x002ADB84` response word |

`0x00239F84(slot)` returns `[slot+4]` and lazily creates it when it is zero.
`0x002ADB54(&handle, r1, response0, response1)` sends the release command; its
`r1` is not read by the callee.

### Control flow (original PCs)
1. `0x35532C..0x35535C`: prologue; store vtable `0x004209F8` and handle `0` in
   the slot; build `{sp+0x2C, 1}` and store `1` at `sp+0x28`.
2. `0x355360..0x35537C`: read the session handle from `0x0044E650+0x10`, store
   it in the `sp+0x4C` temporary, pass the submit block as the two architected
   stack words, and call `0x002ADB84(&handle, sp+0x20, 3, 1, sp+0x2C, 1)`.
3. `0x355380..0x355384`: `lsrs r1,r0,#31; beq 0x3553D4`; a negative status
   takes the failure tail.
4. `0x355388..0x3553C0` (submit failure): store the vtable again; if
   `response0|response1` is non-zero, call `0x00239F84(slot)` and
   `0x002ADB54(&result, -, response0, response1)` using the **reloaded** pair,
   then clear both words. Clear the handle at `0x3553C4` and return the submit
   status (`r5`).
5. `0x3553D4..0x355408` (submit success): reload `0x0044E650+0x10` into
   `slot+4`; copy `sp+0x20`/`sp+0x24` into `slot+8`/`slot+0xC`; build the icon
   block and the descriptor.
6. `0x35540C..0x355418`: call `0x0035654C(slot, &sp+0x18, &descriptor, 1)`.
7. `0x35541C..0x355424`: negative status -> create-failure tail.
8. `0x355428..0x355464` (create failure): destructor with the **reloaded**
   pair, then the common clear and return of the create status.
9. `0x355468..0x35548C`: build the architected arguments `(argument, 0x36C0)`,
   load `operation = [sp+0x18]`, fetch `operation->vtable[0]` and call
   `f(operation, sp+0x58, 0, 0, argument, 0x36C0)`.
10. `0x355490..0x3554A4`: save the result in `r5`, fetch
    `operation->vtable[0x2C]`, and test the result sign.
11. `0x3554A8..0x355514` (start failure): call `operation->vtable[0x2C]`,
    destructor with the **reloaded** pair, then return the start status.
12. `0x355518..0x355590` (start success): call `operation->vtable[0x2C]`,
    destructor with the pair **cached before** `0x00239F84`, clear the handle
    and return 0.
13. `0x355594..0x35559C`: restore `sp` and pop `{r4-r7,pc}`.

The original contains a second destructor copy in each tail
(`0x3554DC..0x355514`, `0x355554..0x355590`, `0x35543C..0x355464`); the first
copy always clears both response words, so the second copy's test is always
zero and the copy is dead. The reconstruction omits those copies.

### Unresolved or unchecked behavior
- The submit helper's IPC/TLS protocol and SVC statuses, `0x0035654C`'s
  allocation path, `0x00239F84`'s lazy creation, and the two operation vtable
  methods are treated as external contracts and stubbed in the test.
- `0x002ADB54`'s `r1` is dead in the callee; the C++ passes an explicit zero.
  The test omits it from the comparison.
- The original leaves `slot+8`/`slot+0xC` undefined when `0x002ADB84` fails and
  still ORs them in the inline destructor. That read is stack-layout dependent
  (a zero-filled stack reads zero; any other fill changes whether the release
  command runs). The reconstruction zero-initializes the slot, and every test
  case runs on a zero-filled stack. This is the only known divergence from the
  literal original and it is a read of uninitialized memory in the original.
- The original's start-success destructor reuses the response pair loaded
  before `0x00239F84`, while the three failure tails reload it after the call.
  The reconstruction keeps both forms; the test exercises the difference with
  a getter stub that mutates the slot.
- `0x0035654C` returning a non-negative status but a null operation pointer
  would fault in both the original and the reconstruction. The test stubs
  always install a valid object on success.
- Return values of the two operation vtable methods other than their sign are
  not used by this routine (start's value is only sign-tested; release's is
  ignored).

## Differential Verification
`python tools/test_leaf_0035532c.py` compiles `src/engine/leaf_batch45_a.cpp`,
relocates the candidate's four direct calls, and runs the pinned 640-byte
original against the candidate in separate Unicorn ARM machines with identical
fixtures.

Compared: return `r0`, continuation PC, final SP, callee-saved `r4-r11`, the
ordered call log (every used register argument, the two stack words of
`0x002ADB84` and of vtable slot 0, the submit block `{self, 1}`, the descriptor,
the icon block, the full request-slot words, the getter result, and the
operation pointer for both indirect calls), the full 0x20000-byte service page,
the full 0x10000-byte fake operation page, and every emulated write outside the
private stack and those fixture pages.

Coverage (41 cases):
- submit statuses `0xFFFFFFFF`, `0x80000000`, `0xFFFFFF00`, `0x80000001`, with
  and without a zero session handle;
- create failures with response pairs `0/0`, `1/2`, `0x80000000/0`,
  `0/0x80000000`, `0/0xFFFFFFFF`, `0xFFFFFFFF/0`, `0xFFFFFFFF/0xFFFFFFFF`,
  `0x7FFFFFFF/0x80000000`, `0xFFFFFFFF/0x7FFFFFFF`;
- start statuses `0`, `1`, `0x7FFFFFFF`, `0x40000000` (return 0) and
  `0x80000000`, `0xFFFFFFFF`, `0xC0000000`, `0x80000001`, `0xDEADBEEF`
  (return the status unchanged);
- getter returning a sentinel different from the slot handle, and a getter that
  mutates the response words on the success, create-failure and start-failure
  tails (zero, asymmetric and signed values);
- a session handle changed by the submit stub between the two loads, on the
  success, create-failure and start-failure tails;
- argument/handle boundaries `0/0`, `0xFFFFFFFF/0xFFFFFFFF`,
  `0x80000000/0x80000000`, `0x7FFFFFFF/0x7FFFFFFF`, `0x0000FFFF/0x00010000`;
- the operation slot-0 output pointer written by the stub and the release
  helper's ignored negative return.

Negative controls mutate the submit command, argument and buffer count, the
descriptor type and size, the icon tag, the create flag, the start stack word,
the first response-word assignment, the second global handle load, the success
return value, the success destructor form, the operation release call, and the
second release-command word. Each mutant is detected by at least one case.

Limits: this is an isolated function-level differential test. It does not prove
whole-game runtime equivalence, the helper bodies, the IPC protocol, the
operation object's lifetime, or the uninitialized response-word read on a dirty
stack. No emulator run was performed.
