# Function Record: ui_func_0030f760 (0x0030F760)

## Summary
- **Address:** `0x0030F760`
- **Size:** 420 bytes (original span `[0x0030F760, 0x0030F904)`; 100 ARM
  instructions through the unconditional `pop` at `0x0030F8EC` plus the five
  literal words at `0x0030F8F0..0x0030F900`)
- **File:** `src/engine/leaf_batch41_c.cpp`
- **Role:** Draws the `0x004C2424` element list (28-byte bounding-box/geometry
  records) as lifted four-corner quads. For every record `i` it submits
  `func_0029705c` with the table color `table[i % 12] | 0x70` and the record's
  four box floats at `y = incoming_s0 + 100.0f`. A viewport command is pushed on
  and popped from the render stack around the loop.
- **Status:** Semantically equivalent C++ (`non_matching`). The compiled body is
  468 bytes versus the 420-byte original. No byte-identity claim is made.

## Contract and Behavior

### Signature and ABI
```c
extern "C" u32 ui_func_0030f760(f32 vertical_offset);
```
- The only live incoming register is `s0` (the vertical offset). `r0..r3` are
  overwritten before they are read.
- Prologue: `push {r4, r5, r6, r7, r8, sb, lr}`, `vpush {d8}`,
  `sub sp, sp, #0x34`. `d8` (`s16`) holds the lifted draw height across every
  helper call. Every exit restores `sp`, `d8` and the callee-saved registers.
- `r0` on return is: `0` on the early exit (`count == 0`), otherwise the popped
  stack value, or the pop flush-callback result when that callback runs.

### Global layout (offsets only, as evidenced by the ARM)
- `0x00404A44..0x00404A70`: twelve contiguous color/format words, loaded by
  `ldm` at `0x004049B4 + 0x90` (eight words), `+0xB0` (three words) and
  `ldr [r0, #0xBC]` (one word). They are copied to `sp+0x00..0x2C` before any
  helper call, and the loop reads the copy. This is the second copy of the
  twelve-entry table that `0x002F4804` reads at `0x004049B4`; the pinned image
  holds identical values in both.
- `0x004C3224` (`0x004C2424 + 0xE00`): signed 32-bit record count. It is
  re-read before the loop and again after every draw call.
- `0x004C2424 + i*0x1C`: 28-byte records. This routine reads the four floats at
  `+0x00`, `+0x08`, `+0x0C` and `+0x14`; `func_002d4ef4` documents the same
  stride and uses those fields as a bounding box.
- `0x0044EA00`: render-register block pointer. The stack node is at
  `+0x124C` (`count` at `+0x00`, flat word slots from `+0x08`, `dirty` at
  `+0x18`, flush callback at `+0x1C`). The global is read three times: once
  before the viewport helper (the push base), once for the render-mode call and
  once for the pop.

### Control flow
1. Copy the twelve words at `0x00404A44` to the stack.
2. `count = *(s32*)0x004C3224`. Exactly zero returns `0` immediately.
3. `base = *0x0044EA00`; `pushed = ui_func_002c5f7c(5, 1)`.
4. `node = base + 0x124C`; `previous = slots[node->count]`;
   `node->count += 1`; `slots[node->count] = pushed`.
   If `node->dirty != 0 || previous != pushed`, call `node->flush_cb(pushed)`
   and clear `node->dirty`. The push base is captured before step 3's helper,
   so a helper that changes `0x0044EA00` does not move this push.
5. `ui_func_002c1d3c(*0x0044EA00, 0)`.
6. `draw_y = vertical_offset + 100.0f` and, for every `i` while
   `i < *(s32*)0x004C3224` (signed bound, re-read every iteration):
   `func_0029705c(color, color, color, color,` with
   `color = table[i % 12] | 0x70` and the twelve floats
   `(rec+0x00, draw_y, rec+0x08), (rec+0x00, draw_y, rec+0x14),
   (rec+0x0C, draw_y, rec+0x08), (rec+0x0C, draw_y, rec+0x14)`.
7. Re-read `*0x0044EA00`, address its node, and pop: `previous = slots[count]`,
   `count -= 1`, `new_top = slots[count-1]`.
   If `node->dirty != 0 || previous != new_top`, call
   `node->flush_cb(new_top)`, clear `node->dirty` and return the callback
   result. Otherwise return `new_top`.

The slot array is addressed flat (`node + 8 + count*4`) with no bounds check;
the reconstruction indexes past the four visible slots exactly like the ARM
(the differential suite covers `count == 3`, whose slot write overlaps the
`dirty` byte).

### Unresolved targets and domain limits
- The three direct helpers and the flush callback are deterministic stubs in the
  differential suite. Their real bodies (viewport command construction, render
  mode selection, draw submission, dirty-state flush) are not executed here;
  only caller-visible arguments, ordering, return registers and memory effects
  are validated.
- The flush callback address comes from game state at runtime and is not
  resolved statically. The reconstruction preserves the unchecked indirect call
  (a null callback faults in both).
- The record array and count are game data; the reconstruction reads them
  through their absolute addresses and performs no bounds check, matching the
  original. `count > 128` would read the count word itself as record data, which
  the original also does; the verified domain stops at the 128-record boundary.
- No emulator/runtime whole-game test was run for this leaf. The evidence is the
  offline Unicorn differential suite.
