# Function Record: script_vm_func_001fc004 (0x001FC004)

## Summary
- **Address:** `0x001FC004`
- **Size:** 416 bytes (original span `[0x001FC004, 0x001FC1A4)`, including the
  four-word literal pool at `0x001FC194`)
- **File:** `src/engine/leaf_batch28_a.cpp`
- **Role:** Script/VM task-table selection. When the table header's `u16` kind
  word is `0x65`, it measures up to 32 task records against the active view
  position, selects the three nearest ready records, copies their position and
  payload words into three result records, and invalidates the remaining
  measured records.
- **Status:** Semantically equivalent readable C++ (`non_matching`). The
  compiled body is 748 B versus the 416 B original because the compiler fully
  unrolls the three-iteration selection loop and keeps the 32-entry scans as
  explicit loops; the original keeps the outer loop rolled and uses the
  function's literal pool. The differential suite in
  `tools/test_leaf_001fc004.py` passes 30/30 cases plus 7 negative controls.

### Table and record layout
The table has a `0x58`-byte header followed by 32 records of 76 bytes:
`record(index) = table + 0x58 + 76*index`. `script_vm_func_002eb0f4` walks the
same records (its +0x58 active byte and +0x5C word are the same gate fields).

Observed record fields:
| Offset | Width | Use |
| --- | --- | --- |
| `+0x00` | `u8` | active flag |
| `+0x04` | `u32` | state word; must be non-zero for selection |
| `+0x0C` | 3 x `f32` | position passed to the distance helper |
| `+0x18` | `u32` | payload word 0, copied verbatim to a result record |
| `+0x1C` | `u32` | payload word 1, copied verbatim to a result record |
| `+0x3C` | `u8` | ready flag |
| `+0x40` | `u32` | reset word; set to `0xFFFFFFFF` when measured but not selected |
| `+0x44` | `f32` | distance written by pass 1 |
| `+0x48` | `u32` | marker: `999` while pending, then selected slot `0..2` |

Result records live at `table + 0x9E4 + 76*slot` and receive:
`+0x00/+0x04/+0x08` = selected record position words, `+0x0C` = payload 0,
`+0x10` = payload 1, `+0x14` (`u8`) = 1.

### Control flow and calls
1. **Header gate.** Load `*(u16*)(table + 4)`; unless it equals `0x65`, return
   without touching anything else.
2. **Pass 1 (32 iterations).** For each record whose active byte and ready byte
   are both non-zero, call
   `engine_func_00287d54(view.x, view.y, view.z, record.x, record.y, record.z)`
   (0x00287D54, `sqrt((a-b)^2)` over three floats), store the returned `f32` at
   record `+0x44`, and set record `+0x48` to `999`. The state word is *not*
   consulted in this pass; the table and view pointers are re-read through
   their global slots.
3. **Pass 2 (3 slots).** For each slot, scan all 32 records in index order and
   choose the first record with active != 0, state != 0, ready != 0,
   marker == 999 and `distance < best`, where `best` starts at `90000.0f`
   (literal `0x47AFC800`). The comparison is strict and unordered comparisons
   are false, so ties keep the lower index and NaN distances are never
   selected. The selected record's marker and reset words become the slot
   number, and its position/payload are copied to the slot's result record.
   When no record qualifies, `best_index` remains `-1`; the original then
   addresses `table + 0x58 - 76 = table + 0x0C`, i.e. the tail of the table
   header, and stores the slot number at `table+0x4C`/`table+0x54` while
   copying header words into the result record. This path is reproduced
   exactly.
4. **Pass 3 (32 iterations).** Records with active != 0, state != 0,
   ready != 0, marker == 999 and reset != `0xFFFFFFFF` get reset
   `= 0xFFFFFFFF`. Selected records are skipped because their marker is no
   longer `999`.

The VFP ordering is preserved: view coordinates are loaded into `s0..s2`,
record coordinates into `s3..s5`, the helper result is stored as a single
`f32`, and the selection comparison is a single-precision `<`.

## Limits
- The helper was stubbed rather than run from the pinned image; its own
  contract is already covered by separate function records. No emulator or
  canonical full-game build was run for this task.
- Consumers of the table header, the three result records, and the `+0x18` /
  `+0x1C` payload words were not traced, so their higher-level meaning is not
  claimed.
- The original's residual caller-saved `r0`/`lr` are not defined results and
  are not compared; `pc`, `sp`, callee-saved registers and all observable
  memory are.
