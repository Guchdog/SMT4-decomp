# Function Record: script_vm_func_00263ee4 (0x00263ee4)

## Summary
- **Address:** `0x00263ee4`
- **Size:** 408 bytes (original span `[0x00263ee4, 0x0026407c)`): 98 ARM
  instructions through the unconditional `pop` at `0x00264068`, plus the
  four-word literal pool at `0x0026406c`.
- **File:** `src/engine/leaf_batch41_c.cpp`
- **Classification:** `non_matching` with semantic evidence. The compiled body
  is 392 bytes versus the 408-byte original. Register allocation, the literal
  pool (two words versus four), non-aliasing store scheduling and two merged
  halfword store pairs differ; final memory is identical in the differential
  suite.
- **Role:** Builds one script-effect work record at `0x004afd64` and registers
  its `0x004a1264` slot entry. It copies the caller's description into the
  record, asks `0x0021c598` for the slot index, asks `0x002526fc` for the
  per-slot allocation handle, writes the slot fields, and advances the global
  count at `0x00447a2c`. The sibling `0x0024f460` does the same work-record
  setup with a six-float ABI; this entry point takes seven.

- `r0 = id`, `r1 = handle`, `r2 = kind` (pointer value, only stored),
  `r3 = type`.
- Fifteen stack words follow, at the entry `r13 + 4*n`. Stack word 14 sits at
  `r13 + 0x38` and is read at `0x002640dc`.
- Seven VFP arguments arrive in `s0..s6` (hard-float ABI). `s7` and above are
  not read.
- The prologue spills `r0-r3`, `d0-d3` and `d8-d9`. `r0/r1/r2` are re-read from
  the register save area at `0x00263fac..0x00263fd8`; `r3` is used directly.
  The epilogue restores `d8/d9`, discards the spilled `d0-d3` and argument
  registers, and returns through `pop {r4,r5,r6,r7,r8,sb,sl,fp,ip,pc}`.
- **Returns:** the `s32` result of `0x0021c598` (`r7`), zero-extended into
  `r0`. The known callers ignore it.

### Global count
`*(u32*)0x00447a2c` is read once at `0x00263f2c` and used for both the work
record and the previous slot. After both calls it is **re-read** at
`0x00264050`, incremented modulo 2^32 and stored back at `0x00264058`. A helper
that rewrites the count therefore affects the final value but not the indices
already computed.

### Code-generation note
Clang merges the original's `strh` pair at `+0x15c/+0x15e` into one 32-bit
store (`0xffff0000`) and the pair at `+0x160/+0x162` into one zero 32-bit store.
It also schedules non-aliasing stores (including the final count store) in a
different order and folds `0x004afd64` as `0x004a1264 + 0xeb00`, which is why
the literal pool shrinks from four words to two. None of this changes the final
memory: all affected addresses are distinct, and the slot/work bases are not
congruent to the count address modulo their strides. No `volatile` was added to
force instruction-level store order.

## Domain Limits
- Both direct callees are stubbed. The real `0x0021c598` body fills fields of
  the work record (including the `+0x5c` subobject) and the real `0x002526fc`
  body writes a 404-byte slot table behind `0x004a1264`; those effects are not
  modelled. Only the call arguments and the consumed return values are
  verified.
- The global-count rewrite cases are synthetic helper behavior; no game
  helper was observed writing `0x00447a2c`.
- The work/slot object types, the full extents of the two global arrays, and
  the engine-level meaning of every field are not established. Field names are
  offset-based on purpose.
- At the first call the original still has `r3 = type`; the reconstruction uses
  the established three-argument declaration and does not reproduce that dead
  register value. The callee overwrites `r1-r3` before reading them.
- Field-initialization order is preserved in source; the compiler may schedule
  non-aliasing stores differently (see the code-generation note).
- No caller-composition, game-engine or whole-game runtime equivalence is
  claimed. No canonical full build or emulator run was performed.
