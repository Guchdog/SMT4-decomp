# Function Record: ui_func_002f4804 (0x002f4804)

## Summary
- **Address:** `0x002f4804`
- **Size:** 416 bytes (original span `[0x002f4804, 0x002f49a4)`): 99 ARM
  instructions `0x002f4804..0x002f498c` plus the five-word literal pool at
  `0x002f4990..0x002f49a3`.
- **File:** `src/engine/leaf_batch41_c.cpp`
- **Role:** Draws the runtime flow-script effect records maintained at
  `0x004be698` (counter at `0x004bf898`).  When the record count is non-zero it
  pushes a viewport command onto the render stack at `*0x0044ea00 + 0x124c`,
  selects render mode 0, submits one four-corner element per record through
  `func_0029705c`, then pops the viewport stack node.
- **Classification:** `non_matching` with semantic evidence.  The compiled body
  is 396 bytes versus the 396 instruction bytes + 20 literal bytes of the
  original: the twelve-word color table is referenced directly from `.rodata`
  instead of copied to the stack, and the prologue/epilogue and the modulo-12
  sequence differ, but the recorded draws, render-stack traffic and returned
  scratch value are the same.

### Viewport-stack push and pop
The node layout at `base + 0x124c` is `{u32 depth; u32 pad; u32 slots[...];
u8 dirty at +0x18; u32 flush_cb at +0x1c}`, matching the push/pop helpers in
`src/engine/block_batch.cpp`:

1. `previous = slots[depth]`
2. `depth = depth + 1`
3. `slots[depth] = push_value`
4. if `dirty != 0 || previous != push_value`, call `flush_cb(push_value)` and
   clear `dirty`.

The pop is the mirror image: read `previous = slots[depth]`, decrement `depth`,
read `new_top = slots[depth]`, and apply the same callback rule with `new_top`.

The push value is the result of `0x002C5F7C(5, 1)`.  That leaf builds
`(r0 == 1 ? 0 : 1) | r0 << 4 | (r1 != 0 ? 0x1000 : 0) | 0xF00`, i.e. `0x1F51`.

### Draw submission
For each record `i` while `i < s32[0x004bf898]`:
- color word `= kColorTable[i % 12] | 0x70`, passed in `r0..r3`;
- `s0..s11` carry four vec3 corners:
  - `(rec+0x00, s16, rec+0x08)`
  - `(rec+0x00, s16, rec+0x14)`
  - `(rec+0x0C, s16, rec+0x08)`
  - `(rec+0x0C, s16, rec+0x14)`
  where `s16 = incoming s0 + 100.0f` (`0x42C80000`).
- `0x0029705C` consumes `r0..r3` and `s0..s11`; it saves them into `s16..s27`
  (`vmov.f32` plus `vmov.f64 d13, d5` for `s10/s11`) and then calls
  `0x002B0208` four times with each vec3 and 100.0f as the remaining
  components.  The reconstruction forwards the same sixteen values.

### Color table (0x004049B4, 48 bytes)
`FF000000 00FF0000 FFFF0000 0000FF00 FF00FF00 00FFFF00 80000000 00800000
FF800000 00008000 FF008000 00FF8000` (little-endian words as stored).  Each
entry is OR-ed with `0x70` before use.

### Call order
1. `ui_func_002c5f7c(5, 1)` — after capturing the render base for the push node.
2. `flush_cb(pushed)` — only when the push comparison fires.
3. `ui_func_002c1d3c(*0x0044ea00, 0)` — note that the base is re-read after the
   push helper/callback, not reused.
4. `func_0029705c(...)` once per live record, with the counter re-read between
   calls.
5. `flush_cb(new_top)` — only when the pop comparison fires.
6. The render base is read a third time for the pop node.

## Domain Limits
- The three direct calls are stubbed deterministically.  `0x002C5F7C` is
  reproduced faithfully (pure bit building); `0x002C1D3C` and `0x0029705C` are
  replaced by argument-dependent stubs, so their internal render/matrix work and
  the PICA command stream they eventually build are not exercised here.  The
  reconstruction passes exactly the registers the original passes, including
  the twelve single-precision corner values.
- The flush callback target is fixture-controlled.  Its real signature is not
  recovered beyond "called with the pushed/new-top word in r0"; the original
  uses the callback's `r0` as the routine's final scratch value on the pop
  path.  The reconstruction models the callback as `u32 (*)(u32)`.
- The render-stack node layout is only backed by the byte offsets above; the
  ownership, capacity and the meaning of the pushed command word are not
  recovered.  The original performs no bounds check: depth 3 overwrites the
  dirty byte, and depth 4 would store `0x1F51` over the callback pointer and
  crash on the following flush.  Depth 3 is covered; depth 4 is not (the
  original faults).
- Neither the render base at `0x0044EA00` nor the flush callback is checked for
  null; both bodies fault identically in that situation and no case exercises
  it.
- The original copies the 48-byte color table to its stack before testing the
  record count; the reconstruction reads the immutable `.rodata` copy only when
  the loop runs.  The stack copy is private and the table is never written, so
  no architectural state differs; only a faulting 0x004049B4 mapping when the
  count is zero could distinguish them (the game always maps that page).
- The original converts `s16 + 100.0f` with a single VFP `vadd.f32`; the
  candidate does the same at `-O2`, and the NaN fixture confirms the propagated
  and quieted payload matches.  FPSCR exception-flag side effects of the
  addition and of the draw helper are not modelled.
- The record counter is signed in the gate (`== 0`) and in both loop tests
  (`ble`, `bgt`); negative counts therefore push/pop without drawing.  The
  reconstruction keeps that behaviour.  A counter above the 144-record capacity
  would read beyond the record array; no case exercises that because both
  bodies would read out-of-range memory.
- The candidate's prologue differs (it also saves `fp`, and its call-time SP is
  0x30 bytes below the entry SP instead of 0x58).  None of the three helpers
  takes a stack argument, so this is not observable; the runner excludes the
  private stack and compares SP after epilogue.
- Runtime integration (a live render stack and the consumer of the submitted
  draw elements) was not exercised; this record covers offline differential
  equivalence only.
