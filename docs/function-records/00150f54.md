# Function Record: func_00150f54 (0x00150f54)

## Summary
- **Address:** `0x00150f54`
- **Size:** 656 bytes (original span `[0x00150f54, 0x001511e4)`; 164 ARM
  instructions through `0x001511d8` plus the two-word literal pool at
  `0x001511dc` holding `0.0f` and `1.0f`)
- **File:** `src/engine/leaf_batch45_a.cpp`
- **Role:** Advances the two animation/blend slots of the global UI window
  element object at `0x004EA168` and publishes the resulting blend factors.
  Each slot owns two signed saturating counters, two float ranges, and two
  optional type-2 elements. The function also advances the object's two
  top-level counters and ORs a notification flag into the object's notification
  list when either top-level counter moves.
- **Status:** Semantically equivalent C++ (`non_matching`). The compiled body is
  616 bytes versus the 656-byte original. A differential Unicorn harness runs
  the pinned original against the compiled candidate; the ledger row is
  classified `non_matching` and carries this record.

## Contract and Behavior

### Signature and ABI
```c
extern "C" void func_00150f54(void* object);   // r0 = object
```
- Only `r0` is read. `r1-r3` are never read; there are no stack arguments and
  no stack locals.
- The original ends with `pop {r4,r5,r6,r7,r8,sb,sl,lr}` followed by a tail
  branch to `0x002BCE38` (`b`, not `bl`); it therefore returns the tail callee's
  `r0`. The tail callee is a thunk that overwrites `r0` with the fixed global
  `0x004E6F14` and only consumes `s0`, so the incoming `r0` value is not part of
  the contract. The C++ reconstruction declares the function and the tail callee
  `void` and calls the callee in tail position.
- Preserves `r4-r8`, `sb`, `sl` and the callee-saved VFP register `d8` (the
  original uses `s16`/`s17`). The compiled candidate saves `{d8,d9}` and uses
  `s16`/`s18` as its two constants; both bodies preserve `s16-s19` and restore
  the entry `sp`.

### Caller
- One direct call exists in `code.bin`: `bl #0x150f54` at `0x0014c4dc` inside
  `engine_func_0014c3e0` (480 B, `src/engine/leaf_batch44_a.cpp`). The reference
  is `ldr r0, [pc, #0xdc]` at `0x0014c4d8`, loading the literal `0x004EA168`

### Control flow
For each slot `i = 0, 1` (`slot = object + 16*i`):
1. Read `first = [slot+0x50]`; if `first < [slot+0x4C]` (signed), store
   `first+1` to `[slot+0x50]` and mark `first_advanced`.
2. Read `second = [slot+0x30]`; if `second < [slot+0x2C]` (signed), store
   `second+1` and re-read `[slot+0x2C]`. If the new value is `>=` that fresh
   limit, call `0x002B4EB8(object, i & 0xFF)`.
3. Continue to the blend only when the second counter advanced **or** the first
   counter advanced. If neither advanced, skip the blend call but still run the
   element cleanup loop.
4. First blend value (`0x150FD0..0x151034`):
   - if `[slot+0x50] >= [slot+0x4C]` (signed), use `[slot+0x48]`;
   - else `start + ((end - start) * (f32)counter) / (f32)limit`, where
     `start = [slot+0x44]`, `end = [slot+0x48]`;
   - clamp: `> 1.0f -> 1.0f`; then keep values that are `>= 0.0f` **or
     unordered (NaN)**, otherwise `0.0f`. Negative zero is kept.
5. Second blend value (`0x151034..0x15109C`): same interpolation over
   `[slot+0x24]/[slot+0x28]` driven by `[slot+0x30]/[slot+0x2C]`; clamp is
   `> 1.0f -> 1.0f` and then `< 0.0f -> 0.0f`, so NaN passes through unchanged.
6. Call `0x002A3418((s8)i, second_clamped * (first_clamped * 1.0f))`. The
   original multiplies the first clamp by the literal `1.0f` before the final
   product; the compiler folds that no-op multiply in the candidate.
7. For each element `j = 0, 1` at `slot + 8*j + 0x2A0`: if the pointer is
   non-null and the byte at `+4` equals `2`, call `0x00153160` for `j == 0` or
   `0x001531AC` for `j == 1`. When the callee returns `0`, store a 32-bit zero
   at the element pointer and a byte zero at `+4`. The two stores happen
   word-then-byte in the original and byte-then-word in the candidate; the final
   memory is identical.

After the slot loop:
8. If `[object+0x0C] > [object+0x10]` (signed), increment `[object+0x10]` and
   call `0x001579D8(0x002BB270(), 0x40)`.
9. If `[object+0x20] < [object+0x1C]` (signed), increment `[object+0x20]` and
   call `0x001579D8(0x002BB270(), 0x40)`.
10. Final blend: if `[object+0x20] >= [object+0x1C]` (signed) use
    `[object+0x18]`, otherwise `start + ((end - start) * (f32)counter) /
    (f32)limit` with `start = [object+0x14]`, `end = [object+0x18]`. The result
    is multiplied by `1.0f` (folded in the candidate) and clamped with the same
    NaN-preserving rule as step 4, then passed to `0x002BCE38`.

Every increment is provably overflow-free: the increment is only reached when
the counter is strictly below a `s32` limit, so the maximum source value is
`INT_MAX-1`.

## Limits and Unresolved Items
- The helper bodies are stubbed deterministically; the harness verifies the
  arguments and the caller-side use of their results, not the real callees'
  internal effects. `0x00153160`, `0x001531AC`, `0x002BB270`, `0x001579D8`,
  `0x002B4EB8`, `0x002A3418` and `0x002BCE38` remain byte-preserved elsewhere
  and are not re-implemented here.
- Field names/semantics beyond the observed arithmetic (animation vs. fade,
  which UI quantity each range controls) are not established by the ARM
  evidence.
- The two `1.0f` multiplies are folded by the compiler; float results were
  verified bit-for-bit in Unicorn, including NaN endpoints, but CPU-level NaN
  payload propagation is hardware-dependent. This is outside the verified
  domain.
- No emulator or whole-game runtime test was performed; this record covers the
  offline differential harness only.
