# Function Record: engine_func_0037fd94 (0x0037fd94)

- **Size:** 600 bytes (original span `[0x0037fd94, 0x0037ffec)`; the body ends

## Contract and Behavior

### Signature and ABI
```c
extern "C" u32 engine_func_0037fd94(u8* self, const u8* desc, u32 span);
```
- `self = r0`, `desc = r1`, `span = r2`; `r3` is never read.
- The original pushes `{r4-r8, sb, sl, fp, lr}` and reserves `0x4c` bytes, so the
  final `sp` equals the entry value. There are no incoming stack arguments.
- Every exit path leaves `r0 = count`, the signed loop bound read once from
  `[*(u32*)(self + 0x134) + 8]` before the loop. The C++ returns that value; the
  caller (`0x0037ffec`) ignores it.
- `self + 0x134` is re-read at each use rather than cached, matching the original
  reloads at `0x37fdf8`, `0x37fee4`, `0x37ff3c` and `0x37ffa0`.

### Receiver layout (`self`)
```text
+0x00            first output record  (0x30 bytes)
+0x18            second half of record 0 (the paired record)
+0x60 + 6*i      u16 anchor[3] for entry i
+0x6C + 6*i      u16 tail[3] for entry i
+0x78  u32       copy of desc[+0x0C]
+0x7C  u8        copy of desc[+0x01]
+0x134 u32       slot-list pointer
```
The records stride 0x30 bytes; entry `i` occupies `self + 0x30*i` and its paired
record `self + 0x30*i + 0x18`. Because the anchor/tail tables start at 0x60, a
count above 2 makes later records overwrite the tables; the original does this
too and the code is reproduced without "fixing" it.

### Descriptor layout (`desc`)
```text
+0x00  u8   mode byte       (only value 3 takes the layout path)
+0x01  u8   flag byte       (non-zero emits the paired record)
+0x0C  u32  scaler input    (also copied to self+0x78)
+0x10  u32  span word       (base of both record time deltas)
+0x14  u32  per-entry base pointer value (at 0x30*i + 0x14)
+0x18  ...  0x20-byte layout blob (at 0x30*i + 0x18)
+0x3E  u16  tail[0]         (at 0x30*i + 0x3E, i.e. past the 0x30-byte stride)
+0x40  u16  tail[1]
+0x42  u16  tail[2]
```
The `+0x3E/+0x40/+0x42` reads are intentionally relative to
`desc + 0x30*i`, so for `i` they read bytes just beyond that entry's 0x30-byte
stride (into the following entry). This is preserved literally.

### Slot list (`*(u32*)(self + 0x134)`)
```text
+0x00  u32  element pointer 0
+0x04  u32  element pointer 1
+0x08  s32  element count    (aliases element slot 2)
+0x0C  ...  further element pointers
```
`count` is signed: `ble` at `0x37fe0c` exits for `count <= 0`. Element pointers
are read as `list[index]`; for a count above 2, index 2 therefore reads the
count word. The practical structure holds two entries; the loop bound is still
reconstructed for arbitrary signed values.

## Contract corrections found during implementation
- **The mode-3 branch jumps over the tail and `0x15D14C` work.** `bne 0x37fef4`
  at `0x37fe54` skips from the mode comparison straight to the record build;
  only mode byte 3 executes `0x2C5FF4`, the tail-table writes and `0x15D14C`.
- **The +0x3E tail fields are not inside the 0x30-byte descriptor entry.** They
  are read relative to `desc + 0x30*index`, so they overlap the following entry.
  The original does not use a 0x40-byte stride.
- **The scaler is called three times per iteration at most.** Two calls happen
  once before the loop (the second result is discarded); the third is inside the
  loop only when the (possibly rounded) span is non-zero, even for descriptor
  modes other than 3.
- **`count` aliases element slot 2.** The count word at slot-list `+8` is also
  `list[2]`; the practical list has two entries, so counts above 2 are only
  meaningful as a loop-bound probe.
- **There are no indirect calls.** All six callees are direct BL targets. The
  only data-driven dispatch is the slot-list element read performed by
  `0x15D14C`/`0x15D91C`; those helper bodies are not reconstructed here.

## Limits
- Fixtures are synthetic. The descriptor header/entries, receiver pages, slot
  table, element objects and pointed-to bytes are not captured game data.
- Every helper (`0x2A21B8`, `0x2C5FF4`, `0x37C36C`, `0x15D14C`, `0x2BD448`,
  `0x15D91C`) is stubbed. `0x2A21B8` and `0x2BD448` are modelled from their
  pinned bodies; `0x2C5FF4` is modelled as memcpy; `0x37C36C`,
  `0x15D14C` and `0x15D91C` have deterministic stub outputs, so their real
  layout/packing and slot-attachment effects are not exercised.
- The real meaning of the descriptor fields, the 14-byte span granule, the
  record words and the `0x37C36C` layout algorithm is not established beyond
  the observed reads/writes. No field names beyond the evidence are claimed.
- `0x15D14C` and `0x15D91C` read element pointers from `*(u32*)(self+0x134)`;
  the targets behind those pointers are unresolved. The stubs guard the
  aliased count word so synthetic counts above 2 can still exercise the loop.
- No rendering, engine-state, caller-composition or whole-game runtime
  equivalence is claimed.
- No emulator or canonical full build was run for this record.
