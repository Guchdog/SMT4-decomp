## Recovered details and corrections
- **The third argument of `0x00123C24` is the element count.** `0x131978` is
  `asr r2, r4, #2` with `r4 = end - begin`, so the helper receives
  `(end - begin) >> 2` as its depth bound; the helper halves it on recursion and
  treats zero as the heapsort fallback. The count is forwarded unchanged.
- **The empty test precedes the count.** `cmp r8, sl; beq` at `0x131968` skips
  both the helper call and both sort stages, but never skips the tail call.
- **The threshold test is signed and inclusive.** `mov r0,#0x10;
  cmp r0, r4, asr #2; bge` sends `count == 16` (and any negative count) to the
  single-phase path; `count == 17` is the first two-phase case.
- **The two-phase split is a byte offset of `0x40`, not an element index.**
  `0x131990` is `add fp, r8, #0x40`.
- **The fast branch's copy is a backward word move.** `0x1319E4..0x1319FC`
  copies `*i -> *(i+1)` down to `*first -> *(first+1)` (the loop counter starts at
  `i - first` and the store index is `(i + 4) + 4*k - 4`). It is not a forward
  `memmove` and it does not call a helper.
- **The phase-A fast branch is unreachable on data produced by `0x00123C24`.**
  The introsort stage leaves the range partitioned, so the element at `first` is
  not ordered after any later element; the unguarded tail stage depends on
  exactly that property (it walks down without a bound). Both implementations
  still execute the test, and the branch is exercised by the short-vector path.
  Confirmed by the original faulting (unmapped read at `0x131AA4`, below the
  vector) when the test's introsort stub returned unordered data.
- **`*first` is re-read on every iteration** (`ldr r2,[r7]` with `r7 = first`),
  it is not cached in a register.
- **The comparator result is only tested for zero**, so any non-zero value means
  "ordered"; the candidate preserves that (`!= 0`).
- **The exit reloads `self` twice** (`ldr r0,[sp,#0x38]` and
  `ldr r1,[sp,#0x38]`) and reads `+0x0C` and `+0x04` from the two copies; the
  candidate re-reads both owner fields after the sort, so an introsort or
  comparator side effect on either field would be observed.
- **The original's comparator call sites use four distinct stack scratches**
  (`sp+0x2C`, `sp+0x24`, `sp+0x18`, `sp+0x0C`; `sp+0x18` is shared by the
  phase-B walk and the single-phase fast test because those branches are
  disjoint). The objects are never read; the candidate passes one stateless
  local for all sites.
- **`0x00123C24` has six static `0x002B3B6C` call sites in the original; the
  candidate has eight** because both `insertion_sort` instantiations inline the
  two comparison helpers. The runtime call sequence is identical (53 differential
  cases, ordered call log compared).

## Limits
- `0x00123C24` (1144 B) and `0x002B3B6C` (308 B) are stubbed. The introsort stub
  is a deterministic permutation (plus the minimum-hoist invariant the real
  helper provides), not the real introsort; the ordering stub reimplements the
  predicate recovered above in Python. No real introsort recursion, heapsort
  fallback or key-object validation is exercised.
- The comparator's invalid-key-object arm (flags bits outside `0x40000001`)
  dereferences address `0x4C` in the original and is not exercised; the fixtures
  keep every key object valid.
- The real sink implementations are not exercised; the three vtable targets are
  synthetic stubs, and the vtable is synthetic (only the `+0x14` slot contract is
  taken from the pinned image).
- Fixtures are synthetic: the owner, state, vector, element records and key
  objects are not captured game data.
- The original C++ type names of the owner, state, vector elements, sink and
  comparator are not established; the reconstruction uses offset-named fields
  consistent with the ARM evidence.
- No caller-composition, whole-game or runtime (emulator) equivalence is
  claimed; this is an offline differential result only.
