# Function Record: shop_func_00230ae8 (0x00230AE8)

## Summary
- **Address:** `0x00230AE8`
- **Size:** 408 bytes (original span `[0x00230AE8, 0x00230C80)`)
- **File:** `src/engine/leaf_batch44_b.cpp`
- **Role:** Touch-region scan for the shop list cursor. It polls the signed
  16-bit region handles of a touch list, records whether the list is active and
  which handle index is selected, then either rejects the row, updates one of
  two cursor layouts, or returns immediately.
- **Status:** Semantically equivalent C++ (`non_matching`). The compiled body is
  408 bytes like the original but 352 of those bytes differ (register
  allocation, branch layout and a materialized `0x0100016C` constant instead of
  the literal-pool load); the ledger row is classified `non_matching` and this
  record carries the semantic evidence.

### Setup guard (`0x230B00..0x230B14`)
The three 32-bit loads at `+0x04`, `+0x08` and `+0x0C` are each compared with
`0xFFFFFFFF` via `cmn r0, #1`. If any equals `-1`, the block at
`0x230B18..0x230B74` is skipped entirely and control joins the shared
`+0x11` check at `0x230B78`. In particular the halfword/byte reset and the
handle scan do not run, so the previously stored `+0x11`, `+0x12` and `+0x14`
values are used as-is. A non-`-1` value of `-2` at `+0x04` is treated as
registered.

### Reset and handle scan (`0x230B18..0x230B74`)
When all three ids are registered:
```
[+0x14] = (s16)0xFFFF
[+0x11] = 0
[+0x12] = 0
count = (s32)[+0x0C]
if (count > 0)                    // signed `ble` skips the loop
    for (index = 0; count > index; ++index)   // signed `bgt`, count reloaded
        state = 0x0029D8FC((s16)[+0x18 + index*2])
        if (state == 1 || state == 2) { [+0x11] = 1; [+0x14] = index; }
        if (state == 6)               { [+0x11] = 0; [+0x12] = 1; [+0x14] = index; }
```
The handle load is `ldrsh` (sign extended) and the index store is `strh` (low 16
bits). The count is reloaded from `+0x0C` on every iteration but is not modified
by this function or its helpers. States `0`, `3`, `4`, `5`, `7`, `0x7F`, `0x80`
and `0xFF` leave all three fields unchanged for that handle.

### Shared active check (`0x230B78`)
`ldrb r0, [+0x11]`; when zero the function returns with `r0 = 0`. This path is
taken by the guard-bypassed list when its stored `+0x11` is clear, and by every
registered scan whose last state was neither 1/2 nor 6.

### Cursor update path (`0x230B84..0x230C74`)
`selected = (s16)[+0x14]` and the kind byte at `cursor_host+0x00` chooses the
helper family:

| Kind | position getter (first/third) | object lookup (debug) | setters |
| --- | --- | --- | --- |
| `1` | `0x0029EBDC` | `0x00240EA4` | `0x0022A60C`, tail `0x00299558` |
| everything else (including `0`) | `0x0029F260` | `0x0029E3BC` | kind `0` uses `0x00299000` + `0x0029D8C0` |

Flow:
1. `position = getter(cursor)`.
2. `visible_end = (s32)((u32)position + (u32)selected)`; the original performs
   `add r0, r0, r5`, so the addition wraps at 32 bits. If
   `(s32)[cursor_host+0x08] <= visible_end` (signed `ble`), return
   `visible_end`.
3. `object = lookup(cursor)`.
4. If `[+0x10] != 0` and `(u32)object != (u32)selected`, call
   `0x002B91C4(0x0100016C)`. The constant is the literal-pool word at
   `0x230C7C` (`6c 01 00 01` little-endian).
5. `value = getter(cursor)` (third call).
6. If the reloaded kind is `0`, call `0x00299000(cursor, value)` then
   `0x0029D8C0(cursor, selected)`.
7. If the reloaded kind is `1`, call `0x0022A60C(cursor, value)` then tail-branch
   to `0x00299558(cursor, selected)`.
8. Otherwise return the reloaded kind byte.

The kind byte is reloaded after the helper calls at `0x230B84`, `0x230BAC`,
`0x230BD4`, `0x230BE8` and `0x230C50`; the C++ reads the field at each of those
points rather than caching it.

- `0x0029F260` / `0x0029EBDC` return `0` when the cursor object's `+0x62` byte
  is set; otherwise they tail into `0x002D5674` with the original cursor for

- `0x0029E3BC` returns `*(u32*)(cursor+0x20)` and `0x00240EA4` returns

- `0x0029D8C0` stores at `cursor+0x20` and sets `+0x60` when it changes.

- `0x00299558` stores at `cursor+0x48` and sets `+0x61` when it changes.
Those internal stores are helper-owned; the differential treats the cursor

## Domain Limits
- All ten helpers are deterministic stubs. Their real memory effects and tail
  targets are not modelled; only the observed argument/return contract is
  exercised. In particular the setters' `+0x20`/`+0x24`/`+0x48`/`+0x4C` stores
  and `+0x60`/`+0x61` dirty-byte updates are not applied in the harness.
- The handle count is exercised up to six entries (plus the singleton/boundary
  cases). Arbitrary large counts were not run because the handler polls every
  entry and the harness intentionally keeps runtime bounded; the loop is a
  signed `count > index` comparison with a fresh count load per iteration.
- The guard-bypass path reuses whatever `+0x11`/`+0x14` state the caller left
  behind; this record documents the observed data flow, not the higher-level
  reason the shop screen keeps the stale selection.
- Runtime behavior in the game (how `0x003BB840` consumes `+0x12` and the
  ignored return value) was not exercised; this record covers offline
  differential equivalence only.
