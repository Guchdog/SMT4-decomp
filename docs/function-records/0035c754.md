## Contract and Behavior

- `state = r0`, `out = r1`, `value = r2`.
- `r1` is **not** a live argument register across the body: the callee reloads
  it from the pushed register save area (`[sp+0x3C]` after the
  `push {r0,r1,r2,r4-r11,lr}` / `sub sp,#0x38` prologue) only at the two exit
  stores. Both reads/writes target the caller's `u32*`.

- Returns `0`, `1` (only from `0x0035C65C`) or `2`, or any other non-zero,
  non-`1` handler result. `r4-r11` are preserved and the final SP equals the
  entry SP.
- All four direct calls are `bl` (ARM) to `0x0035C65C`, `0x00238C44`,
  `0x00237F10` and `0x00237EFC`; the per-token handlers are reached with

### Node layout (0x20 bytes = two 16-byte pool units)
```text
+0x00  next          list next
+0x04  prev          list prev (a new node stores the sentinel address here)
+0x08  inner0        container: state->node + 8 (empty nested list)
                     reference: the container address
+0x0C  inner1        container: state->node + 8
                     reference: byte 1 written by 0x00237EFC
+0x10  pool          container: copy of state->child_pool
                     reference: written by 0x00237F10/0x00237EFC
```

A container's empty nested list uses the sentinel at `container + 8`, i.e.
`[container+8] = container+8` and `[container+0xC] = container+8`.
A reference node is initialised by `0x00237F10(node+8)` and then
`0x00237EFC(node+8, &container)`; the second argument is a stack copy of the
container pointer. Both helpers are exact:
- `0x00237F10(p)`: `p[0]=0`, byte `p[4]=1`, `p[8]=p+8`, `p[0x10]=0`, `p[0xC]=p+8`.
- `0x00237EFC(p,v)`: byte `p[4]=1`, `p[0]=*v`.

### Handler tables

indexed by the zero-extended token type byte. The second table is exactly
`+0x98` (19 entries) from the first, so types 0..18 select the 19 shipped
first handlers and the 19 shipped second handlers. The shipped entries all

still implemented because the binary executes it based on the table word and

## Contract corrections found during implementation
- **The second handler's `1` continues the loop.** `0x35C92C` is
  `cmp r0,#1` followed by `cmpne r0,#0`; when `r0 == 1` the conditional
  compare is skipped, so the flags stay equal and the `beq 0x35C890` is taken.
  The loop therefore continues for both `0` and `1`, unlike the first handler
  where `1` is the nested-container signal.
- **The loop advances through the `+0x04` link, not `+0x00`.**
  `0x35C878` is `ldr r0,[r0,#4]`; the same advance appears in
  `0x0035D6AC`. `+0x00` is the other direction of the same circular list.
- **The `+0x10` store is not the list field.** `str r5,[r1,#8]` with
  `r1 = node + 8` writes `node+0x10`, not the sentinel. The nested-list header
  occupies `node+0x08..node+0x14`, and `state->child_pool` is loaded into
  `node+0x10` *after* the list insertion.
- **The descend path allocates from `*value`, not from `parsed`.**
  `0x35C958` loads the pool from `[sp+0x18]` (the value re-read from `*value`
  at the loop head); the initial reference at `0x35C80C` uses `parsed`
  (`[sp+0x20]`).
- **The initial check and the loop check forward different words.**
  `0x35C7A0` forwards `parsed`; `0x35C868` forwards the container pointer.
- **`[sp+0x3C]` is the saved incoming `r1`.** The prologue also pushes
  `r0/r1/r2` for alignment, and the epilogue pops only nine registers after
  `add sp,#0x44`; no fourth argument exists.
- **Two dead stores exist in the original.** `[sp+0x24]` (the reader's value
  copy) is never re-read, and `[sp+0x20] = value2` at `0x35C954` is never
  re-read either; neither is reproduced.
- **Compiler null checks on non-null subobjects.** `adds r1,r0,#8; beq` and
  `adds r0,r6,#8; blne 0x237F10` only skip their work for the impossible
  pointer `0xFFFFFFF8`; container/node null is checked separately.

## Limits
- All helpers (`0x0035C65C`, `0x00238C44`, `0x00237F10`, `0x00237EFC`) and every
  table handler are stubbed with scripted results; no real token scanning,
  pool allocation or macro handler is exercised. In particular the real
  handlers' cursor movement is modelled explicitly by the test stubs.
- The handler tables are synthetic. Only the `0x00472B40`/`0x00472BD8`
  addresses, the 8-byte entry layout and the second-table offset are taken from
  the pinned image.
- Fixtures are synthetic: the parse state, token chain, tree nodes and pools
  are not captured game data.
- The nested-object payload semantics of `+0x08..+0x18` are expressed as raw
  fields; no claim is made about the original C++ type names or about how the
  tree is consumed after this function returns.
- No caller-composition, whole-game or runtime (emulator) equivalence is
  claimed; this is an offline differential result only.
