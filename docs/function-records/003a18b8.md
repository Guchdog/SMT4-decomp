# Function Record: shop_func_003a18b8 (0x003a18b8)

## Summary
- **Address:** `0x003a18b8`
- **Size:** 436 bytes (original span `[0x003a18b8, 0x003a1a6c)`; the 102
  instructions end at the `pop {r4,r5,r6,pc}` at `0x003a1a4c`, followed by the
  seven-word literal pool `0x003a1a50..0x003a1a68`)
- **File:** `src/engine/leaf_batch41_c.cpp`
- **Role:** Shop-scene resource bootstrap. Runs four shared reset/frame helpers,
  loads one named resource into the `+0x160` status word, brings up texture
  group `0x2B`, then selects a second resource plus one or two sprite ids from
  the scene state byte (`+0x14`) and the item type word (`+0x18`). The first
  sprite handle is stored at `+0x15d40`; when the selection also carries a
  second id, a second sprite is created, stored at `+0x15d44` and handed to the
  shared continuation `0x00247d64`.
- **Status:** Semantically equivalent C++ (`non_matching`). The compiled body is
  332 B versus the 436 B original; the compiler keeps a different register set
  (`r4-r8` instead of `r4-r6`), folds the literal-pool names into a single
  `0x00407720` base plus `sub` offsets, and shares the type-6/7 and type-5
  epilogues. The ledger row is classified `non_matching` with this record.

- No stack frame and no stack arguments: the prologue is

## Contract corrections found during implementation
- **`type` is not read on unmatched states.** The `cmp r0,#1 / bne 0x3a1978`
  path skips the `ldr r0,[r4,#0x18]` entirely, so a state byte other than 0/1
  never touches `+0x18`. The C++ keeps the type load inside each branch.
- **The first sprite factory is always called.** Even for an unmatched state
  (`r5 == 0`) the original executes `mov r0,r5` / `bl 0x2fdfb8`, so the
  candidate calls `0x002fdfb8(0)` rather than skipping the call.
- **The first handle store precedes the `second_id` test.** `str r0,[r1,r4]` at
  `0x003a1988` is not conditional in the instruction stream; only the return
  is.
- **`0x00297704`'s fourth argument is dead.** `0x00297704` writes `r3 = 0`
  before its own `bl 0x002ae6c8`, so the candidate declares and calls the
  three-argument form.
- **`0x00015d40` is an offset, not an address.** The literal is used as
  `str r0,[r1,r4]` with `r1 = 0x00015d40` and `r4` holding the object pointer,
  i.e. `object + 0x15d40`.

## Limits
- All ten callees are deterministic stubs in the harness. This record validates
  the caller-side contract (argument values, order, status/handle memory
  effects, return forwarding), not the callees' own behaviour; in particular
  the real resource names behind `0x004076B0..0x00407720` and the real sprite
  tables are outside this span.
- The `0x00247d64` tail declaration is `u32` here only to forward the
  original's `r0`; the reconstruction of `0x00247d64` itself is `void`.
- No emulator run was performed for this span; verification is the static
  original-vs-candidate differential above.
