## Contract and Behavior

### Signature and ABI
```cpp

                             u32 unused,    // r1: never read
                             u32 tag);      // r2: forwarded unchanged to func_002b5318
```
- The original saves `{r3, r4, r5, r6, r7, r8, sb, lr}` (32 bytes) and returns
  through `pop {r3, r4, r5, r6, r7, r8, sb, pc}`; `sb` and the saved `r3` are
  never used as values.  The pushed `r3` word at `[sp]` is reused as the
  by-address child argument for `func_002b52c8`.
- `r4` is the OR accumulator, starting at `0`; `r5` keeps `r0`; `r7` is a
  constant `0` used as the "null" value of every `moveq`/`addne` pair; `r8`
  keeps `r2` (the tag).
- Result: `r4` in `r0`.  It is a pure bit-OR of the two helpers' results, so it
  can carry bit 31 when a query reported negative.
- `r2` is read on entry (`mov r8, r2`); `r1` is overwritten by the first load
  before any use, so the second argument is ignored.

### Input and container layout
`r0` is **not** the container: it points at a word that holds the container.
The only direct caller `0x0013F68C` (`func_0013f68c`) resolves the node's `+0x28`
container, stores it in a stack word, and passes the address of that word:
```text

```
`SlotContainer` (the six self-relative slot words also used by `func_0014ad58`):
```text

+0x04 u32 slot_04
+0x08 u32 slot_08
```

Each slot word is a self-relative offset.  The original reads it through a

uses `ldr r1, [r0]`; the observed value is the same.

### One slot group
Walked in the order `0x0C, 0x10, 0x00, 0x04, 0x08, 0x14`:

```text
container = *(u32*)slot_ref
rel1      = *(u32*)(container + offset)
first     = rel1 != 0 ? container + offset + rel1 : 0     // wrapped sum tested
if (first == 0) skip the whole group

rel2      = *(u32*)(first + 0x08)                          // only if first != 0
child     = rel2 != 0 ? first + 0x08 + rel2 : 0            // wrapped sum tested
candidate = child
if (candidate != 0 && (*(u32*)candidate & 0x40000000) == 0)
    candidate = 0                                          // bit-30 filter

status    = func_002b5318(candidate, tag)
if ((status & 0x80000000) == 0) {
    container2 = *(u32*)slot_ref                            // re-read
    plain      = resolve(container2, offset)                // NO bit-30 filter
    r4        |= func_002b52c8(&plain)                       // plain in a stack word
}
r4 |= status
```
Notes that matter:
- The guard tests only the **first hop** being non-zero.  The second hop's
  zero/wrap result is not a skip: `func_002b5318(0, tag)` is still called.
- The guard's resolution and the candidate resolution are two separate re-reads
  of `slot_ref`/container with no call in between, so they see the same memory;
  the candidate state is identical to the guard state up to the second hop.
- The **second** resolution (before `func_002b52c8`) happens after
  `func_002b5318` may have modified memory, so it re-reads `slot_ref` and the
  slot word and does **not** apply the bit-30 filter.  The differential test's
  `cached_container` and `filtered_dispatch` mutants cover both properties.
- Every branch condition is an exact zero/bit test; there are no signed
  comparisons and no loops.

## Limits
- Fixtures are synthetic pattern-filled pages, not captured game memory.
- `slot_ref` must be a readable pointer to a valid container; a null or unmapped
  `slot_ref`, and a container whose guard passes but whose first hop lands in
  unmapped memory, fault in the original.  Those are preconditions, not modelled
  recovery behavior.  Notably, a helper that rewrites `slot_ref` between the
  guard and the second resolution can make the original load the second hop
  through a zero first hop; the candidate has the same fault behavior, so the
  harness only exercises rewrites that keep the next resolution readable.
- `func_002b5318` and `func_002b52c8` are deterministic stubs here; their real
  bodies, side effects and the indirect targets inside `func_002b52c8` are not
  validated by this test.
- Field names (`slot_ref`, `tag`, `candidate`, `plain`) are descriptive only.
- The original instruction stream is not reproduced (820 B versus 984 B); the
  ledger row is truthfully `non_matching` with this semantic record.
