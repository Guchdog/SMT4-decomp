# Function Record: shop_func_003aa730 (0x003AA730)

## Summary
- **Address:** `0x003AA730`
- **Size:** 620 bytes (original span `[0x003AA730, 0x003AA99C)`; the last word

- **File:** `src/engine/leaf_batch45_a.cpp`
- **Role:** Bible-style screen update callback. It marks a work byte, then runs
  either a selection pass (state != 4) or a cursor/sprite pass (state == 4).
  Both converge on rebuilding the 16-entry selected-id array at `work + 0x96`
  through `0x003AAD98`, one `0x0022DF7C` append per visible entry, and a final
  `0x003AADB0` sanitise pass. The only direct reference to the function in the
  pinned image is the callback pointer at `0x00402294`.
- **Status:** Semantically equivalent C++ (`non_matching`). The compiled body is
  536 B versus the 620 B original; the compiler uses a different register
  allocation and shares the two `0x0029E260(0)` call sites, but keeps the
  original halfword/word accesses and the same ordered call sequence. The
  ledger row is classified `non_matching` with this semantic record.

## Contract corrections found during implementation
- **`0x0029E398` argument is dead.** The original enters the call with `r0`
  holding the entry flag byte (or zero), not the entry pointer. The callee reads
  only a global (`ldr`/`ldr`/`add`/`ldr` at `0x0029E398`), so the candidate passes
  the second entry pointer. The call log intentionally records no argument for
  this helper.
- **`0x003AADB0` is not a standalone ledger row.** It is the second entry point
  inside the 96-byte `0x003AAD98` span (`0x003AAD98 + 0x18`). The candidate
  declares it as `func_003aadb0`; the differential harness resolves it to
  `0x003AADB0`. A future production link needs to split or alias that entry.
- **The cursor index is re-read after `0x2334D8`.** The record pointer is not
  computed from the argument passed to the helper; the original executes a
  second `ldrsh r0,[r7,#0xB2]`. The candidate reloads it, and the test's
  `0x2334D8` stub advances the field to prove the reload is present.
- **Both accessor calls matter.** The first `0x2337A0` result supplies the id;
  the second supplies the flag byte and entry pointer. The id is sampled before
  the second call. A single shared lookup would be observably wrong when the
  helper changes the selection between calls.
- **The two `0x0029E260(0)` calls share one tail block in the candidate.** This
  is a compiler layout choice; both original call sites still execute exactly
  one call with `r0 = 0` before joining.

## Limits
- Fixtures are synthetic: the work page, pick-list entries, slot records and
  child coordinate words are not captured game data.
- Every helper is stubbed. The `0x2334D8` stub advances `work+0xA5B2` only in
  the dedicated re-read case; the real sprite switch is not exercised.
  `0x2BEF70`/`0x2BEF7C` are modelled with safe reads so extreme `s16` cursor
  values do not fault; unmapped-address fallbacks are deterministic functions
  of the address.
- `0x0022DF7C`'s append model writes at the call index rather than reproducing
  its real search / `0x002B9364` lookup. `0x003AADB0`'s 16-slot sanitise loop is
  modelled faithfully. `0x003AAD98`'s four word stores are modelled faithfully.
- `Status_GetFlag1E63`, `StatusDown_GetActiveMode` and
  `StatusDown_GetStatusMode` are declared as `extern "C"` ledger symbols for
  deterministic relocation; their reference implementations currently live in
  the `smt4::ui` namespace.
- The semantic meaning of the `0xA6BE` byte, the `work+0x14` state values and
  the two coordinate helpers' exact UI role are not established beyond the ARM
  evidence.
- No rendering, menu-state, caller-composition or whole-game runtime
  equivalence is claimed.
