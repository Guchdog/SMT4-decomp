# Function Record: engine_func_00140318 (0x00140318)

## Summary
- **Address:** `0x00140318`
- **Size:** 404 bytes (original span `[0x00140318, 0x001404AC)`)
- **File:** `src/engine/leaf_batch28_a.cpp`
- **Role:** selector filter/forwarding pass. Runs an optional pre-check filter,
  performs a vtable lookup, and then either fills a 0x18-byte record from the
  lookup context and forwards its first two words, or iterates a list returned
  by `0x001522DC` and runs the filter over every element.
- **Status:** Semantically equivalent C++ (`non_matching`). The compiled body

## Contract corrections found during implementation
- **The in-loop `tst r7,#8` at `0x00140458` is always true.** Only the
  `flags & 8` path reaches the loop, and `r7` is not modified on the way, so
  the conditional filter call is unconditional. The C++ keeps it as a plain
  call.
- **The loop element load at `0x0014045C` is dead.** `ldr r1,[r0,#4]` is
  immediately overwritten by `mov r1,r0` at `0x0014046C` after
  `0x002ACA0C`. The C++ performs the equivalent indexed read and discards it;
  the compiler removes it, which is unobservable except for a fault on a
  malformed count (the count is trusted by the original too).
- **The list count is re-read at the loop head (`0x00140490` → `0x00140450`/
  `0x0014045C`).** The C++ keeps the list pointer non-const so the load is not
  hoisted; a case where the key helper rewrites the count mid-loop verifies it.
- **`alt_selector` is the second stack word, not `selector`.** The caller at
  `0x002AF74C` stores `0xFFFFFFFF` in `[sp+4]` before the call, which is the
  documented "use the register selector" sentinel. The caller at
  `0x001306F0` passes two different words (`r5`, `r6`).
- **`0x001522DC`'s result is not null-checked.** The original faults on a null
  list at `0x0014043C`; the reconstruction has the same dereference.
- **The record name is cleared between the two helpers.** `0x001403D0..E4`
  stores five zero bytes, overwriting the two bytes written by `0x0014D390`.
  The `0x002AC614` stub log confirms all five bytes are zero at the call.
- **`0x0014D390` writes only `+0x00`, `+0x04`, `+0x08`, `+0x09`.** The rest of
  the record at `0x00140398` starts uninitialised; `0x002AC614` fills it later.
  Initialising the whole C++ record would only change private stack bytes, but
  the reconstruction writes exactly the same three fields the assembly does.

## Limits
- All seven helpers are deterministic stubs with scripted results; no real
  engine lookup, filter, record fill, vtable dispatch or list construction is
  exercised. The vtable slot `+0x10` implementation is unresolved.
- The record/cursor helpers are modelled from their disassembly and the
  existing `0x002AC614` reconstruction; the cursor's internal word semantics
  are not used by this function.
- Fixtures are synthetic; no game data or real caller composition is used.
- The dead element load is not emitted by the C++ (compiler removes the
  discarded read). Fault behaviour on an inconsistent list count is therefore
  not reproduced; with a trusted count the read is in bounds.
- No emulator, whole-game or runtime equivalence is claimed; this is an
  offline differential result only.
