# Function Record: engine_func_0013056c (0x0013056C)

## Summary

- **Size:** 432 bytes (span `[0x0013056C, 0x0013071C)`; the next function starts

- **File:** `src/engine/leaf_batch34_c.cpp`
- **Role:** Walks one inclusive range of engine table indices and forwards each

Details pinned by the ARM encoding:
- The first dispatch compares the lookup result against `1` and then `3`; every
  other value (including `0` and `2`) falls through to the `mov r0,#1` exit.
- Both range pre-checks are unsigned (`addhs` / `blo`) against `u32` values, and
  both loop back-edges use unsigned `bls` (`index <= end`) — a signed compare
  would stop at the `0x7FFFFFFF..0x80000000` boundary and is exercised as such
  by the test.
- The original reloads `[sp+0x0C]` (`info.end`) before each back-edge. Nothing
  in a body iteration can write that stack slot, so the reload is only
  structural; the candidate keeps the bound as a plain local.
- The pre-check and the loop bound are logically redundant for `begin <= end`,
  but the pre-check is the only thing that prevents entry when `end < begin`,
  and it is kept.
- On the forward path the second architected stack word is the *original `r1`*
  (`selector`), because that path is taken at `0x001306CC`, before `r6` is
  overwritten with `info.begin` at `0x001305E0`. Reading `r6` as the loop index
  would be wrong there; the test asserts the forwarded value.
- `0x002AC8E4` is called with `mode = 0` for every index and `0x0014056C` /
  `0x00140318` receive `flags` unchanged. `0x0014D448` receives only
  `(context, index, &set)`.
- The id expansion loop always forwards the four slots in ascending order and
  never more than four (`cmp r4,#4` / `blo`).

## Domain Limits
- All seven direct-call targets are stubbed by address, so their internals
  (`0x00151F64`, `0x002A6D58`, `0x002A6D28`, `0x00151DD0`, `0x002A6D94`,
  `0x001521A4`, `0x00152054`, `0x00152074`, `0x0015209C`, `0x00151FF4` and the

  `0x002AC8E4` / `0x0014056C` / `0x00140318` bodies are documented elsewhere in
  this tree but were not executed here.
- A range whose inclusive end is `0xFFFFFFFF` makes the original's back-edge
  (`index <= end` after the 32-bit increment) wrap forever. The original and the
  candidate both fail to terminate; the test reaches that boundary only through
  a helper failure that exits first, so the hang itself is not differentially
  compared (it is a shared defect, not a difference).
- `0x0014D404`'s third output word (`result + result[0x0C]`) is written by the
  callee and never read by this function, so its contents beyond "the callee
  wrote it" are unverified here.
- Real ids equal to `0xFFFFFFFF` are indistinguishable from empty candidate
  slots; the body has no way to express them and the reconstruction keeps that
  behavior rather than inventing a wide sentinel.
- No runtime, staging or production promotion is claimed.
