## Hazards and corrections
- **Two different projection aspects.** The first camera block uses
  `0x3FD55555` (1.6666666) and the second `0x3FAAAAAB` (1.3333334). The
  differential test caught the naive assumption that both reuse `s3`.
- **`s16` is `0.0f`, `s18` is `-1.0f`.** The `vldr` pair at `0x10f1f4/0x10f1f8`
  loads `0x00000000` and `0xBF800000`; both are reused as `s3/s4/s5` in the
  keyframe matrices.
- **Keyframe conversion is unsigned.** `vcvt.f32.u32` converts the `u32` lookup
  results (0, 2), so `0xFFFFFFFF` becomes 4294967296.0f, not `-1.0f`; the
  candidate casts from `u32`.
- **Argument evaluation order matters.** The original calls
  `0x2C1784` before `0x2C17AC` for both keyframes. The candidate sequences the
  two calls into named locals because C++ leaves call-argument evaluation order
  unspecified.
- **Single stack buffer reused for both camera blocks.** The three vec3 locals
  (`sp+0x00` eye, `sp+0x18` target, `sp+0x0C` up) are written once and passed to
  both `0x2C20A8` calls; `0x2C2210` and `0x2C1FFC` also observe that stack
  region in the original but do not read it (they take `r0`,`r1` and
  `s0..s3` only). The candidate uses shared local arrays.
- **The out-size word is uninitialised in the original** (`[sp]` is passed to
  `0x2C5E3C` before any write). The loader always writes it on every return
  path, so the candidate initialises it to 0 without changing observable
  behaviour.
