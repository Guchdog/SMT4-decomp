# Function Record: camp_func_0013b508 (0x0013B508)

## Summary
- **Address:** `0x0013B508`
- **Size:** 704 bytes (`[0x0013B508, 0x0013B7C8)`: 0x2A8 bytes of code through the
  final `ldr r0,[sp,#4]; add sp,sp,#0x54; pop {r4-r8,sb,sl,fp,pc}`, plus the
  six literal-pool words at `0x0013B7B0..0x0013B7C7`)
- **File:** `src/engine/leaf_batch34_c.cpp`
- **Role:** Bounded retry loop around the engine's shared thread-descriptor
  query. It first tries a non-blocking claim on the shared word at
  `0x00465644`; on success it either publishes/clears the shared wait state or
  fills a thread-descriptor record through `0x0013B364`, and on failure (or a
  negative result) it sleeps `10 * 1,000,000` ns and polls again until the
  64-bit timeout argument or one of the two marker words says to stop.
- **Status:** Reconstructed as readable C++ and **semantically verified**
  against the pinned original. The candidate body is 716 bytes and is not
  byte-identical, so the ledger row is `non_matching` and this record carries
  the semantic evidence.

Notes on the exact shape:
- The three "give up" exits all return `[sp+4]`, i.e. the same `result` value;
  the original stores it there with `str sb,[sp,#4]` before the sign test.
- The second marker comparison in the entry block (`timeout == primary`) is
  redundant after the first branch but present in the original; the candidate
  keeps it.
- The claim-failure branch does **not** call `0x002A84D0`; only the two
  successful arms reach the common release.
- The `r3` re-load on every iteration is preserved as a single value because
  nothing in the loop can change `[sp+0x50]`.
- The shared-word path stores through `r1` before checking anything, so a null
  `second_output` is an unmapped write in both implementations (verified by a
  dedicated fault case).
- The `svc #0x23` release only happens when the caller passed no sixth output:
  in that case the descriptor handle lands in the private `[sp+0x2C]` slot and
  is closed if the callee left it non-zero.

### Elapsed-time reduction (`0x0013B704..0x0013B774`)
One `svc #0x28` (`GetSystemTick`, 64-bit in `r0:r1`), a wrapping 64-bit
subtraction of the baseline, then the same fixed-point stage as
`engine_func_0011b6a8`: bits 32..95 of the signed 64x34 product with
`0x3BAD34AEE = 3*2^32 + 0xBAD34AEE`, i.e. 268,111,856 Hz ticks → nanoseconds.
The literal pool supplies `0xBAD34AEE` and `mov r2,#3`, exactly like the
sibling. The final test is a signed 64-bit compare (`subs`/`sbcs` + `blt`)
between the timeout and the reduced elapsed value.

ARMv6K has no `__int128`, so the candidate reuses `MultiplyHighSigned` and
`kTickNanosecondsMagic` from the `0x0011B6A8` reconstruction in the same file
(they recover the same partial products the original computes).

## Domain Limits
- Every direct call is stubbed, so the real claim/lock/descriptor behaviour is
  not exercised: in particular the private `0x00465644` claim word, the shared
  `0x0044E390` word, the engine object lock and the `svc #0x32` descriptor
  service are driven deterministically by the fixtures. Whether the real
  helpers write `0x0044E370`/`0x0044E378` at runtime is unresolved; the scans
  only prove that no direct 32-bit literal or `movw`/`movt` reference stores to
  them.
- The two marker words are equality-only sentinels here. Their producer and
  their relation to the two callers' retry sentinels
  (`0xC8A0CFF0`/`0xE0A0CC08`/`0xC8A0CC02`) are not decoded.
- `0x0013B364`'s `svc #0x32` service and the meaning of the TLS control word
  `(count << 14) | 2` are only observed, not proven; the fourth argument of
  `0x0013B364` is therefore typed as an opaque `u32*` (it is either the
  descriptor buffer or a private dummy).
- Tick values are supplied by the test. The real tick source, the exact
  frequency relation and the units of the timeout argument are inferred from
  the shared `0x3BAD34AEE` reduction documented for `0x0011B6A8`.
- The redundant `timeout == primary` check inside the entry marker block cannot
  be observed separately from the first comparison; the candidate keeps it.
- No runtime/emulator execution, staging or production promotion is claimed.
