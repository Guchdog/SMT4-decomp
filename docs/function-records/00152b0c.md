# Function Record: engine_func_00152b0c (0x00152b0c)

## Summary
- **Address:** `0x00152b0c`
- **Size:** 600 bytes (original span `[0x00152b0c, 0x00152d64)`). The body ends
  with the `pop {r4, r5, r6, r7, r8, sb, sl, fp, ip, pc}` at `0x00152d4c`; the
  five words `0x00152d50..0x00152d63` are the literal pool (`0x00464B94`,
  `0x00464B8C`, `0x004DAD80`, `0x00464B84`, `0x00464B7C`) plus four padding
  bytes.
- **File:** `src/engine/leaf_batch34_c.cpp`
- **Role:** Teardown/finalisation pass for one engine "task action" record. It
  resolves which of the two engine registry slots the action belongs to, erases
  the action's entries from their container vectors, optionally unregisters the
  slot with the shared engine sync helpers, decrements the selected frame-sync
  counter and resets the action's state/pending words. The only direct caller is
  `0x002A7AA0` (`script_vm_func_002a7aa0`), which invokes it on
  `task->field_8` when that record's signed state word is `>= 0` and discards the
  result.
- **Status:** Reconstructed as readable C++ and **differentially verified**
  against the pinned original (53 cases + 6 negative controls). The candidate
  body is 584 bytes and is not byte-identical (different register allocation,
  a `strh` instead of two `strb` gate stores, and a different case-block
  layout), so the ledger row is `non_matching` and this record carries the
  semantic evidence.

## Contract and Behavior

### Signature and ABI
```c
extern "C" u32 engine_func_00152b0c(engine_152b0c::ActionRecord* action);
```
- `action = r0`; `r1..r3` are never read.
- **Return value:** the routine has no computed result; every return site
  propagates whatever the original happened to leave in `r0`:
  - `state` not in `{1, 2, 4, 5}` and no pending record: `0x00464B8C` (the
    literal loaded at `0x00152b2c`);
  - pending record present and its `+0x00` word zero: the pending pointer;
  - `state == 2` with a zero container gate: the return value of `0x002A3068(0)`
    (`0x004DAD80` in the pinned image);
  - `state == 5` with a zero container gate: the return value of `0x002A3068(1)`
    (`0x004DAD98`);
  - `state == 1` or `state == 4` with a zero gate: `0x00464B8C`;
  - every full teardown path: `0xFFFFFFFF` (`mvn r0,#0`).
  `0x002A7AA0` ignores the result.
- The original preserves `r4-r8, sb, sl, fp` **and `r12`** (the `push` list
  contains `ip`). `r12` is caller-saved, so the candidate does not reproduce it;
  the differential test compares `r4-r11` only and this deviation is documented.
- No stack arguments, no floating point, no indirect call of its own.

### Control flow
1. `pending = action->pending_14`. If non-null, `gate = *(u32*)pending` and the
   state word is never read. Otherwise dispatch on the **signed** state:
   - `1` -> `gate = *(u32*)0x00464B8C` (r0 was reloaded with that literal at
     `0x00152B2C`, so `0x00152CD4` dereferences the token table, not the null
     pending pointer);
   - `2` -> `gate = [0x00464B94]`, then `0x002A3068(0)`;
   - `4` -> `gate = [0x00464B90]`, no helper call;
   - `5` -> `gate = [0x00464B98]`, then `0x002A3068(1)`;
   - anything else returns immediately.
2. `gate == 0` returns immediately.
3. `first = action->entries_24[0]`; `owner = first->container_0C`
   (unconditionally, before the count test). `slot = 0` when
   `[0x00464B94] == owner`, else `slot = 1` when `[0x00464B98] == owner`, else
   `-1`. The second table word is only read when the first misses.
4. For `index = 0; action->entry_count_28 > index; ++index` (count re-read each
   iteration, signed `bgt`):
   - `entry = entries[index]`, `container = entry->container_0C`;
   - `container == 0` -> next entry;
   - linear scan `[container->begin_18, container->end_1C)` for the first word
     equal to the entry pointer;
   - when found, forward-compact `[found + 1, end)` with libc++ `remove`
     semantics, skipping every word equal to the entry pointer;
   - re-read `container->end_1C`, store the new end (equal to `end` when the
     entry was absent), and clear `entry->container_0C` only when the end moved.
5. When `slot >= 0` **and** `owner->begin_18 == owner->end_1C`:
   - clear the slot's `+0x04`/`+0x05` bytes;
   - `container_word = [0x00464B94 + slot*4]`, `registry = [0x00464B84 + slot*4]`;
   - `0x002C028C(registry, container_word)`;
   - `registry = [0x00464B84 + slot*4]` (re-read after the call),
     `work = [0x00464B7C + slot*4]`;
   - `0x002ABDB0(work, registry)`.
6. Re-read `action->pending_14`; choose `sync_slot = (pending != 0)
   ? (pending->side_08 != 0 ? 1 : 0) : (state >= 3 ? 1 : 0)` (signed). Then
   `0x002ABDB0([0x00464B7C + sync_slot*4], [0x00464B84 + sync_slot*4])` and
   `[0x004DAD80 + sync_slot*0x18] -= 1` (32-bit wrap).
7. Re-read `action->pending_14` again. If non-null: `+0x10 = -1`, `+0x14 = 0`,
   `state = -1`, `+0x18 = pending`. Otherwise: `+0x18 = 0`, read the current
   state, `state = -1`, `+0x10 = previous state`. Both branches return
   `0xFFFFFFFF`.

## Contract corrections found during implementation
- **`state == 1` does not dereference the null pending pointer.** `r0` is
  reloaded with the `0x00464B8C` literal at `0x00152B2C` before the `beq
  0x00152CD4`, so the shared `ldr r5,[r0]` reads `token_table[0]`. The first
  differential run caught this: with the wrong model the original still ran the
  full teardown while the candidate returned early.
- **The return value is a dead register, not a status.** Each early exit leaves
  a different value in `r0` (pending pointer, `0x2A3068` result, `0x00464B8C`,
  or `-1`); the C++ reproduces them because they are observable to a caller that
  inspects `r0`.
- **Entry 0 is dereferenced before the count check** (`0x00152B70..0x00152B80`),
  so a zero or negative count does not make a null entry array or null entry 0
  safe.
- **The container end word is written back on every visit**, including when the
  entry was not found; only a moved end clears `entry->container_0C`.
- **The slot table entries are re-read around both helper calls.** A stub that
  rewrites `0x00464B84`/`0x00464B7C` inside `0x002C028C` changes the arguments of
  the following `0x002ABDB0`.
- **The sync slot and the reset branch both use a *re-read* pending pointer**
  taken after the helpers (`0x00152CB8` and `0x00152D1C`). A `0x002ABDB0` stub
  that clears or replaces the pointer changes both decisions.
- **`0x2A3068` has real side effects.** Its `+0x04 = 1`, `+0x05 = 0` writes are
  visible when the slot is not unregistered afterwards (e.g. `slot == -1`); the
  differential stub reproduces them instead of returning a constant.
- **The `state >= 3` test is signed and can only be reached without a pending
  record**, and states `0`/`3` never reach it through the dispatch. The
  boundary is exercised by having a later helper change the state to `3`.

## Limits
- Fixtures are synthetic: the action record, pending records, entries,
  containers, slot tables and frame-sync block are hand-built, not captured game
  data.
- Every helper (`0x2A3068`, `0x2C028C`, `0x2ABDB0`) is stubbed. `0x2A3068`'s
  observable write/return behaviour is reproduced; `0x2C028C` and `0x2ABDB0`
  perform vtable dispatches internally (`[registry]`+0x10 and `[work+8]`) whose
  targets are not identified here.
- The meaning of the action state machine (states `-1..5`), of the pending
  record's gate/side words and of the per-slot objects is inferred from the
  access pattern and the sibling routines (`0x001182DC`, `0x00132240`,
  `0x002A7AA0`); it is not proven beyond that evidence.
- The records are dereferenced without null checks. Null entry 0 / null matching
  container faults in both builds; the harness treats "both faulted" as equal
  and compares only the effects before the fault, so fault-site identity is not
  claimed.
- `r12` differs between the original (restored by its push list) and the
  candidate (not preserved); the comparison covers `r4-r11` only.
- Fixture shapes are bounded (at most a few entries, one container page); the
  compaction loop is verified over odd/even lengths up to four elements, not over
  arbitrary vector sizes.
- No emulator or whole-game runtime session was run; equivalence is offline
  differential evidence only. The caller `0x002A7AA0` was inspected statically,
  not composed.
