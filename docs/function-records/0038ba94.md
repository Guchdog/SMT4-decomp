# Function Record: script_vm_func_0038ba94 (0x0038ba94)

## Summary
- **Address:** `0x0038ba94`
- **Size:** 452 bytes (original span `[0x0038ba94, 0x0038bc58)`; 110 ARM
  instructions through the unconditional `pop`, then 12 bytes of inline
  jump-table/literal-pool data)
- **File:** `src/engine/leaf_batch41_c.cpp`
- **Role:** Rebuilds the "listed" flags of one sub-table from its row category
  bytes. For every row of TBB sub-table 0 it reads a signed category byte from
  the row's first byte; selected categories are formatted as
  `"<self+0x24>/<row+1>"` and handed to a renderer together with the matching
  16-byte state entry. The whole body is gated on `self+0x45` being non-zero.
- **Status:** Semantically equivalent C++ (`non_matching`). The compiled body is
  272 B versus the 452 B original: the original keeps a 48-entry inline jump
  table and an inline `"%s/%s"` literal, while the candidate uses a 48-byte
  `.rodata` predicate table plus `.rodata.str1.1`, and clang allocates
  registers/frame differently. The ledger row is `non_matching` with this
  semantic record.

## Contract corrections found during implementation
- **The count test is an unsigned zero test.** `subs r7,r0,#0` followed by `bls`
  cannot be taken for a negative count (subtracting zero sets carry), so a
  `u32` row count of e.g. `0xFFFFFFFF` iterates that many rows rather than
  exiting. The candidate uses the `u32` count directly.
- **Signed category, unsigned bound.** `ldrsb` loads a signed byte, then
  `cmp r0,#0x30` / `ldrlo` uses an unsigned comparison. Negative categories
  (`0x80-0xFF`) never index the jump table.
- **The entry-array pointer is re-read twice per rendered row.** Once after the
  format call (for the render argument) and again after the renderer returns
  (for the `+0xC` flag store). The C++ re-reads `self+0x4c` at both points.
- **The mode byte and container are re-read before the row-count lookup.**
  `0x38BAD4`/`0x38BADC` reload them instead of reusing the first values.
- **`0x38A364` takes two stack words.** It is called with `r0 = *(0x00433130)`,
  `r1 = text`, `r2 = entry`, `r3 = 1`, and `[sp] = 0x80`, `[sp+4] = entry`.
- **The format literal is data.** `add r1, pc, #0x50` points at `0x0038BC4C`,
  whose bytes spell `"%s/%s"`; it is not a pointer-valued constant.
- **No indirect calls.** All six callees are direct `bl`/`blx` targets.

## Limits
- Fixtures are synthetic: `self`, container/table, entry arrays, payload rows,
  names, prefix and the global manager cell are not captured game data.
- All six helpers (`0x2AC2F4`, `0x2C0E9C`, `0x2C0E4C`, `0x2C4B30`, `0x2BE7FC`,
  `0x38A364`) are stubbed; no real TBB parsing, memory zeroing, text
  formatting, rendering or engine state is exercised.
- The real meaning of the `self+0x24` prefix, the `self+0x45` mode and the
  entry `+0x0C` flag is not established beyond their observed use. The
  renderer's real fifth/sixth argument semantics are opaque 32-bit words.
- The `0x80`-byte text buffer width is taken from the original frame; the
  format helper's real truncation/overflow contract is not modeled.
- Caller composition, runtime/emulator validation and whole-game equivalence
  are not claimed.
