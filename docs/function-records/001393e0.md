# `func_001393e0` (0x001393E0)

## Summary
- **Address:** `0x001393E0`
- **Size:** 976 bytes
- **Domain:** Calendar / time-based regeneration accumulator
- **Status:** Semantically verified (`non_matching` in ledger)
- **Source File:** `src/engine/leaf_batch34_c.cpp`
- **Differential Suite:** `tools/test_leaf_001393e0.py`

## Role and Behavior
The routine is a periodic "day tick".  It reads the current calendar date,
reconstructs the stored date held in the state record, and decides whether the
record is due for a catch-up pass.  A catch-up pass advances the stored
timestamp one day (86,400,000 ms) at a time until it reaches the present one,
charging a checksum difference into two saturating counters.

### State record (`r0`, offsets observed in the ARM code)
| Offset | Width | Meaning |
|--------|-------|---------|
| +0x04  | u16   | `counterA`, saturates at 300 (`0x12c`) |
| +0x06  | u16   | `counterB`, saturates at 10 (`0x0a`) |
| +0x08  | u32   | `lastStamp`, compared against the result of `0x0013924c` |
| +0x0C  | u32   | `accum`, checksum of the 24 calendar words |
| +0x10  | s16   | stored year (low 16 bits of the date record's first word) |
| +0x12  | s8    | stored month |
| +0x13  | s8    | stored day |

Offsets +0x00..+0x03 are never read or written.

### Calendar record (`0x002AD8F8` output, 12 bytes)
| Offset | Width | Meaning |
|--------|-------|---------|
| +0x00  | u32   | year (word 0); the caller keeps only the low 16 bits |
| +0x04  | s8    | month |
| +0x05  | s8    | day |
| +0x06  | s8    | unknown byte, copied through but never reinterpreted |
| +0x07  | s8    | hour |
| +0x08  | s8    | minute |
| +0x09  | s8    | second |
| +0x0A  | s16   | millisecond |

The caller immediately zeroes hour/minute/second/millisecond after copying the
record, then converts it to a millisecond timestamp through `0x00139F20`.

### Control flow
1. `engine_func_002c586c(&raw64)` reads the current raw time; a copy is passed to
   `engine_func_002ad8f8(&date, &raw64)` to unpack the calendar record.
2. The time-of-day fields are zeroed and `func_00139f20(&firstMs, &date)`
   produces the "present" timestamp. `func_002ad714(&secondMs, year, month, day,
   0, 0, 0, 0)` produces the stored timestamp (hour..millisecond are zeroed
   stack arguments).
3. `func_0013924c()` returns the current frame/stamp value used for cooldowns.
4. Rebuild branch (`0x1394B4`): taken when `first < second`, or `lastStamp >
   cur`, or `counterA >= 300`, or (`first == second && counterB >= 10`). It
   clears `counterB` when the two timestamps differ, stores `lastStamp = cur`,
   and recomputes `accum` as the sum of the 24 u16 words produced by
   `func_00139230(&words, 0x18, first)`.
5. Advance branch (`0x139520`): if `(u32)(cur - lastStamp) < 100`, the function
   returns immediately with that difference. Otherwise it loops:
   - exit the loop when `first < second`;
   - build the calendar words for the current `second` via
     `func_00139230(&words, 0x18, second)` and sum them (24 u16 words, 48 bytes);
   - the accumulator base and `counterB` base are only used on the first
     iteration (the function compares the current `second` with the copy taken
     before the loop); later iterations use base 0;
   - `elapsed = max(0, total - base)`, `steps = elapsed / 100`, and the
     remainder is `elapsed % 100`;
   - `delta` starts as `steps`; if `counterB + steps >= 10` it becomes
     `max(0, 10 - counterB)` and the remainder is cleared; if
     `counterA + delta >= 300` it becomes `max(0, 300 - counterA)` and the
     remainder is cleared again (the same delta feeds both counters);
   - when `first == second` the function stores `counterB = counterBBase +
     delta`, `lastStamp = max(0, cur - remainder)`, and `accum = max(0, total -
     remainder)`;
   - `counterA += delta` and `second += 86400000`, then the loop repeats.
6. Tail (`0x13976C`): stores the (low 16 bits of the) new year, month and day
   back into the state record, clamps `counterA` to 300 when it is greater than
   300, and returns (in `r0`, not part of the caller contract): `300` when the
   clamp triggered, otherwise the zero-extended day byte.

## ABI and Calls
- `r0` is the only incoming argument (state pointer); the function returns a
  value in `r0` but callers ignore it.
- Callee-saved registers `r4-r11` are preserved; the frame is 0xA0 bytes
  (`push` of 9 registers + `sub sp, #0x7C`).
- Direct calls, in order: `0x002C586C`, `0x002AD8F8`, `0x00139F20`,
  `0x002AD714`, `0x0013924C`, then `0x00139230` once per rebuild/loop step.
- `0x002AD714` is called with four stack arguments (`hour, minute, second,
  millisecond`) that are all zero.

## Differential Verification
`tools/test_leaf_001393e0.py` compiles the translation unit, extracts the
candidate body, resolves the seven `R_ARM_CALL` relocations to deterministic
stubs at the original addresses, and runs the pinned original
(`extracted/exefs/code.bin`) against the candidate in separate Unicorn ARM
machines with identical fixtures.

Compared: return `r0`, continuation PC, final SP, `r4-r11`, the ordered call log
with every register argument and the four stacked `0x002AD714` arguments, the
calendar record observed by the `0x00139F20` stub (proving the time-of-day
zeroing and the signed month/day/year extension), the full 64 KiB state page,
and any write outside the private stack and the state page.

Coverage: both entry branches and the early-return window at exactly 0/1/99/100
units; equality on the first and on later loop iterations; `counterA` and
`counterB` below/at/above their caps; accumulator divisor boundaries
99/100/999/1000; sum-below/equal-to accumulator; multi-day loops; signed 64-bit
timestamps including negative and near-`INT64` values; signed year/month/day
bytes. 42 differential cases plus four mutant negative controls (day step,
counter A cap, counter B cap, early-return threshold) pass.

## Evidence Limits and Unresolved Targets
- The four calendar helpers are stubbed: `0x002C586C` (raw time),
  `0x002AD8F8` (calendar unpack), `0x00139F20` (calendar → ms), and `0x00139230`
  (24-word calendar buffer). Their internal contracts are inferred from the
  register traffic and are recorded above, not proven here.
- `func_002AD714` was reconstructed separately (`docs/function-records/` for
  `0x002AD714`); its day-count helper `script_vm_func_002a8730` is outside this
  record.
- `func_0013924c()` returns an opaque current-stamp value; the magnitude of
  `cur` only affects the early-return window and the stored `lastStamp`.
- Byte identity is not claimed: the candidate compiles to a different size and
  frame layout. No emulator or whole-game runtime scenario was executed for
  this record.
