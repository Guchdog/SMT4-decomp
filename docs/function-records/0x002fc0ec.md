# `TitleConfig_IsReady` (`0x002FC0EC`)

## Recovered contract

- ABI: zero explicit arguments; returns a boolean-like `u32` in `r0`; preserves the normal ARM callee-saved state. It reads `g_TitleConfigWork` through absolute global pointer `0x0044E2D0`.
- If `g_TitleConfigWork == nullptr`, it returns `1` without calling another function.
- Otherwise it reads the task handle at `work+0` and calls `battle_func_002BF41C(task)`.
- It returns `0` when that helper reports the task is still registered, and `1` when the helper reports the task is no longer registered. A null task handle is passed through when the global work pointer is non-null; the predicate itself does not special-case it.

## Caller meaning and evidence

The pinned body at `[0x002FC0EC, 0x002FC120)` is 52 bytes. `python tools/split_asm.py --addr 0x002fc0ec` shows: load the global work pointer, branch to return-ready if null, load `work->calc_task`, call `0x002BF41C`, invert its zero/nonzero status, and return. The initializer allocates a `TitleConfigWork` whose first field is `calc_task` (`include/camp/title_flow.h`, size `0x158`). The accepted secondary contract documents `0x002BF41C` as a boolean-like task-registration lookup.

In the title caller (`src/ui/ui_runtime2.cpp`, state 10), `TitleMain_Calc` waits when `TitleConfig_IsReady()==0`; on `1` it calls `Title_ResetForBoot` and proceeds toward title state 5. Thus this is a completion gate for the registered Calc task, not a general UI-ready/resource-ready query.

## Production source integration

`src/engine/leaf_batch26_b.cpp` now expresses the predicate as readable C++, retaining the original global address and calling the original task-registration helper directly through its C-linkage symbol. The current production symbol is 48 bytes within the pinned 52-byte span. Its sole relocation is an `R_ARM_CALL` at symbol offset 28 to `battle_func_002bf41c`; at final VMA `0x002FC0EC`, the call site `0x002FC108` resolves to `0x002BF41C`. The remaining four bytes in the original span are left untouched in the planned in-place replacement.

The exact production symbol passed all four directed cases at its final VMA using a task-local relocation-aware runner. Return value, return PC, helper trace, SP, `r4-r11`, and `d8-d15` matched, and the always-ready control was detected. Production source/object/symbol hashes and the report are in `docs/agent-work/h2-ready-direct-call-optimization.md` and its task packet. The run-013 shared patcher resolves its call and the final-address differential repeats the four cases against the exact five-function image. The State-9/10 caller also executes this body, with the task-registration helper kept as an HLE.

The ledger is `non_matching` because the production source differs from the pinned bytes. This classification does not itself promote the function.

## Limits

The helper implementation is modeled, not revalidated by the callback differential. The comparator checks SP restoration and preserved registers, not caller-owned stack bytes. Caller composition verifies the State-9/10 path with this production gate but leaves task registration and other subsystem services as HLEs; it does not schedule registered callbacks. There is no Azahar runtime, settings input/edit/cancel/confirm, persistence, or restart evidence yet.
