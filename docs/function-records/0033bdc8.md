# Function Record: script_vm_func_0033bdc8 (0x0033BDC8)

## Summary
- **Address:** `0x0033BDC8`
- **Size:** 684 bytes (span `[0x0033BDC8, 0x0033C074)`; the last two words
  `0x0033C06C = 0x00000604` and `0x0033C070 = 0x002013E8` are the literal pool
  and are not executed)
- **File:** `src/engine/leaf_batch45_a.cpp`
- **Role:** NkmGrowEvent demon-record merge. Copies a 0x604-byte growth record,
  merges its 0x40 flag bytes and 0x500 stat bytes into the live Nkm record
  selected by the growth record's `+0x4A` index, collects the growth record's
  skill ids that the live record does not already know, sorts them, and either
  installs them into the live record's free skill slots (return 0) or rejects
  the whole batch when the capacity recovered from `0x0029CB94` cannot cover it
  (return 1). Both paths notify `0x0029C950`.
- **Status:** Reconstructed as readable C++ and **semantically verified**
  against the pinned original with a differential runner. The candidate body is
  2896 bytes with 17 `R_ARM_CALL` relocations and no data relocations; it is not
  byte-identical (different register allocation, larger unrolled frame, `uqadd8`
  for the saturating add loop), so the ledger row is `non_matching` and this
  record carries the semantic evidence.

    else                           ++known              // original re-tests id != 0

    id = out[i]

    if ((s32)known >= 8) continue                       // `cmp sb,#8; bge`

Notable details preserved in the C++:

- The index comparison sign-extends the manager byte but zero-extends the
  record index (`ldrsb` versus `ldrb`), so an index of `0x80..0xFF` can never
  match a stored byte with the same bit pattern.
- The source index is read twice: once from the stack copy for the live-index
  comparison and `0x0029C468`, once from the original source pointer for
  `0x0029BE68`. Both are the same byte; the C++ keeps the two reads.
- The `0x002A8A08` argument is the leftover `memcpy` return value (`buf + 0x604`);
  the getter ignores it, but the call log preserves it.
- Only one zero terminator is written at `out[new]`. Entries after it are the
  caller's previous contents; the qsort of all eight entries and the install
  loop therefore can see them, exactly as in the original.
- `capacity` is a signed `s32`. Zero and negative values skip the zero-count
  loop, `1..8` count that many live slots, and values above eight read past the
  skill array (`+0x46` id word at capacity 9).
- The zero-count loop is a plain pair-unrolled countdown in the original
  (`subs`/`ldm`-style pointer walk) but has exactly the semantics of
  `for (i = 0; i < capacity; ++i)`; the C++ uses the simple form.
- The install loop searches from `known`, not from slot 0, and rejects all
  inserts when `known >= 8`; both quirks are kept.
- The qsort receives the whole eight-entry array, not just the `new` entries.

## Domain Limits
- All ten helpers are stubbed, so their own bodies are not compared. The field
  contracts above come from reading the pinned callees; internal lookups
  (`0x002041xx`-family table readers, `0x002C4B30`, `0x002032B8`,
  `0x001DD9F4`, the `0x002013E8` rank table `0x0029EC14`) remain unresolved at
  this level.
- `0x0029C468`'s stub models the observable `0x001A7CAC` mode-0 rebuild: zero
  fill, `+0x46`/`+0x48`/`+0x4A`, eight skill slots, `0x40` flag bytes, `0x500`
  stat bytes and the free-list claim. The real camp-table copy (values from the
  `0x002B9364` entry) is not reproduced; both machines run the same stand-in.
- The qsort stub sorts the eight `u16` entries ascending instead of using the
  `0x002013E8` rank/order comparator. The call arguments (including the
  comparator address) are compared, but the real ordering of the installed ids
  is not reproduced; both machines see the same sorted array.
- `0x0029CB94` is stubbed to a case-controlled value. The pinned callee always
  returns 4..8, so capacities outside that range are fault-injection boundary
  tests for the candidate's loop bounds, not claimed game behavior.
- No real caller was exercised; the single pinned caller at `0x00217110` is
  used only as evidence for the three argument roles. Whole-game equivalence,
  staging and production promotion are not claimed.
